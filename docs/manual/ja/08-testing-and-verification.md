# 8. テスト — DSQL が主導するシナリオ

_言語: [English](../en/08-testing-and-verification.md) | [한국어](../ko/08-testing-and-verification.md) | **日本語**_

> **前へ:** [7. パフォーマンスとチューニング](07-performance-and-tuning.md)

この章は一つの考え方に沿って構成されています。すなわち、**Aurora DSQL の各特性が、テストすべき特定のマイグレーションシナリオを不可避的に生み出す** という考え方です。MySQL→MySQL のマイグレーションでは、これらを証明する必要は決してありません。これらのシナリオが存在するのは、まさに DSQL が異なるエンジン(PostgreSQL ワイヤプロトコル、分散型、サーバーレス、IAM 認証、楽観的並行性制御)だからです。以下では DSQL の各特性について、それが生み出すシナリオと、ツールがそれをどのように検証するかを列挙します。

> すべてのシナリオは 2 つのテストレイヤーで裏付けられています。1 つは **オフラインスイート**(約 3,100 件の Python テスト + 72 件の Java テスト。AWS を使わず、シーム(seam)を注入)で、その動作を決定論的に証明します。もう 1 つは **ライブの end-to-end 実行**(実際の RDS MySQL + Aurora DSQL + MSK)で、意図的に失敗させる行を含めて実インフラ上でそれを証明します(§8.2 に要約)。

---

## 8.1 DSQL 特性が生み出すシナリオ

### トランザクションの形状 — DSQL はすべての書き込みトランザクションに上限を課す

DSQL は 1 トランザクションあたり **3,000 行以下**、**変更データ 10 MiB 以下**、**5 分以下**、そして **DDL 1 つ** を許容します。これを無視するローダーは、そのまま失敗するか、あるいは静かにデータを切り捨ててしまいます。

| DSQL 特性 | テストするシナリオ | どう検証するか |
|---|---|---|
| 1 トランザクションあたり 3,000 行以下 | 1 トランザクションに収まらない大きさのテーブル。上限ちょうどのバッチ。上限を超えるリクエスト | バッチの行数に上限を課す。上限は受け入れ、上限超過は拒否する(`test_batch_size_at_the_hard_cap_is_accepted`、`…_above_the_hard_cap_is_rejected`) |
| 1 トランザクションあたり 10 MiB 以下(安全予算 8 MiB) | 行数よりも先に **バイト数** が上限を超える幅広い行。予算を超える単一行 | 行数分割の前にバイト数を考慮した分割を行う。サイズ超過の単一行は単独で yield される(`test_iter_batches_splits_on_byte_budget_before_row_count`、`…_single_oversized_row_yields_alone`) |
| 1 トランザクションあたり DDL 1 つ | テーブルのセカンダリインデックスの作成 | 各インデックスの DDL はそれぞれ独立したトランザクションで実行される(`test_indexes_created_after_all_data_each_its_own_statement`) |

### 楽観的並行性制御 — DSQL にロックはなく、競合はコミット時に顕在化する(40001)

DSQL は書き込み競合をコミット時に検出し、`SQLSTATE 40001` を返します。敗れたトランザクションは **再実行** しなければならず、競合が激しい状況ではこれが頻繁に発生します。

| DSQL 特性 | テストするシナリオ | どう検証するか |
|---|---|---|
| 書き込みでの 40001 競合 | あるバッチがシリアライゼーション競合に遭遇し、その後リトライで成功する | バックオフ/ジッターを伴うステートメント単位のリトライで回復する(`test_occ_conflict_on_batch_is_retried_then_succeeds`)。CDC シンクにも同じロジックがある(`OccRetryTest.java`) |
| リトライ予算の枯渇 | 競合が一向に解消しない | **失敗** として記録され、決して静かに破棄されない(`test_exhausted_occ_conflict_is_recorded_as_failure`) |
| 高並行性と接続クォータ(クラスターあたり 10,000、毎秒 100) | 多数のテーブル × 多数のバッチを同時に処理 | 進行中の合計接続数は上限内に収まる(`test_parallel_connection_use_is_bounded`)。デフォルトは 4 テーブル × 8 バッチ = 32 で、クォータをはるかに下回る |

### 値あたり 1 MiB の上限 — 単一の大きな値は保存できない

| DSQL 特性 | テストするシナリオ | どう検証するか |
|---|---|---|
| 1 MiB を超える値 | Full Load 中 **および** CDC 中に、上限を超える LOB/TEXT 値 | Full Load では行単位の **隔離**(quarantine)(PK と理由を記録し、テーブルの読み込みは継続)。シンクでは書き込み前に計測して **DLQ** へ(`DsqlSinkTask` のサイズ超過ガード) |
| 8 MiB を超える値(Kafka を通過できない) | さらに大きなカラム | Evaluation の `OVERSIZED_LOB` フラグに基づき、Debezium の `column.exclude.list` によって **キャプチャ時点で** 除外する |

### IAM トークン認証 — パスワードなし、15 分のトークン、60 分の接続

| DSQL 特性 | テストするシナリオ | どう検証するか |
|---|---|---|
| 短命なトークン / 切断された接続 | トークンの寿命を超えて、または 60 分の接続上限に達して継続する長時間のロードや CDC ストリーム | プールは死んだ接続やハーフオープンの接続を破棄し、リトライは **新しい** トークンで再接続する(`test_transient_connection_error_is_retried_and_recovers`、`test_pool_discards_connection_after_in_use_error`。シンク側: `DsqlSinkTaskTest`、`DsqlIamTokenProviderTest`) |

### 非同期インデックス — `CREATE INDEX ASYNC`、データ投入後に構築される

| DSQL 特性 | テストするシナリオ | どう検証するか |
|---|---|---|
| インデックスは非同期に、ロード後に構築される | セカンダリインデックスを持つテーブル。データバッチが失敗するロード | インデックスは **すべての** データが着地した後にのみ作成される。いずれかのデータバッチが失敗した場合、インデックスは作成 **されない**(`test_indexes_created_after_all_data…`、`test_indexes_are_skipped_when_a_data_batch_fails`) |

### スキーマの違い — FK なし、PK 必須、非対応の型/オブジェクト

DSQL は外部キー、トリガー、ストアドプロシージャ、いくつかの型を省略し、プライマリキーを必須とします。

| DSQL 特性 | テストするシナリオ | どう検証するか |
|---|---|---|
| 外部キーなし | FK を多用したソース | FK を DDL から取り除き、`MANUAL` ノートとして保存する。Validation の **孤立レコードチェック** で、アプリ側の整合性が保たれていたことを確認する(`test_orphan_records_are_detected_and_fail_the_match`) |
| プライマリキー必須 | PK が **ない** テーブル。**複合** PK | PK なしは前段でブロックされ(`UNSUPPORTED`)、keyset(キーセット)エクスポートはそれを拒否する。複合 PK は明示的な辞書式選言のキーセット述語(`(k0 > :last_0) OR (k0 = :last_0 AND k1 > :last_1) OR …`)によってロードされる — これは意図的に行値タプル形式を **使わない**。行値タプル形式は MySQL 5.7 以降で PK インデックスを活用しにくいためである(`test_exporter.py`、シナリオドキュメント) |
| 非対応の型/オブジェクト | 精度が 38 を超える `DECIMAL`、255 を超えるカラム、トリガー/ルーチン | Evaluation で理由付きで `UNSUPPORTED` としてフラグが立てられる(`test_converter.py`、アセッサのテスト) |
| TINYINT(1) → boolean、範囲外 | `2` を保持する `TINYINT(1)` | **明示的でテーブル単位で致命的な** エラー。`2` を `true` に平坦化することを拒否する(静かな破損はしない) |
| 型の不均一性(MySQL → PG 方言) | 型の多様性が最大となるスキーマ | Full Load(Python)と CDC シンク(Java)は各型を **同一の** 保存形式にエンコードしなければならない。共有の **書き込みコントラクト** の同等性テストによって強制される(`test_dsql_write_contract.py`) |

### ギャップのない Full Load → CDC の引き継ぎ — 最も難しい正しさの性質

| DSQL 特性 | テストするシナリオ | どう検証するか |
|---|---|---|
| バルクロードした後、ギャップなし/重複なしでストリーミングを再開する | スナップショットをロードし、ライブの INSERT/UPDATE/DELETE ワークロードを実行し、ウォーターマーク(watermark)から CDC を開始し、収束させる | オフセットをウォーターマーク + `snapshot.mode=recovery` にシードする。PK をキーとした冪等な適用により、重複区間があっても重複は生じない(`test_cdc_pipeline.py`、`test_cdc_offset_seed.py`、`test_offset_seeder_lambda.py`) |
| CDC は DDL ではなくデータを複製する | CDC 中のソーススキーマ変更 | ターゲットの形状にもう一致しない行は失われずに **DLQ** へ送られる(`test_cdc_dlq.py`) |

### ライブソースは変わり続ける — ドリフトは正しく帰属させなければならない

| DSQL 特性 | テストするシナリオ | どう検証するか |
|---|---|---|
| マイグレーション中/後にソースが進む | ソースの GTID がウォーターマークを越えて進んだ状態で検証する | ドリフトはウォーターマークの GTID を介して検出・報告されるため、件数の差分はバグではなく **新しいソースアクティビティ** に帰属される(`test_drift_since_snapshot_is_reported`、`test_no_drift_when_gtid_unchanged`) |
| 件数は等しいがデータが異なる | 行数は一致するが値が異なる | **チェックサム** がそれを捕捉する。件数のみの「一致」は決して信頼されない(`test_deliberate_data_mismatch_with_equal_counts_is_not_a_match`) |

### 再開可能性 — 中断が作業を失わせたり重複させたりしてはならない

| DSQL 特性 | テストするシナリオ | どう検証するか |
|---|---|---|
| 冪等な再適用 | バッチを再実行する / 中断されたロードを再開する | `INSERT … ON CONFLICT` は決して重複を生じさせない。再開は未完了の PK 範囲のみを再実行し、中断されなかった状態へ収束する(`test_reapplying_batches_does_not_duplicate_rows`、`test_resume_skips_done_batches_and_converges_to_uninterrupted_state`) |

**スイートの実行:** `\.venv/bin/python -m pytest -q` と
`cd connectors/dsql-sink && mvn -q test`。

**ブラウザ UI E2E(任意):** `tests/e2e` 配下の Playwright スイートは、ヘッドレスブラウザで実際の Web UI を駆動します(アプリはサブプロセスとして起動されます)。これはオプトインであり、デフォルトの `pytest` 実行では除外されます。`playwright` の dev 依存関係と、その Chromium ビルド(初回のみ)が必要です。

```bash
uv sync                                         # installs the playwright dev dep
.venv/bin/python -m playwright install chromium # one-time browser download
.venv/bin/python -m pytest -m e2e               # run the browser E2E suite
```

デフォルトの「スモーク」E2E は外部インフラを必要としません(UI がレンダリングされ、ナビゲートし、Query Converter がクエリを変換することを検証します)。**connected**(接続)ティアは、ライブインフラに対して実際のフローを駆動します。Connect 画面でソース + ターゲットを検証し、続いて Query Converter → Test on target(`EXPLAIN ANALYZE` + DPU)、そして Amazon Bedrock に到達可能な場合は Tune with AI DBA → 再テスト → コードブロックごとのコピーボタンを検証します。

```bash
RUN_E2E_CONNECTED=1 .venv/bin/python -m pytest -m e2e   # connected tier too
```

依存関係の欠落でフレーク(不安定な失敗)しないよう、三重にゲートされています。`RUN_E2E_CONNECTED=1` でオプトインし、続いてソースの MySQL + ターゲットの Aurora DSQL が実際に到達可能(`.env` から)でなければクリーンにスキップし、さらに AI チューニングのケースは Bedrock に到達可能でなければ追加でスキップします。接続値は、アプリが Connect フォームに事前入力するのと同じ `.env` から取得されます。

## 8.2 シナリオをまとめて実行する — ライブ end-to-end 実行

上記のシナリオは、実際の AWS(RDS MySQL + Aurora DSQL + MSK)上で **まとめて** も検証しました。1 回の実行でできる限り多くの DSQL 特性を突くように設計された、専用のスキーマを用いています。

- parent → child / lob の外部キーチェーン(**FK なし** + **PK** + **孤立レコードチェック** のシナリオを強制)。
- 最大限の型の多様性 — あらゆる整数/unsigned のバリアント、精度が 38 を超えるものを含む `DECIMAL`、`FLOAT`/`DOUBLE`、`BIT`、collation、DATE/TIME ファミリー一式、`ENUM`/`SET`/`JSON`、そして LOB ファミリー一式(**型の不均一性** と **非対応型** のシナリオを強制)。
- **意図的に失敗させる行**: 約 1.5 MiB の LOB 値(**1 MiB の隔離/DLQ** シナリオを強制)、および分離したテーブル内の `TINYINT(1)` = `2`(**明示的でテーブル単位で致命的な** シナリオを強制)。

この実行では、**ギャップのない引き継ぎ** シナリオを実際に実行しました — Full Load → ライブワークロード → ウォーターマークからの CDC → 収束 → 権威ある PK ごとの突合。これこそが、実インフラでテストする価値のあるところです。初期の実行で、オフラインスイートでは捕捉できなかった本物の CDC データ損失バグ(ウォーターマークと CDC 開始の間で連続したブロックが失われ、DLQ にも残らない)が表面化しました。これは、静かに失敗していたオフセットシードと Debezium のスキーマ履歴のギャップにまで追跡され、**両方とも修正** されました。最終実行の目的は、その修正が有効であることを証明することでした。

### 検証結果

修正後、全体の実行を再度行ったところ、**クリーンなテーブルはすべて正確に突合し、説明のつかない不一致はゼロ** でした。

| テーブル | ソース行数 | ターゲット行数 | ターゲットで欠落 | ターゲットで余分 | 判定 |
|---|---|---|---|---|---|
| `typetest_parent` | 3,906 | 3,906 | 0 | 0 | **一致 ✓** |
| `typetest_child` | 3,785 | 3,785 | 0 | 0 | **一致 ✓** |
| `typetest_lob` | 2,309 | 2,309 | 0 | 0 | **一致 ✓** |

これが示していることを、項目ごとに説明します。

- **データ損失ゼロ、重複ゼロ。** Full Load **と** ライブ CDC の全区間にわたり、プライマリキーごとの突合は、すべてのテーブルで **欠落 0** および **余分 0** の行を確認しました。すべてのソース行がちょうど 1 回だけ到達し、すべてのソースの削除が適用されました。以前の連続したギャップ(1 ラウンドあたり 50〜70 行)は **0** にまで抑えられました。
- **意図的な失敗は、失われずに捕捉されました。** 約 1.5 MiB のサイズ超過 LOB 行は、正しく **隔離** され(設計上ターゲットには存在せず、プライマリキーで記録)、範囲外の `TINYINT(1)` 行は **明示的でテーブル単位で致命的な** 停止を引き起こしました — まさに安全な動作です。何も静かに破棄されず、静かに破損することもありませんでした。
- **件数だけでなく値が一致しました。** Validation のチェックサム/突合は、実際のデータを(不均一な型サーフェス全体にわたって)比較したため、ここでの「一致」は行が *数において等しい* だけでなく *等しい* ことを意味します。
- **デプロイ自体も成功しました。** Fargate の再デプロイは `UPDATE_COMPLETE` に到達し HTTP 200 を返したため、この結果は使い捨てのローカルセットアップではなく、出荷される構成によって生み出されました。

**採用者への結論:** すべての DSQL の違いを — 失敗するように設計された行も含めて — ストレスにかけるべく意図的に構築したスキーマにおいて、マイグレーションは **すべてのクリーンなテーブルで 100% 一致し、説明のつかない不整合はゼロ** という結果を生み出し、*失敗すべき* 行は失われずに捕捉・報告されました。そして、あなた自身が自分のマイグレーションの最後に **Validation** を実行するので、Cut over(カットオーバー)の前に、*あなたの* データについて同じ証拠 — 正確な件数、チェックサム、PK ごとの突合 — が得られます。結果を信頼で受け入れる必要はありません。あなた自身が再現するのです。
