# 8. テストと検証

_言語: [English](../en/08-testing-and-verification.md) | [한국어](../ko/08-testing-and-verification.md) | **日本語**_

> **前へ:** [7. パフォーマンスとチューニング](07-performance-and-tuning.md)

マイグレーションで最も不安な問いは、結局ひとつです: **「移行の途中で自分のデータが静かに失われたり、誤って保存されたりしないか? そして、移し終えたあとにソースと本当に同じだとどうやって確信できるのか?」**

この章はその両方に答えます。Aurora DSQL は MySQL とは異なるエンジンであるため、素朴にコピーするとデータが静かに壊れてしまうポイントがあります。**§8.1** は、*あなたの* データでそうした状況が起きたときにツールが代わりに何を処理してくれるか、そして *あなた自身が* それをどこで確認するかをまとめます。**§8.2** は、意図的に厄介なデータで実際の AWS 上で行った end-to-end 実行の結果を示します — そして、マイグレーションの最後の **Validation** ステップで、あなたも *あなたの* データについて同じ証拠を得られます。

> ここに書かれた動作は推測ではありません。各状況を AWS なしでも決定論的に再現する自動テストと、実インフラ上で *意図的に失敗させるデータ* まで含めて実行したライブ実行で確認されています (§8.2 に要約)。両方のソースエンジンをこの方法で end-to-end に検証しました — MySQL ソース (RDS MySQL + Aurora DSQL + MSK) と PostgreSQL ソース (RDS/Aurora PostgreSQL → MSK → Aurora DSQL) を、それぞれ Schema Conversion + Full Load + CDC + カットオーバーの全区間にわたって。

覚えておくべき原則はひとつです: **静かな破損よりも、騒がしい失敗のほうがましです。** ツールは、データをこっそり歪めたり捨てたりするよりも、目に見えて修正できるエラーで停止します。不完全なロードを成功として報告することはありません。

## 8.1 あなたのデータで起こり得ること — ツールが代わりに行うこと

以下は、「ソースでは何の問題もなかったものが、DSQL へ移すと危険になる」代表的な状況です。各行は、*あなたのデータにそれがあるとき* ツールが何をしてくれるか、そしてその結果をあなたがどこで確認するかを示します。PostgreSQL ソースは型のサーフェスが DSQL とほぼ同じなので (どちらも PostgreSQL-16 ワイヤ)、型の不整合に関する状況は当てはまりませんが、分散・サーバーレス・IAM 認証・OCC に関する状況はそのまま当てはまります。

| あなたのデータにこれがあると | 素朴に移すと危険な理由 (DSQL との違い) | ツールが代わりに行うこと | あなたが確認する場所 |
|---|---|---|---|
| **非常に大きなテーブル** (数億行) | DSQL はトランザクションあたり 3,000 行・10 MiB・5 分・DDL 1 つに制限 — 一度に押し込むと失敗するか切り捨てられる | PK 順に **ストリーミング** し、上限に収まるバッチに分けてロード — テーブルがどれほど大きくてもメモリとトランザクションは安全に保たれます。インデックスはデータのロードが終わってから構築します。Validation も上限付きのページ単位で件数とチェックサムを計算するため、大きなテーブルでも 5 分の上限に達しません | Full Load の進捗、Validation の **行数** |
| **1 MiB を超える大きな値** (MySQL の LOB/TEXT、または PostgreSQL の `text`/`bytea`/`json`) | DSQL は 1 つの値が 1 MiB を超えると保存できない | その **行だけを隔離** (quarantine) して PK と理由を記録し、テーブルの残りはロードを続けます。CDC 中も同じ値は DLQ に分離 — 1 つの値のためにテーブル全体が止まることはありません | Full Load の **エラーログ**、CDC の **DLQ**、Validation の不足分 |
| **型の変換があいまいな値** (MySQL ソースのみ — 例: `TINYINT(1)` に入った `2`、24 時間の範囲外の `TIME`) | `TINYINT(1)` → `boolean` で `2` を `true` に潰したり、範囲外の `TIME` を 1 日に切り詰めたりすると **静かな破損** | そうした値を勝手に平坦化せず、**そのテーブルのロードを騒がしく停止** して人が判断できるようにします (どの列・値か、どう直すかも案内)。PostgreSQL ソースにはネイティブの `boolean` 型があり、そのまま通過するため、この平坦化のリスクはありません | Full Load の **エラーログ** (テーブル単位の失敗) |
| **DSQL が対応しないオブジェクト・型** (MySQL: トリガー、プロシージャ、255 を超える列、FULLTEXT/SPATIAL インデックス — 作成せず `MANUAL` / PostgreSQL: 複合型、ドメイン、pgvector など) | そのまま移すと、ロードの途中で 1 つずつ失敗する | **Evaluation** の段階で事前にすべて分類 (AUTO / MANUAL / UNSUPPORTED) し、項目ごとに理由・推奨対応・作業量を提示 — ロード前に決められます。値を保てる代替型があれば (配列 → `jsonb`、range・ネットワーク型 → `text`、`money` → `numeric(23,4)`、enum → `CHECK` 付きの `text`)、アプリケーションが追従すべき型の変更を明示する **警告付きで** 変換し、代替型がない型は `UNSUPPORTED` | **Evaluation** レポート |
| **ソース固有の型が多いスキーマ** (MySQL: すべての整数/unsigned、`DECIMAL`、`BIT`、DATE/TIME 系、`ENUM`/`SET`/`JSON`、LOB など) | Full Load (バルク) と CDC (ストリーミング) が同じ値を **異なる形** で保存すると、後で不一致になる | 1 つの変換規約により、両方の経路が各値を **同じ形** で保存するようにします | Validation の **チェックサム** (値まで比較) |
| **書き込み競合が多いワークロード** | DSQL にはロックがなく、競合 (`40001`) はコミット時に (ステートメントの実行中にも) 通知される — 敗れたトランザクションは再実行が必要 | 競合したら失敗した試行をロールバックし、間隔を空けて **自動リトライ** します。リトライ予算を使い切っても解消しない場合は **失敗として記録** します (黙って捨てることはありません) | ジョブの状態 / エラーの要約 |
| **Aurora DSQL の一時的な障害** (`XX000` "server unavailable") | Aurora DSQL が一瞬リクエストを処理できない — コミット中だった場合、反映されたかどうかが不確実 | トランザクション全体を `40001` と同じ予算で **自動リトライ** します。再実行は主キー単位で冪等なので、コミットがすでに反映されていても同じ行が残ります (ただし二次 `UNIQUE` インデックスを持つテーブルではシンクに例外があります — [§4.4](04-cdc-and-dsql-constraints.md#44-sink-がデータパスで-dsql-の制約を処理する方法))。予算を超えた場合、Full Load のバッチは **失敗として記録** され (再試行可能)、CDC はバッチを再配信されます — このために行を隔離したり DLQ に送ったりすることはありません | ジョブの状態 / エラーの要約 |
| **パーティションをまたぐ一意制約の競合** (`23505`) | 主キーを変える `UPDATE` の insert が、別のパーティションにある古い行の delete より先にシンクに届く — 主キー以外の一意インデックスがその insert を拒否 | シンクは delete が適用されるまでそのパーティションを **保留** し、適用後にデッドレターなしで反映します。同じ行の後続の変更が置き換える変更は、代わりにスキップされます。5 分たっても解消しない変更は実際の理由とともにデッドレターになり、静かに失われることはありません ([§4.4](04-cdc-and-dsql-constraints.md#44-sink-がデータパスで-dsql-の制約を処理する方法)、[§6.2](06-limitations.md#62-移行プロセスの制限)) | CDC ステップの DLQ カード / シンクコネクタのログ |
| **長時間かかるロード・CDC ストリーム** | DSQL の接続は短命な IAM トークンと 60 分の接続上限 — 長引くとトークンや接続が期限切れになる | 死んだ接続や半分切れた接続を破棄し、**新しいトークンで再接続** して続行します — 利用者が手を加える必要はありません | 自動 (進捗が途切れず続く) |
| **バルクロードから CDC へ切り替わる地点** (ほぼ無停止の切り替え) | バルクロードから CDC へ移るときに間の区間を取りこぼすと **行の欠落**、重なると **重複** | バルクロードが確保した **ウォーターマーク** から CDC を開始します (MySQL: binlog の位置または GTID、PostgreSQL: スナップショット地点で作成した論理レプリケーションスロット)。すべての変更が PK 単位で **冪等に適用** されるため、重なっても重複は生じません | Validation の **突合** (欠落 0 / 余分 0) |
| **外部キーの多いスキーマ** | FK を有効にしたままロードや CDC を行うと、順序が前後した行 (親より先に届いた子) が FK 違反で失敗し、ソースがカスケードした削除は CDC に届かず孤立行が残る | FK を **保持** し (`NOT ENFORCED` や `PERIOD` で宣言された PostgreSQL 18 のキーは作成しません)、データのロード後 (CDC ではカットオーバー時) に `ADD CONSTRAINT … NOT VALID` で再作成し、すでにロード済みの行は Aurora DSQL が検証します。**孤立チェック** は、親のない子の行を前もって見つける早期警告であり、FK を外すことにした場合はアプリ側の整合性の安全網になります | Validation の **孤立チェック** |
| **移行中も変わり続けるライブソース** | 移行の間にソースが進むと行数に差が出るが、バグなのか正常なのか分かりにくい | スナップショット後の件数の差は、バグではなく *新しいソースアクティビティ* に帰属させます。**MySQL:** ウォーターマークの binlog/GTID 位置から **ドリフトを検出して報告** します。**PostgreSQL:** Validation はドリフトを再計算しないため (`drifted` = 判定不能)、代わりに CDC の収束を見守ります | Validation レポートの **drifted** フラグ |
| **途中で止めて再開する** | 素朴なローダーは最初からやり直すか、重複を作る | `INSERT … ON CONFLICT` により **再適用しても安全** で、再開時は **完了したテーブルはそのまま** にして、完了していないテーブルだけを最初からロードし直します (Retry unfinished tables) | 再開後の Full Load の進捗 |

> 表の「確認する場所」は、すべて **あなたが UI で直接見る画面** です。特に最後の **Validation** ステップは、正確な行数・チェックサム・全 PK の突合で判定を下すため、「たぶん大丈夫」ではなく **証拠にもとづいて** 切り替えを決められます (使い方の詳細は [5. Validation](05-validation.md))。

## 8.2 実際の証拠 — 意図的に厄介なデータで行った end-to-end 実行

上記の状況を **まとめて** 突くよう設計したスキーマで、**MySQL ソース** (RDS MySQL + Aurora DSQL + MSK) について、実際の AWS 上で全体のフローを実行しました:

- parent → child → lob とつながる **外部キーのチェーン** (FK の保持と適用、PK 必須、孤立チェックを強制)。
- **可能な限り多様な型** — あらゆる整数/unsigned、MySQL の最大 (65,30) までの `DECIMAL`、`FLOAT`/`DOUBLE`、`BIT`、collation、DATE/TIME 系一式、`ENUM`/`SET`/`JSON`、LOB 系一式 (型の不整合と非対応型を強制)。
- **意図的に失敗させるデータ** — 約 1.5 MiB の LOB 値 (1 MiB の隔離を強制) と、隔離したテーブル内の `TINYINT(1)` = `2` (騒がしいテーブル失敗を強制)。

> **PostgreSQL ソース。** 同じ end-to-end の経路を、PostgreSQL ソース (RDS/Aurora PostgreSQL → MSK → Aurora DSQL) についても実インフラ上で別途検証しました — Schema Conversion + Full Load + CDC + カットオーバー (外部キーの保持を含む)。PostgreSQL ソースは PG-16 → DSQL のほぼ恒等の通過であるため、上記の型の不整合と `TINYINT(1)` の平坦化の状況は当てはまりませんが、分散・サーバーレス・IAM 認証・OCC・ギャップのない Full Load → CDC の引き継ぎに関する状況はすべて当てはまります。

この実行では、最も難しい **ギャップのない引き継ぎ** を実際に行いました — Full Load → ライブワークロード → ウォーターマークからの CDC → 収束 → PK 単位の突合。実インフラで実行する価値はまさにここにあります: 初期の実行で、本物の CDC のデータ欠落 (ウォーターマークと CDC 開始の間の連続した区間が失われ、DLQ にも残らない問題) が表面化し、原因を突き止めて **修正しました**。以下の最終実行は、その修正が有効であることを実際のデータで証明した結果です。

### 検証結果

修正後に全体の実行をやり直した結果、**正常なテーブルはすべて正確に突合し、説明のつかない不一致はゼロ** でした:

| テーブル | ソース行数 | ターゲット行数 | ターゲットで欠落 | ターゲットで余分 | 判定 |
|---|---|---|---|---|---|
| `typetest_parent` | 3,906 | 3,906 | 0 | 0 | **一致** |
| `typetest_child` | 3,785 | 3,785 | 0 | 0 | **一致** |
| `typetest_lob` | 2,309 | 2,309 | 0 | 0 | **一致** |

この結果があなたにとって意味すること:

- **データ損失ゼロ、重複ゼロ。** Full Load とライブ CDC の全区間にわたり、PK 単位の突合がすべてのテーブルで **欠落 0 / 余分 0** を確認しました — すべてのソース行がちょうど 1 回だけ到達し、すべての削除が反映されました。修正前の初期実行で見られた連続した欠落 (CDC の 1 ラウンドあたり 50〜70 行) は **完全にゼロ** です。
- **失敗すべきデータは、失われずに捕捉されました。** 約 1.5 MiB の巨大な LOB 行は設計どおり **隔離** され (ターゲットには存在せず PK で記録)、範囲外の `TINYINT(1)` 行は **騒がしいテーブル失敗** を引き起こしました — まさに安全な動作です。何も静かに捨てられたり歪められたりしませんでした。
- **行数ではなく値が一致しました。** Validation のチェックサムと突合が実際の値 (多様な型の全体にわたって) を比較したため、ここでの「一致」は *件数だけが同じ* ではなく *値が同じ* ことを意味します。

### §8.1 が約束したことも、別途ライブで確認しました

上記の引き継ぎの実行に加えて、§8.1 の表で約束した **再開** と **CDC のエッジ動作** も、実インフラで別途負荷をかけて確認しました:

- **大規模な再開** — 約 180 万行のロードを途中 (約 1 万行の時点) で意図的に中断してから再開したところ、**未完了のテーブルだけ** が再実行されて全体が完了し、PK 単位の突合の結果、すべてのテーブルが **欠落 0 / 余分 0** に収束しました (107 万行のテーブルを含む)。中断でデータが失われたり重複したりすることはありません。
- **CDC のエッジ操作** — 主キーの変更、挿入-削除-再挿入の繰り返し、1 トランザクション内の挿入 + 削除、連続 UPDATE の集中、1 回のコミットにまとめた大量 INSERT まで、すべてソースと **完全に一致** するように反映されました。特に、CDC の最中にソースへ **列が追加された** (スキーマ変更の) 行は — CDC はデータのみを複製し DDL は伝播しないため — ターゲットに静かに誤って入る代わりに **DLQ に隔離** されました (§8.1 の約束どおり)。

**結論:** すべての DSQL の違いを — 失敗するよう仕込んだデータまで — 突くよう意図的に作ったスキーマで、マイグレーションは **正常なテーブルで 100% 一致、説明のつかない不一致ゼロ** を達成し、*失敗すべき* データは失われずに捕捉・報告されました。そして、マイグレーションの最後に **Validation をあなた自身が実行する** ので、切り替えの前に *あなたの* データについて同じ証拠 — 正確な行数、チェックサム、PK 単位の突合 — を得られます。結果を信じてほしいと頼むのではなく、自分で再現できるのです。

> 同じ PK 単位の突合はシェルからも利用できます: `scripts/cdc_consistency_check.py` (ターゲットで **欠落** / **余分** な正確な PK を列挙) と `scripts/compare_rows.py -t <schema.table> --watch N` (行数 / ライブ収束のチェック) — [`scripts/README.md`](../../../scripts/README.md) を参照。権威ある go/no-go は組み込みの **Validation** ステップです。
