# 10. まとめ

_言語: [English](../en/10-conclusion.md) | [한국어](../ko/10-conclusion.md) | **日本語**_

> **前へ:** [9. Query Converter と AI DBA](09-query-validation.md)

ここまでで全体の流れをひととおり見てきました。すなわち、接続、計画、**Evaluation（評価）**、**Schema Conversion（スキーマ変換）**、**Full Load**、必要に応じた **CDC**、**Validation（検証）**、そして **Cut over（カットオーバー）** です。この章では、どの経路を選ぶか、推奨するエンドツーエンドのフロー、カットオーバーのランブック、そして次に進むべき場所という形で、これらすべてを 1 つに結び付けます。

---

## 10.1 どの経路が必要か？

| あなたの状況 | 使うもの |
|---|---|
| 一度きりのマイグレーション。短いメンテナンス凍結が許容できる | **Full Load のみ**（ストリーミングインフラは不要、継続的なコストもなし）。 |
| 大規模／継続的。**ほぼ無停止**のカットオーバーが必要 | **Full Load + CDC**（ギャップのない引き継ぎにより、切り替えるまで DSQL をライブに保つ）。 |
| ターゲットはすでにロード済み。ストリーミングの接続／再開のみ | **CDC only**（すでにロード済みのターゲットにストリーミングを接続する — 例: 以前のウォーターマークから CDC を再開、または別途ロードされたターゲットへ流し込む — 新規の Full Load なし）。 |

CDC は実際に動く構成要素（MSK、MSK Connect、シンクコネクタ）を追加し、**デプロイされている間は継続的なコスト**が発生します。継続的なレプリケーションが本当に必要なときにのみ使ってください。そうでなければ、Full Load 単体のほうがシンプルで安価です。

---

## 10.2 推奨するエンドツーエンドのフロー

1. **Connect** — ソース（読み取り専用）とターゲット（DSQL、IAM トークン）に接続します。
2. **Evaluation** — 互換性レポートを読みます。すべての **UNSUPPORTED** 項目（PK、トリガー、ルーチン、空間型、精度 > 38、超過サイズの LOB）を解決し、各 **MANUAL** 項目（FK → アプリ側での整合性、パーティショニングなど）について判断します。*これをスキップしないでください* — 「ロードがなぜか失敗した」を「あのオブジェクトは変更が必要だと分かっていた」に変えてくれる工程です。CDC がそもそも可能かどうかも、ここで分かります: カスケードする外部キーはバイナリログに残らないため、CDC では複製できません。
3. **Schema Conversion** — ソースと変換後の DDL を見比べて、DSQL に適用します。
4. **Data Migration** — レポートで状況を把握したうえで、移行タイプ（**Full Load のみ**、**CDC only**、または **Full Load + CDC**）を選びます。前提条件チェックを実行すると、**Full Load** が行を一括コピーし、ウォーターマーク(watermark)をキャプチャします（エラーログを確認してください。隔離(quarantine)された行は想定内のもの（例: 超過サイズの値）か、対処が必要なものです）。CDC タイプの場合は、ロードを開始する**前に** Prerequisites サブステップからストリーミングインフラをデプロイしてください — 約 15〜20 分の作成がスナップショットと並行して進みます。その後、そのウォーターマークから **CDC** を開始し、ターゲットが収束していく様子を見守ります。
5. **Validation** — 行数 + チェックサムを実行します（カットオーバー前の照合も含む）。すべての差分が説明できる場合（ドリフト、意図的な隔離、まだ収束していない CDC）にのみ、判定が **MATCH** になります。
6. **Cut over** — Validation がクリーンな MATCH になったら、アプリケーションを DSQL に切り替えます。これはツールが代わりに実行しない唯一のステップであり、経路に合わせたランブック（下記 §10.3）に従ってください。

---

## 10.3 カットオーバー: アプリケーションを DSQL へ切り替える

「Cut over」は最後のワークフローステップであり、アプリケーションが MySQL の使用をやめて Aurora DSQL を使い始める瞬間です。これはツールが代わりに実行**しない**唯一のステップです — ツールはターゲットが正しいことを証明し、ギャップのないレプリケーションストリームを提供しますが、アプリケーションを *いつ*、どのように再ポイントするかは、あなただけが下せる運用上の判断です。Validation がクリーンな MATCH になると、UI の **Cut over** ステップに対応するランブックが表示されます。以下は、それと同じ各経路向けのガイダンスです。

### Full Load のみ（短いメンテナンス凍結）

短い書き込み凍結が許容できる場合に使います。ストリーミングがないため、凍結はロード + 検証にかかる時間ぶんだけ続きます。

1. **ソースの書き込みを凍結する** — アプリケーションをメンテナンス／読み取り専用モードにして、MySQL に新しい行が書き込まれないようにします。（ツールはソースを読み取り専用に保ちますが、書き込みを止めなければならないのは *あなたのアプリケーション* です。）
2. スナップショット以降にソースへの書き込みがあった場合は **Full Load を再実行** します — 冪等なので、まだ終わっていない作業だけを埋め、決して重複を作りません。
3. **Validation** — クリーンな **MATCH** を確認します（go/no-go のゲート）。
4. **アプリケーションを再ポイント** して DSQL エンドポイントへ向けます（PostgreSQL ワイヤ、IAM トークン認証 — パスワードなし）。重要な読み取り／書き込みパスをスモークテストします。
5. **凍結を解除する** — アプリケーションはこれで DSQL 上でライブになります。

### Full Load + CDC（ほぼ無停止）

アプリケーションが MySQL に書き込み続けている間も CDC が DSQL を収束させ続けるため、凍結は最後のドレイン + スモークテストのぶんだけに縮まります。

1. **CDC が追いつくまで待つ** — レプリケーションラグがゼロに近づく（または達する）まで。
2. **ソースの書き込みを凍結する**（短時間の読み取り専用／メンテナンスモード）。
3. **最後のドレインを待つ** — CDC が処理中(in-flight)の最後の変更まで適用し、ラグが再びゼロになるようにします。これで MySQL と DSQL は同じ行を保持します。
4. 最終の go/no-go のために **Validation を再実行** し、クリーンな MATCH のときにのみカットオーバーします。
5. **アプリケーションを再ポイント** して DSQL エンドポイントへ向け、スモークテストします。
6. **CDC パイプラインは最後に撤去する** — **Cut over** ステップで *Start over* → *Delete all CDC infrastructure* をクリックします。これはレプリケーションを終了し、MSK / MSK Connect / NAT のコストを止め、古いスタックをクリアします（将来、新しい Full Load や CDC を実行するには、デプロイする前にそれが削除されている必要があります）。

### ロールバックのアンカー

カットオーバーする *前に* ロールバックのルールを決めておきましょう。DSQL について正式に承認（サインオフ）するまでは、MySQL ソースを**削除せず、凍結（読み取り専用）**の状態に保ちます。再ポイントする前であれば、ロールバックは簡単です — ソースは手つかずで、依然として権威あるデータ（authoritative）だからです。アプリケーションが DSQL に書き込みを始めると、それらの新しい行は **DSQL にのみ** 存在するため（このツールは MySQL → DSQL のレプリケーションであり、**逆方向ではありません**）、その時点でロールバックするには、まずそれらの行を自分で照合し直す必要があります。

## 10.4 ツールが従う原則（だから判定を信頼できる）

- **ソースは常に読み取り専用。** ツールが MySQL ソースに書き込むことは決してありません。
- **静かにするより声高に。** ツールはデータを黙って破損させることを拒みます — 表現できない値があればテーブルを目に見える形で停止させ、不完全なロードが成功として報告されることは決してありません。
- **冪等で再開可能。** Full Load の再実行や CDC の再適用が重複を作ることはなく、中断されたロードはまだ終わっていない作業だけを再開します。
- **健全な検証。** エビデンス（行数、チェックサム、PK セット）が裏付けるときにのみ「一致」と報告します。
- **認証情報はメモリ内にとどまる。** ディスク、ログ、レポート、ジョブ状態には決して書き込まれません。
- **AI はあくまで助言。** 任意の Bedrock による提案はレビュー専用であり、データパスには一切触れません。
