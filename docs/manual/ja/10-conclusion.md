# 10. まとめ

_言語: [English](../en/10-conclusion.md) | [한국어](../ko/10-conclusion.md) | **日本語**_

> **前へ:** [9. Query Converter と AI DBA](09-query-validation.md)

ここまでで全体の流れをひととおり見てきました。すなわち、接続、計画、**Evaluation（評価）**、**Schema Conversion（スキーマ変換）**、**Full Load**、必要に応じた **CDC**、**Validation（検証）**、そして **Cut over（カットオーバー）** です。この章では、どの経路を選ぶか、推奨するエンドツーエンドのフロー、カットオーバーのランブック、そして次に進むべき場所という形で、これらすべてを 1 つに結び付けます。

## 10.1 どの経路が必要か？

| あなたの状況 | 使うもの |
|---|---|
| 一度きりのマイグレーション。短いメンテナンス凍結が許容できる | **Full Load のみ**（ストリーミングインフラは不要、継続的なコストもなし）。 |
| 大規模／継続的。**ほぼ無停止**のカットオーバーが必要 | **Full Load + CDC**（ギャップのない引き継ぎにより、切り替えるまで DSQL をライブに保つ）。 |
| ターゲットはすでにロード済み。ストリーミングの接続／再開のみ | **CDC only**（すでにロード済みのターゲットにストリーミングを接続する — 例: 以前のウォーターマークから CDC を再開、または別途ロードされたターゲットへ流し込む — 新規の Full Load なし）。 |

**PostgreSQL** では、ギャップのない引き継ぎをロードの*前*に選んでおく必要があります。WAL を保持するレプリケーションスロットは過去の位置に作成できないため、**Full Load + CDC** を選べばツールがスナップショット時点でスロットを作成します。**Full Load のみ**を実行した後はその選択肢が失われ、後から CDC を開始すると対象テーブルをすべて再スナップショットします — 依然としてギャップはありませんが、ソースをもう一度読み込み、すべての行が MSK を通過します (以前にコネクタを開始した CDC スタックでは、代わりに Start CDC がそのスタック自身のスロットから続けます。ただし、そのスタックの source connector がストリーミングしていなければ、Debezium が先に選択したすべてのテーブルをスナップショットします: sink が適用していなかった変更を CDC トピックがまだ保持している間だけギャップがありません)。MySQL はコンシューマーがいなくてもバイナリログが履歴を保持するため、一度もストリーミングしたことのない CDC スタックでは、後から CDC を開始してもウォーターマークから再読み込みなしで開始します。ストリーミングしたことのあるスタックでは Start CDC がそのより新しい開始位置を拒否するため、マイグレーションの種類を CDC only に切り替えてから、その CDC ステップで Delete CDC infrastructure して再デプロイし、Start CDC してください (Full load only には CDC ステップがありません。[第 3 章 §3.5](03-full-load.md#35-ウォーターマーク--cdc-への橋渡し))。どちらの場合も CDC はウォーターマークから開始してその後の変更しか運ばないため、その Full load only の実行が以前のロードがターゲットに残した行に append した場合は、先に **Drop & reload** で Re-run Full Load してください。

CDC は実際に動く構成要素（MSK、MSK Connect、シンクコネクタ）を追加し、**デプロイされている間は継続的なコスト**が発生します。継続的なレプリケーションが本当に必要なときにのみ使ってください。そうでなければ、Full Load 単体のほうがシンプルで安価です。

## 10.2 推奨するエンドツーエンドのフロー

1. **Connect** — ソース（読み取り専用）とターゲット（DSQL、IAM トークン）に接続します。
2. **Evaluation** — 互換性レポートを読みます。すべての **UNSUPPORTED** 項目（PK なし、トリガー、ルーチン、DSQL に相当のない PostgreSQL 型）を解決し、各 **MANUAL** 項目（CDC が複製できないカスケード FK、空間型、FULLTEXT/SPATIAL インデックス、`ENUM`/`SET`、まずサイズを確認すべき超過サイズの LOB/JSON 列など）について判断します。*これをスキップしないでください* — 「ロードがなぜか失敗した」を「あのオブジェクトは変更が必要だと分かっていた」に変えてくれる工程です。CDC がそもそも可能かどうかも、ここで分かります: ソースのカスケード（`ON DELETE/UPDATE CASCADE`）はバイナリログに残らないため、CDC では複製できません — それが残す孤立した子行があると、カットオーバー時にその外部キーに対する Aurora DSQL の検証が失敗し、修正するまでカットオーバーを止めます（Validation の孤立チェックも報告します）。
3. **Schema Conversion** — ソースと変換後の DDL を見比べて、DSQL に適用します。
4. **Data Migration** — レポートで状況を把握したうえで、移行タイプ（**Full Load のみ**、**CDC only**、または **Full Load + CDC**）を選びます。前提条件チェックを実行すると、**Full Load** が行を一括コピーし、ウォーターマーク(watermark)をキャプチャします（エラーログを確認してください。隔離(quarantine)された行は想定内のもの（例: 超過サイズの値）か、対処が必要なものです）。CDC タイプの場合は、ロードを開始する**前に** Prerequisites サブステップからストリーミングインフラをデプロイしてください — 約 15〜20 分の作成がスナップショットと並行して進みます。その後、そのウォーターマークから **CDC** を開始し、ターゲットが収束していく様子を見守ります。
5. **Validation** — 行数 + チェックサムを実行します（カットオーバー前の照合も含む）。すべての差分が説明できる場合（ドリフト、意図的な隔離、まだ収束していない CDC）にのみ、判定が **MATCH** になります。CDC 移行では、デッドレターされた CDC 変更があるテーブルも自動的に CHECKSUM で比較されます。
6. **Cut over** — Validation がクリーンな MATCH になったら（CDC では [§5.5](05-validation.md#55-cdc-のデッドレターとカットオーバー) のデッドレター確認と [§5.7](05-validation.md#57-ソーススキーマの変更とカットオーバー) のソーススキーマの再確認も解消したら）、アプリケーションを DSQL に切り替えます。これはツールが代わりに実行しない唯一のステップであり、経路に合わせたランブック（下記 §10.3）に従ってください。

## 10.3 カットオーバー: アプリケーションを DSQL へ切り替える

「Cut over」は最後のワークフローステップであり、アプリケーションが MySQL の使用をやめて Aurora DSQL を使い始める瞬間です。これはツールが代わりに実行**しない**唯一のステップです — ツールはターゲットが正しいことを証明し、ギャップのないレプリケーションストリームを提供しますが、アプリケーションを *いつ*、どのように再ポイントするかは、あなただけが下せる運用上の判断です。Validation がクリーンな MATCH になると（CDC では [§5.5](05-validation.md#55-cdc-のデッドレターとカットオーバー) のデッドレター確認と [§5.7](05-validation.md#57-ソーススキーマの変更とカットオーバー) のソーススキーマの再確認も解消すると）、UI の **Cut over** ステップに対応するランブックが表示されます。以下は、それと同じ各経路向けのガイダンスです。

### Full Load のみ（短いメンテナンス凍結）

短い書き込み凍結が許容できる場合に使います。ストリーミングがないため、凍結はロード + 検証にかかる時間ぶんだけ続きます。

1. **ソースの書き込みを凍結する** — アプリケーションをメンテナンス／読み取り専用モードにして、MySQL に新しい行が書き込まれないようにします。（ツールはソースを読み取り専用に保ちますが、書き込みを止めなければならないのは *あなたのアプリケーション* です。）
2. スナップショット以降にソースへの書き込みがあった場合は **「Drop & reload」で Full Load を再実行** します (既定の *Append* は欠けている行を追加するだけで、その後の UPDATE や DELETE は適用しません)。その後 CHECKSUM で検証します。再ロードするとテーブルの外部キーも一緒に消えるため、Data Migration ステップ (または Cut over) で **Apply foreign keys** をもう一度クリックしてください — 各キーはすぐに追加されてすべての新規書き込みを強制し、ロード済みの行は Aurora DSQL がバックグラウンドで検証します。
3. **Validation** — クリーンな **MATCH** を確認します（go/no-go のゲート）。PostgreSQL ソースでは、どの列にも所有されていないシーケンス (Evaluation の `PG_STANDALONE_SEQUENCE`) を、ここで自分でソースの最終値の先へ進めます: Cut over ステップが *Before you repoint: move standalone sequences past the source* の下にそれぞれを、ソースで実行する読み取り (`SELECT last_value, is_called FROM <seq>`) と、その読み取りが返した 2 つの値で Aurora DSQL で実行する文 (`SELECT setval('<seq>', <last_value>, <is_called>)`) とともに一覧します。
4. **アプリケーションを再ポイント** して DSQL エンドポイントへ向けます（PostgreSQL ワイヤ、IAM トークン認証 — パスワードなし）。重要な読み取り／書き込みパスをスモークテストします。
5. **凍結を解除する** — アプリケーションはこれで DSQL 上でライブになります。

### Full Load + CDC（ほぼ無停止）

アプリケーションが MySQL に書き込み続けている間も CDC が DSQL を収束させ続けるため、凍結は最後のドレイン + スモークテストのぶんだけに縮まります。

1. **CDC が追いつくまで待つ** — レプリケーションラグがゼロに近づく（または達する）まで。
2. **ソースの書き込みを凍結する**（短時間の読み取り専用／メンテナンスモード）。
3. **最後のドレインを待つ** — CDC が処理中(in-flight)の最後の変更まで適用してラグが再びゼロになり、ソースの最後の書き込みから少なくとも 5 分経つようにします: 一意インデックスを待つ変更は、適用されるかデッドレターになるまでそれだけ保留され、そのラグが表れるまでに 1〜2 分かかることがあります。これで MySQL と DSQL は同じ行を保持します。
4. 最終の go/no-go のために **Validation を再実行** し、クリーンな MATCH のときにのみカットオーバーします。最終検証は、移行がロードしたすべての identity / `AUTO_INCREMENT` キーの**シーケンスを CDC が届けた行の先まで前進**させます (実行から外したテーブル、つまり **Objects to validate** でチップをオフにしたテーブルも含みます)。Cut over の *Sync identity sequences* 操作も同じです。これにより、カットオーバー後のアプリの最初の insert が移行済み id と衝突(`23505`)することを防ぎます。この操作が届かなかった移行対象の identity テーブルは赤い通知に名前が示され (もう一度実行してください)、完了とは表示されません。どの列にも所有されていない PostgreSQL のシーケンスはこれに含まれません: Evaluation がそれぞれを一覧し(`PG_STANDALONE_SEQUENCE`)、Cut over ステップが *Before you repoint: move standalone sequences past the source* の下にそれぞれを、ソースで実行する読み取り (`SELECT last_value, is_called FROM <seq>`) と、その読み取りが返した 2 つの値で Aurora DSQL で実行する文 (`SELECT setval('<seq>', <last_value>, <is_called>)`) とともに示すので、アプリケーションを切り替える前に実行してください。アクティビティログの承認行には、あなたに任されたシーケンスの数が記録されます。デッドレターされた CDC 変更があるテーブルは自動的に CHECKSUM で比較され、Cut over は開く前にデッドレターキューを読み直します（[§5.5](05-validation.md#55-cdc-のデッドレターとカットオーバー) 参照）。リキーされたテーブルがある PostgreSQL ソースでは、Cut over は開く前にそれらの REPLICA IDENTITY も読み直します（[§5.6](05-validation.md#56-リキーされた-postgresql-テーブルとカットオーバー) 参照）。Cut over は開く前に、ソース上のキャプチャ対象テーブルの定義も読み直します（[§5.7](05-validation.md#57-ソーススキーマの変更とカットオーバー) 参照）。
5. **外部キーを適用してから、アプリケーションを再ポイント** して DSQL エンドポイントへ向け、スモークテストします。Cut over でドレイン確認のチェックボックスを選び、**Apply foreign keys** をクリックします: 各キーはすぐに(`NOT VALID`、数秒)追加され、その時点からすべての新規書き込みを強制します。ロード済みの行はその後 Aurora DSQL がバックグラウンドで検証し、このステップは検証されたキーの数と、失敗したキーの詳細・キーを破る行・**Validate again** を示します。**I've cut over** はその検査ではなく、キーが配置されるまでだけ待ちます — ただし MySQL ソースで `ON DELETE` / `ON UPDATE` アクションのあるキーや、MySQL がより緩く一致させるテキスト列のキー(大文字小文字を区別しない照合順序、または `VARCHAR` の `utf8mb4_bin` のような PAD SPACE の照合順序)のように CDC が孤立行を残しうるキーは、検証されるまで、またはその検査なしでカットオーバーすると選ぶまで Finish が待ちます。Finish は **Apply foreign keys** が追加するキーだけを待ちます: 移行に含まれないテーブルが Aurora DSQL にない場合、そのテーブルのキーは追加するものがないため待ちません。Finish は最新の検証の後に読んだキーの状態だけを信頼し、CDC の開始・再開始は最後の適用結果を消去し(ストリームにはキーがあってはならない)、Start CDC の **Remove foreign keys** もその後 CDC を開始しなくても同様に消去するため、最終ドレインの後にもう一度適用してください。配置されていないキーと検証されていないキーは別々の二つの保留で、それぞれに別の選択があります: 強制される外部キーなしでカットオーバーするという選択は、配置済みのキーの検証の検査まで免除しません(逆も同様です)。
6. **CDC パイプラインは最後に撤去する** — **Start over(右上)** → *Delete all CDC infrastructure* をクリックします。これはレプリケーションを終了し、MSK / MSK Connect / NAT のコストを止め、古いスタックをクリアします（将来、新しい Full Load や CDC を実行するには、デプロイする前にそれが削除されている必要があります）。

### ロールバックのアンカー

カットオーバーする *前に* ロールバックのルールを決めておきましょう。DSQL について正式に承認（サインオフ）するまでは、MySQL ソースを**削除せず、凍結（読み取り専用）**の状態に保ちます。再ポイントする前であれば、ロールバックは簡単です — ソースは手つかずで、依然として権威あるデータ（authoritative）だからです。アプリケーションが DSQL に書き込みを始めると、それらの新しい行は **DSQL にのみ** 存在するため（このツールは MySQL → DSQL のレプリケーションであり、**逆方向ではありません**）、その時点でロールバックするには、まずそれらの行を自分で照合し直す必要があります。

## 10.4 ツールが従う原則（だから判定を信頼できる）

- **ソースは常に読み取り専用。** ツールが MySQL ソースに書き込むことは決してありません。
- **静かにするより声高に。** ツールはデータを黙って破損させることを拒みます — 表現できない値があればテーブルを目に見える形で停止させ、不完全なロードが成功として報告されることは決してありません。
- **冪等で再開可能。** Full Load のバッチの再実行や CDC の再適用が重複を作ることはなく、中断されたロードはまだ終わっていない作業だけを再開します (**Retry unfinished tables**)。新しいコピーは **Drop & reload** で作ります: 再実行の既定の *Append* は欠けている行を追加するだけです。
- **健全な検証。** エビデンス（行数、チェックサム、PK セット）が裏付けるときにのみ「一致」と報告します。
- **認証情報はメモリ内にとどまる。** ディスク、ログ、レポート、ジョブ状態には決して書き込まれません。
- **AI はあくまで助言。** 任意の Bedrock による提案はレビュー専用であり、データパスには一切触れません。

Aurora MySQL から Aurora DSQL への移行は、**ヘテロジニアス(heterogeneous)** な移行です — バージョンアップグレードではなく、ルールの異なる別のエンジンへ移すことです。このツールの役割は、その違いを最初に明確に浮き彫りにし（Evaluation）、可能なところでは決定論的に処理し（Schema Conversion、Full Load、CDC）、結果を証明する（Validation）ことです — そうして、あなたのカットオーバーが漠然とした信念に頼った飛躍ではなく、エビデンスに裏打ちされた判断になるようにするためです。
