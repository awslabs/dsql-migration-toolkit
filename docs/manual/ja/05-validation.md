# 5. Validation の仕組み

_言語: [English](../en/05-validation.md) | [한국어](../ko/05-validation.md) | **日本語**_

> **前へ:** [4. CDC と DSQL の制約](04-cdc-and-dsql-constraints.md)
>
> **除外した列**は値を比較せず、NULL であることを証明します。[13.9 Validation と Cut over](13-excluding-tables-and-columns.md#139-validation-と-cut-over)を参照してください。

**Validation** は、ターゲットがソースと一致することを証明する手順であり、安全なカットオーバーの根拠となります。**正確な** `COUNT(*)` とチェックサムを実行する唯一の手順であり（Full Load はスキャンを伴わない推定を意図的に使用していました）、近似ではなく信頼できる判定を提供します。

Full Load の後（そして CDC を使用している場合はストリームが追いついた後）に、**Validation** 手順から実行します。移行された DSQL ターゲットを **ウォーターマーク時点の** ソースと比較し、**MySQL** ソースの場合はライブソースがその後に変化していればドリフトを報告します（**PostgreSQL** ソースはドリフト判定を受けません。5.2 を参照）。クリーンな **MATCH**（またはすべての差異が説明済み）を報告し、CDC 移行では 5.5〜5.7 の確認も解消すると、**Cut over** 手順が表示されます。

## 5.1 比較する対象

Validation は **テーブル単位** で動作し、選択できる厳密さのレベルが段階的に高くなります。

| モード | 検査内容 | コスト |
|---|---|---|
| **行数**（デフォルト） | テーブルごとのソース対ターゲットの正確な `COUNT(*)`。 | 安価。 |
| **チェックサム** | **順序に依存しない** テーブルごとのチェックサム（両エンジンで同一の方法で計算）を追加 — 行数だけでは見逃す値の差異を捕捉します。 | より重い（すべての行を読み取る）。 |
| **Reconcile（全 PK セット）** | 両側の **すべての主キー** を PK 順にストリーミングしてソートマージし、**ターゲットに欠落している** PK と **ターゲットに余分にある** PK（CDC がまだ適用していない削除）を正確に報告します。 | 最も重い。カットオーバー前の「不一致レコードなし」の証明。 |

- あるオプションを使うと、**すでに行数が一致しないテーブルにのみ** 高コストなチェックサム / reconcile を計算するため、行数が一致したテーブルは「詳細未検査」として報告されます（誤った一致としてではありません）。
- **CDC 移行:** ストリームが変更をデッドレターしたテーブルは、どのモードを選んでも **CHECKSUM** でも比較されます — 行数では取りこぼした UPDATE を検出できないためです（5.5 参照）。
- **Reconcile は単一カラムの整数 PK に適用されます。** これらは両エンジンで明確に定義された順序を持つためです。複合 PK や非整数 PK は reconcile パスから除外されます（行数 / チェックサムは引き続き適用されます）。Aurora DSQL で boolean になる `TINYINT(1)` キーも reconcile され、その `false` / `true` は MySQL の 0 / 1 として比較されます。
- **チェックサムは MySQL ソースの浮動小数点および JSON 列を含めません**（`FLOAT`/`DOUBLE`、`JSON`: 両エンジンで同一にレンダリングされるテキスト形式を持たないため）。レポートには **「value 未比較（not value-compared）」** と表示されます。**PostgreSQL** ソースでは、含めないのはプレーンな `json` のみです。したがって **非キー（non-key）** 列に限定された値の差異は、どのモードでも検出されません（行数は変わらず、reconcile は PK の *存在* のみを比較します）。キー列とその他すべての型は、テーブルがどれだけ幅広くても完全に比較されます。
- **大きなテーブルは、複合キーも含めて、行数とチェックサムを上限付きのページ単位で計算します。** 信頼できないページは、PostgreSQL ソースではテーブルを一致ではなくエラーにし、MySQL ソースではチェックサムを代わりに 1 文で読みます（理由はログに残ります）。降順・プレフィックスの部分を持つキーや、単精度 `FLOAT` の部分を持つキーも同様です。こうした 1 文は実行中に進捗を報告しないため、Stop はその文が終わったときに効き、非常に大きいテーブルではジョブの 15 分の無進捗上限が実行を終わらせることがあります。Aurora DSQL 上で主キーのないテーブル（本ツールは移行しません）は 1 文で数えられ、非常に大きいと Aurora DSQL の 300 秒トランザクション上限で止まり、一致ではなくエラーとして表示されます。

## 5.2 ライブソースのドリフト

実際のソースは移行中も変化し続けるため、「行数は一致しているか?」には基準点が必要です。Validation は **ウォーターマーク** を使用します。

- **MySQL ソースの場合**、**現在の** ソース位置をウォーターマークの位置と比較します。ウォーターマークとライブソースの **両方** が GTID を公開している場合は GTID で、そうでなければ binlog の **file:position** で比較します。ソースが進んでいる場合、レポートは **`drifted = true`** とマークします。
- **PostgreSQL ソースの場合**、Validation は現在ドリフトを **再計算しません**。`drifted` は **「could not be determined」** として報告されます。CDC 中にターゲットが **収束** していく様子を観察し（`scripts/compare_rows.py --watch N` が *N* 秒ごとに再チェックします）、追いついたら完全な Validation を実行してください。
- いずれの場合も、レポートはウォーターマークの **スナップショットタイムスタンプ** を「基準時点」として保持します。これにより、行数の差異は移行のバグではなく *スナップショット以降の新しいソースアクティビティ* が原因であると正しく帰属されます。

## 5.3 判定モデル

判定は **構造的に健全** です — 証拠が裏付ける場合にのみ一致を報告します。

- **テーブル** が `matched` になるのは、行数が等しく、**かつ**（チェックサムモードでは）チェックサムが等しく、**かつ**（reconcile した場合は）PK セットが整合している場合に限られます。
- **レポート全体** が `is_match` になるのは、**すべての** テーブルが一致し、孤立行が存在しない場合に限られます。
- 1 つのテーブルの比較の失敗は、そのテーブルのエラーエントリに **隔離** されます — 実行を中断させたり、残りを暗黙のうちに通過させたりすることはありません。

Aurora DSQL は外部キーを **強制** し、ツールはロード後（CDC マイグレーションではカットオーバー時）にそれらを再作成します: 各キーをすぐに `NOT VALID` で追加し、その後 Aurora DSQL がロード済みの行を検証します — 孤立行があるとこの検証は失敗します。オプションの **孤立チェック** は、（NULL でない、`MATCH FULL` のキーならすべてが NULL ではない）外部キーに対応する親が存在しないターゲットの子行を数えます。これはそのステップの **早期警告** です — 書き込みを凍結する前のリハーサルで実行してください — さらに、代わりに外部キーを **取り除く** ことを選んだ場合には、参照整合性のセーフティネットになります。親テーブルが Aurora DSQL 上にない外部キーは数えられないため、レポートに **未チェック（not checked）** として示され、判定は変わりません。

孤立チェックが失敗すると（例: 外部キー列の型が親キーと合わなくなったとき）、そのテーブルだけを不一致にします。そのテーブルの行数と判定はそのまま表示されるため実際の不一致も見え、**Orphan records** にその外部キーとエラーが示されます。原因を直してそのテーブルを再確認するか、**Check for orphan records** をオフにして再実行してください。比較が一致していれば、データの不一致とは呼びません: そのテーブルの Result は *orphan check could not run* となり、**Cut-over readiness** はそのテーブルを専用の **Orphan check ran** 行に示し、**How to recover** は再ロードの手順を示さず（埋め戻すものがありません）**Orphan records** を指します。

不一致となったテーブルについては、オプションの範囲を限定した **行差分サンプル** が、差異のある PK（およびチェックサムトークン）をいくつか列挙します — **行の値は決して表示しません** — そのため、データを露出させることなく調査できます。レポートは **エクスポート可能** なので、カットオーバーの判断に添付できます。

## 5.4 典型的な結果の読み方

| テーブル | source | target | 判定 |
|---|---|---|---|
| `orders` | 3906 | 3906 | **MATCH** |
| `order_items` | 3785 | 3785 | **MATCH** |
| `documents` | 2309 | 2306 | **investigate** |

- すべてのテーブルが **MATCH**（かつ孤立行なし）→ カットオーバーは安全です（CDC 移行では、5.5〜5.7 の確認が解消してから）。
- 小さな **ターゲット不足** は、通常 (a) **ドリフト** — ウォーターマーク以降にソースが進んだ（ドリフトフラグを確認）か、(b) **意図的** — 隔離された行（例: DSQL の 1 MiB 制限を超える値）のいずれかです。不足分が移行が恒久的に破棄した行数と **正確に** 一致する場合、テーブルが *「Fully explained: N rows were permanently dropped during the migration … this deficit is expected, not new data loss」* と伝えます。不足分が破棄件数より **多い** 場合は *「Partly explained: … but N more are missing and are NOT accounted for」* と表示され、調査すべきはその N 行です。テーブルは依然として **MISMATCH** として報告されます — これは意図的です: それらの行は実際に存在しないため、この説明はギャップを **解明** するものであって免除するものではありません。ソース値を修正して当該テーブルをリロードしてギャップを閉じるか、カットオーバー前に既知のギャップとして受け入れてください。（アプリを再起動するとテーブルごとの破棄件数は失われ、不足分は未解明として報告されます。その場合は **Full Load エラーログ** と照合してください。）
- CDC 中の **ターゲット超過**（ターゲットに余分にある PK）は、通常、ストリームがまだ適用していないソースの **削除** を意味します — 収束後に再確認してください。

> **経験則:** 差異がドリフト、意図的な隔離（サイズ超過の値）、またはまだ収束していない CDC のいずれかで説明できるだけであれば、その移行は健全です。行数が一致し追いついたテーブルにおける、**説明のつかない** 欠落 / 余分な PK こそが、Validation が浮き彫りにするために存在するものです。

不一致が **説明のつかない** ものである場合、レポートは順序のあるクリック手順とともに **How to recover** を表示します。

| マイグレーション | カードの手順 |
|---|---|
| **Full load + CDC** または **CDC only** で、CDC スタックが **ストリーミングしたことがある**（Start の後に停止した、コネクタがそのまま残っている、または CloudFormation が Start をロールバックした）か、CDC の状態をまだ読み取っていない（アプリの再起動後、Data Migration ステップが読み取るまで） | CDC が動いていれば Stop CDC → **Delete CDC infrastructure** して再デプロイ → **Drop & reload** で **Re-run Full Load**（一部が失敗していれば **Re-run all tables**）→ **Start CDC**（新しい Full Load の開始位置から始まります）→ **Re-run validation**。CDC only では、再デプロイの後の手順でマイグレーションの種類を、Full Load ステップのある Full load + CDC に切り替えます。新しいトピックが先に来る理由: そのようなスタックでは、インフラを再デプロイするまで Full Load ステップが新しい開始位置を拒否し（[第 3 章 §3.5](03-full-load.md#35-ウォーターマーク--cdc-への橋渡し)）、新しい開始位置を取った Full Load の後の再開には **ギャップがない保証がありません**。 |
| CDC スタックがストリーミングしたことがない | 上記の手順から Stop CDC と再デプロイを除いたものです（CDC only では、先にマイグレーションの種類を Full load + CDC に切り替えます）。ここでも再実行は **Drop & reload** です: CDC は新しい開始位置から始まり、append はそれより古い行をそのまま残すためです。 |
| **Full load only** | *Re-run Full Load to backfill the gap*、次に **Re-run validation**。CDC の手順はありません。 |
| 1 つのテーブル | 特定のテーブルの **Drop & reload**（CDC を停止して）は **元の** 開始位置を維持するため、5.5〜5.7 のテーブルごとの対処手順はまったく制限されません。 |
| *The target holds rows the source does not — a delete never landed* | 再実行は行を埋めるだけなので、カードはそのテーブルごとの再ロード（CDC を停止して **Reload specific tables**、**Drop & reload** を選択。CDC only では、マイグレーションの種類を Full load + CDC に切り替えてから）を示します。CDC only でこのセッションに Full Load の記録がない場合は再ロードするテーブルがないため、代わりに新しい Full Load の開始位置を示します（1 行目の手順、Stop CDC から **Start CDC** まで）。 |
| 孤立チェックを実行できなかったことだけで一致しないテーブル | これらの手順は 1 つも出ません: 比較は一致しているので、カードは埋め戻すものがないと述べ、**Orphan records** を指します（5.3）。 |

Cut over にはレポートが Full Load 以降に選択したすべてのテーブルを対象にしていることも必要です: そのようなテーブルの行がレポートにないと、それをロードして（Full load + CDC と CDC only では、その開始点の下で）Validation を再実行するまで（または **Objects to validate** でそのチップをオフにするまで）Cut over は保留されます。Full load + CDC で Full Load の後（CDC を開始する前）にチェックを外したテーブルは検証されません。最後のレポートがその変更より前のものなら、Validation を再実行してください。カットオーバーのシーケンス（CDC ドレイン対 Full Load フリーズ）とロールバックのアンカーについては、[結論](10-conclusion.md) の推奨されるエンドツーエンドのフローを参照してください。

> **コマンドラインで検証（任意）。** 2 つの読み取り専用 CLI スクリプトでシェルからスポットチェックできます（終了コードでスクリプトをゲート可能）: `scripts/compare_rows.py`（テーブルごとの行数 / PK 範囲チェック。CDC 中にターゲットの収束を見る `--watch N` あり）と `scripts/cdc_consistency_check.py`（完全な主キー突合 — ターゲットに **欠落** または **余分** な正確な PK を特定する、カットオーバー前のゼロデータロス証明）。詳細は [`scripts/README.md`](../../../scripts/README.md) を参照。権威ある go/no-go は引き続きこの組み込みの Validation です（チェックサムとドリフトの帰属も実行します）。

## 5.5 CDC のデッドレターとカットオーバー

**デッドレター** とは、Aurora DSQL が拒否したため（例: ソースのスキーマ変更後）CDC ストリームが脇に置いた変更です。**再試行されることはありません。** 同じ行の後続の全行 UPDATE が来れば修復されますが、二度と触れられない行は欠落または古い値のまま残り、失われた DELETE はターゲットに余分な行を残します。取りこぼした UPDATE は行数を変えないため、デフォルトの行数モードでは検出できません。

そのため CDC 移行（**Full Load + CDC** または **CDC only**）では、ツールがデッドレターの **テーブルごとの件数**（最新時刻とドリフトの種類を含む）を保持し、Validation と Cut over がそれを使います:

| | 動作 |
|---|---|
| **Validation** | どのモードを選んでも、それらのテーブルを **自動的に CHECKSUM で比較** します（実行前に Options がどのテーブルかを表示します）。後からデッドレターが届くと、レポートは *「Tables match — cut over waits for a CHECKSUM re-check of N table(s)」* と表示し、**Re-check N table(s) with CHECKSUM** を提示します。デッドレターの履歴を確認できない場合（後述）は、代わりに *「Tables match — cut over waits for one CHECKSUM run of every table」* と表示し、Fast sweep をオフにした CHECKSUM モードでの実行を 1 回行えば解消します。REPLICA IDENTITY が FULL 未満に下がったテーブル（[§5.6](#56-リキーされた-postgresql-テーブルとカットオーバー)）と、CDC の実行中にソーススキーマが変わったテーブル（[§5.7](#57-ソーススキーマの変更とカットオーバー)）も同じように CHECKSUM で比較します。 |
| **Cut over は次のすべてを満たしたときにのみ開きます** | (1) 各デッドレター対象テーブルが、最新のデッドレターレコードより **1 分以上後に開始した** CHECKSUM 比較で一致した; (2) ツールが、**最新の Validation が終わった後に開始した**、CloudWatch Logs の CDC デッドレターログの **成功した完全な読み取り** を行った; (3) その読み取りの履歴が **Full Load のウォーターマーク**（CDC only では CDC の開始）まで遡る。 |
| **保留された変更** | まだデッドレターではありません: シンクが一意インデックスのために保留した変更（[§4.4](04-cdc-and-dsql-constraints.md#44-sink-がデータパスで-dsql-の制約を処理する方法)）は、待機が終わったときにはじめてデッドレターになるため、その間の読み取りはそれを数えられません。最終検証の前に、ソースの最後の書き込みから少なくとも 5 分待ってください（[§10.3](10-conclusion.md#103-カットオーバー-アプリケーションを-dsql-へ切り替える) の手順 3）。そのテーブルの Stream lag が待機を示します。 |
| **再起動** | テーブルごとの件数、最新時刻、ドリフトの種類はアプリの再起動後も残りますが、Data Migration ステップのレコード一覧は残りません。再起動後、Cut over はログを自動的に読み直します — Validation または Cut over ステップが描画されるたびに範囲の限られた読み取りを 1 回、最大 1 分に 1 回です。 |

**フェイルクローズ** で動作します。ログを読めない（多くは `logs:FilterLogEvents` 権限の不足 — デプロイされたタスクロールは `dsql-cdc-*` または `mysql-dsql-cdc-*` という名前の CDC スタックをカバー。ローカルの AWS プロファイルにも同じ権限が必要）、CDC インフラ（とともにロググループ）が削除された、または読み取りがページ上限で止まった場合、Cut over はランブックの代わりに赤い通知を表示します。履歴を確認できない場合 — すでに実行中のときにアタッチしたパイプライン、または以前のバージョンのツールが保存したセッション — は、代わりに黄色（警告）の通知を表示します。全テーブルの CHECKSUM 実行を 1 回行えば自動的に解消します。

**Check again** は止まった位置から読み取りを続けます（1 回では読み切れない大きなロググループも、押すたびに先へ読み進みます）。**Continue without this check** はその判断をアクティビティログに記録し、再確認すべきテーブルが残っていないときにだけ提示されます。それまでに見たレコードに範囲が限定され、より新しいレコードが届くと再び開きます — ただしログを読めない間は例外です。その間ツールは新しいレコードを見られないため、アプリケーションを切り替える前に別の方法でストリームを確認してください。新しい Validation の実行で消え、Validation の不一致を上書きすることはありません。CHECKSUM が再確認でも失敗し続けるデッドレター対象テーブル（テーブルのエラーに理由が表示されます）は、再確認では解消できない唯一のケースです。**Objects to validate** でオフにして再実行し、Cut over で承認してください。（孤立チェックが失敗したテーブルはこのケースではありません: 直すべきことは **Orphan records** が示します、5.3。）デッドレター対象テーブルについては、Cut over は CHECKSUM が値を比較できない列（5.1）もブロックしない警告として再表示します。

一致しないテーブルの **対処手順**:

- **Full Load + CDC:** ソースのスキーマが変わった場合は Step 1（Evaluation）を再実行 → Stop CDC → **Drop & reload** でテーブルをリロード → Start CDC → 再確認。
- **CDC only:** Aurora DSQL 上の行を手作業で修正（dead-letter queue カードに各レコードの主キーと Kafka オフセットが表示され、キーの値は整数か UUID のときだけ表示されます）→ 再確認。カードがキーの値を伏せるテーブルには **Start over** を使ってください。ソースの `TRUNCATE` のデッドレターはどの行も示しません: Stop CDC → ソースにもう存在しない行をトランザクションあたり最大 3,000 行ずつ削除 → Start CDC → 再確認（[§4.2](04-cdc-and-dsql-constraints.md#42-cdc-は-スキーマ-ではなく-データ-を複製する--重要)）。

**Full Load only** は影響を受けません。ただし同じセッションで先に CDC を実行していた場合、そのとき記録されたデッドレターには引き続き CHECKSUM での一致が必要です。

## 5.6 リキーされた PostgreSQL テーブルとカットオーバー

この節は **PostgreSQL** ソースにのみ、そして CDC が **リキー** するテーブル — ソースの主キー外の列を加えた複合ターゲットキー（Schema Conversion の Composite key、または編集したキー）— にのみ当てはまります。そのようなテーブルの `DELETE` は、ソースの `REPLICA IDENTITY` がテーブルとすべてのパーティションで **FULL** の間だけその列を載せます。CDC の実行中に FULL 未満に下がると（`ALTER TABLE … REPLICA IDENTITY DEFAULT`、新しいパーティション、`USING INDEX`）、delete はエラーもデッドレターもなく Aurora DSQL に行を残すことがあります。CDC モニターがこれを読み直し、下がるたびに記録します（どのような場合かは [§4.6](04-cdc-and-dsql-constraints.md#リキーされた-postgresql-テーブル-replica-identity-の再確認) にあります）。Validation と Cut over はその記録を使います:

| | 動作 |
|---|---|
| **テーブルが FULL 未満** | Validation はそのようなテーブルを **自動的に CHECKSUM で比較** し（実行前に Options に名前を表示します）、テーブルがまだ FULL 未満なら、レポートは *「Tables match — cut over is held: REPLICA IDENTITY on N re-keyed table(s) is below FULL」* と表示します: 変更が失われ続ける可能性があるため、どの CHECKSUM でも解除されません。 |
| **再び FULL** | 修正前に開始した一致では足りません: レポートは *「cut over waits for a CHECKSUM re-check」* と表示し、**Re-check N table(s) with CHECKSUM** を提示します。**Cut over が開くのは**、そのようなテーブルがすべて再び FULL であり、**かつ** ツールが FULL を読んだ時刻より **1 分以上後に開始した** CHECKSUM 比較で一致した場合**だけ**です。さらに Cut over は開く前に、最新の Validation 以降の REPLICA IDENTITY を **1 回新たに読み**（数秒）、その間の変化を捉えます。 |
| **レポートから外れたテーブル、または受け入れたギャップ内のテーブル** | FULL 未満または再確認が必要な他のリキーされたテーブルがない場合に **Continue without this check** で承認できます（アクティビティログに記録され、identity が再び下がると再び開きます）。受け入れたギャップ内のテーブルは、ソースの行を修正して **Drop & reload** でリロードするまで CHECKSUM では解消できません。まだ FULL 未満のテーブルは決して免除できません。 |
| **ソースを読めず**（アプリ再起動後にパスワードがない、読み取りの失敗、テーブルが見つからない）**FULL 未満と記録されたテーブルがない** | Cut over は保留しません: ランブックの上に警告を表示し、アクティビティログの承認行に identity を再確認できなかったことを記録します。アプリケーションを切り替える前に、ソースでこれらのテーブルとパーティションが FULL であることを確認するか、Connect ステップでソースを再接続してください（ツールが自動で読み直します。読み取りに失敗した後は **Check again** を押してください）。まだ FULL 未満と記録されたテーブルがあれば、ツールが FULL を読むまで Cut over は保留され、保留の通知が読み直しの失敗を伝えます。 |
| **再起動、MySQL、Full load only** | 下がった記録はアプリの再起動後も残り、Start over でのみ消えます。**MySQL** ソースと **Full load only** は影響を受けません。 |

修正後も異なるテーブルの **対処手順**: Full Load + CDC — CDC を追いつかせてから Stop CDC、**Drop & reload** でリロード、Start CDC、再確認; CDC only — Aurora DSQL 上の余分な行を手作業で削除してから再確認。

## 5.7 ソーススキーマの変更とカットオーバー

この節は CDC 移行（**Full Load + CDC** または **CDC only**）に、MySQL・PostgreSQL のどちらでも当てはまります。ソースの DDL の中には、拒否される行が 1 つもないまま CDC が書き込む値を変えるものがあります — nullable 列の削除、型の拡張、テーブルの名前変更など（[§4.2](04-cdc-and-dsql-constraints.md#デッドレターにならない変更-ソーススキーマの再確認)）。CDC モニターがソース上のキャプチャ対象テーブルの定義を読み直し、定義が Step 1（Evaluation）のインベントリと一致しなくなったテーブルを記録します（[§4.6](04-cdc-and-dsql-constraints.md#ソーススキーマの再確認)）。Validation と Cut over はその記録を使います:

| | 動作 |
|---|---|
| **テーブルのソース定義が Step 1 のインベントリと異なる** | Validation はそのようなテーブルを **自動的に CHECKSUM で比較** しますが（実行前に Options に名前を表示します）、レポートの表示にかかわらず Cut over は保留されます。列の追加・削除やテーブルが見つからない場合は、たいていテーブルをまったく比較できません（*「N table(s) could not be compared」*。Step 1 を再実行してください）。それ以外の場合、レポートは *「Tables match — cut over is held: the source schema changed on N table(s)」* と表示します。どの CHECKSUM でも解除されません: 比較は各列を Step 1 のインベントリに基づいて描画するため、誤って一致することがあるからです（`INT` に広げられた `TINYINT(1)` は引き続き true / false として比較されます）。 |
| **解消は 2 段階です** | まずソースが再び Step 1 のインベントリと一致する必要があります: Step 1（Evaluation）を再実行して新しい定義を取り込むか（追加または名前変更された列は、先に **Fix target schema…** で Aurora DSQL に追加するか名前を変更します: Validation は Step 1 のインベントリにない列を比較できません）、ソースの変更を元に戻します — ツールが自動で読み直しますし、**Check again** を押しても構いません。そのうえで、その時刻より **1 分以上後に開始した** CHECKSUM 比較でテーブルが一致する必要があります。レポートは **Re-check N table(s) with CHECKSUM** を提示します。キャプチャ対象テーブルの定義を変える Step 1 の再実行も同じように扱います: それ以前に CDC が適用した値が異なる可能性があるため、そのテーブルにも再実行後に開始した CHECKSUM が必要です。Cut over は開く前に、最新の Validation または Step 1 の実行以降のソース定義を **1 回新たに読み**（数秒）、その間の変更を捉えます。 |
| **レポートから外れたテーブル、Step 1 のインベントリにもう存在しないテーブル**（ソースで削除または名前変更した後に Step 1 を再実行）**、または受け入れたギャップ内のテーブル** | 開いているものや再確認が必要なものがほかにない場合に **Continue without this check** で承認できます（アクティビティログに記録され、テーブルが再び変わると再び開きます）。ソースがまだ異なるテーブルは決して免除できません。 |
| **ソースを確認できず**（アプリ再起動後にパスワードがない、Step 1 の実行中または最後の実行の失敗で Step 1 のインベントリがない、読み取りの失敗）**変更ありと記録されたテーブルがない** | Cut over は保留しません: ランブックの上に警告を表示し、アクティビティログの承認行にソーススキーマを再確認できなかったことを記録します。アプリケーションを切り替える前に、CDC の実行中に移行対象テーブルへ DDL が実行されなかったことを確認するか、Connect ステップでソースを再接続してください（読み取りに失敗した後は **Check again**）。変更ありと記録されたテーブルが残っていれば Cut over は保留されます。 |
| **再起動、Full load only** | 各変更の記録はアプリの再起動後も残り、Start over でのみ消えます。**Full load only** は影響を受けません。ただし同じセッションで先に CDC を実行していた場合、そのとき記録された変更は引き続き適用されます。 |

その CHECKSUM で異なったテーブルの **対処手順**: Full Load + CDC — CDC を追いつかせてから Stop CDC、**Drop & reload** でリロード、Start CDC、再確認; CDC only — Aurora DSQL 上の行を手作業で修正してから再確認。
