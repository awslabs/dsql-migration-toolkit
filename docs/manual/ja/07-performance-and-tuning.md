# 7. パフォーマンス、チューニング、そしてこの設計の理由

_言語: [English](../en/07-performance-and-tuning.md) | [한국어](../ko/07-performance-and-tuning.md) | **日本語**_

> **前へ:** [6. 制限事項](06-limitations.md)

デフォルトは Aurora DSQL の上限に合わせてあり、ソースへの負荷も控えめなので、**ほとんどのマイグレーションではチューニングは不要です。** 大きなテーブルはすでに主キーの区間に分けて読み書きされ、進行中のバッチ数には、それ以上増やしても Aurora DSQL が速くならないところで上限を設けてあります。大規模な実行では、*Tables in parallel* をタスクの vCPU 数に設定してください ([§7.2](#72-並列度のチューニング))。ソースが本番トラフィックを処理しているときは、代わりに 2〜4 から始め、ソースを観察しながら上げてください ([§7.3](#73-ソースへの負荷を最小化する))。Aurora DSQL に合わせてツールがすでに行っていることは [§7.1](#71-aurora-dsql-に対してツールが代わりに行うこと) にあります。

> 以下のすべての設計上の選択は、文書化された Aurora DSQL の動作・制限にマッピングされています。出典: [DSQL のクォータと制限](https://docs.aws.amazon.com/aurora-dsql/latest/userguide/CHAP_quotas.html)、 [並行性制御](https://docs.aws.amazon.com/aurora-dsql/latest/userguide/working-with-concurrency-control.html)、 [PostgreSQL→DSQL マイグレーションガイド](https://docs.aws.amazon.com/aurora-dsql/latest/userguide/working-with-postgresql-compatibility-migration-guide.html)、 [非同期インデックス](https://docs.aws.amazon.com/aurora-dsql/latest/userguide/working-with-create-index-async.html)、 [プライマリキー](https://docs.aws.amazon.com/aurora-dsql/latest/userguide/working-with-primary-keys.html)。

## 7.1 Aurora DSQL に対してツールが代わりに行うこと

各行は、文書化されている Aurora DSQL の動作・上限と、それに対してツールが行うことの組です。

| Aurora DSQL の動作 | ツールが行うこと |
|---|---|
| 書き込み競合はコミット時に検出され、敗れたトランザクションは `40001` で失敗します (行ロックはありません) | すべての書き込みトランザクションを小さく冪等に保つため (Full Load のバッチや CDC のチャンクは最大 3,000 行で、プライマリキーで書き込みます)、再実行は安価で安全です |
| 1 つのトランザクションは最大 3,000 行・10 MiB・5 分で、DDL は 1 つだけです | 最大 3,000 行と 8 MiB のバイト予算でバッチ化し、トランザクションごとに DDL を 1 つだけ実行します |
| ストレージは主キーでパーティショニングされるため、主キー順の挿入の流れは一度に 1 つのキー範囲へ向かいます: 実測では、バッチサイズや進行中のバッチ数にかかわらず約 20,000 rows/s です | 大きなテーブルを主キーの区間に分けて読み取るため、その書き込みは同時に複数のキー範囲へ向かいます。進行中のバッチはキー範囲あたり 2 (テーブルまたは部分あたり最低 4)、実行あたり 128 までに制限します: それ以上は待つだけです (§7.2) |
| `CREATE INDEX ASYNC` はバックグラウンドでインデックスを構築します | テーブルの二次インデックスを、空のうちに、どの行よりも先に作成します: Schema Conversion の適用が作成し、**Drop & reload** も作り直したテーブルにもう一度作成して、ロードの前に構築を最大 10 分待ちます。実測では、インデックスは空のテーブルのほうがはるかに速く構築されるため、ロードとインデックスの構築が早く終わります (§7.5) |
| IAM トークンの有効期間は約 15 分で、接続は 60 分で切れます | トークンを期限切れの前に更新し、Aurora DSQL が拒否したときはすぐに更新するため、数時間にわたるロードや CDC ストリームも認証で止まりません |
| ターゲットにできる論理レプリケーションスロットがありません | 独自のバルクローダー (keyset ストリーミング: 再開可能、メモリ有界) でコピーし、そのあと Debezium → MSK → カスタムシンクで変更をストリーミングします。Kafka が変更をバッファするため、競合の集中中にシンクが遅れてもイベントは失われません |

**書き込みが失敗したとき。** `40001` の競合が起きると、ツールは **トランザクション全体** を指数バックオフとジッターで再実行するため、競合したワーカーが同じタイミングでリトライすることはありません。切断された接続や期限切れの IAM トークンも、再接続してリトライします。Aurora DSQL の `XX000` ("server unavailable") もリトライします。一時的なサービス状態です。リトライが予算を超えて続く場合、Full Load のバッチは失敗し (**Retry unfinished tables** で再ロードします。これが原因で隔離される行はありません)、シンクは Kafka Connect にバッチを再配信させます (デッドレターになる行はありません)。繰り返し発生する場合は AWS サポートに問い合わせてください。それ以外のエラーはリトライしません: Full Load はバッチを拒否された行まで分割してその行を隔離 (quarantine) し、シンクはその行を DLQ に送ります。正常な行はすべて反映されます。

### プライマリキー戦略 — ホットパーティションの回避

Aurora DSQL は **プライマリキーによってストレージをパーティショニングし分散** します。AWS のガイダンスは明確です。**「ランダムなプライマリキーを選択してください… 単一キーへの競合を増やすパターンは避けてください。」** MySQL の `AUTO_INCREMENT` キーは単調増加するため、すべての新しい行が最も右側の同じキー範囲を狙います。カットオーバー後のアプリケーションの挿入 (そして CDC がそれをストリーミングする間は CDC の挿入) が 1 つのパーティションに収束し、**行が論理的に競合していなくても** 書き込みレイテンシが上がります。大きなテーブルの書き込みは、Full Load が自らキー範囲に分散します ([§7.2](#72-並列度のチューニング))。

ツールはこうしたキーを **Evaluation** で知らせ (`AUTO_INCREMENT` → `MANUAL`)、**Schema Conversion** でテーブルごとに戦略を選べます: キャッシュ付き identity 列 (`bigint` に収まる単一列キーのデフォルト)、整数キーの維持、または複合キーです ([主キー戦略を選ぶ](02-evaluation-and-schema-conversion.md#主キー戦略を選ぶ) を参照)。

#### ホットパーティション向けの複合キーオプション

Schema Conversion では、選んだ高カーディナリティの列をテーブルの元のキーの先頭に置けます。たとえば `(id)` の代わりに `(customer_id, id)` とすると、挿入は最も右側のパーティション 1 つではなく多数のキー範囲に分散されます。

テーブルの書き込みが明らかにホットパーティション化されていて (低い OCC 競合率のまま負荷下で `CommitLatency` にロングテールが出る: p99 で数秒、最大で数十秒)、**かつ** 自然な高カーディナリティのグルーピング列がある場合に使います。Aurora DSQL での実測では、バッチを大きくしても進行中のバッチを増やしても、ホットなキー範囲は速くなりません (1 つのキー範囲は進行中の数にかかわらず約 20,000 rows/s でした)。速くなるのは書き込みをキー範囲全体に分散したときだけです。Full Load は大きなテーブルをキー範囲ごとに読み取ってこれを行い (§7.2)、複合キーはそのテーブルへのすべての書き込みに対して、カットオーバー後のアプリケーションの書き込みと CDC の書き込みも含めてこれを行います。負荷がほかの要因 (クライアント CPU など) に律速されているなら、複合キーは何も変えません。まず計測してください ([§7.5](#75-ライブインフラでの実測--71-と-72-の裏付け) 参照)。

- **ソースは一切変更されません。** 変更されるのは Aurora DSQL のターゲットキーだけです。`CREATE UNIQUE INDEX ASYNC` が元のキーの一意性を保つため、元のキーによる参照や制約は引き続き有効です。
- **アプリケーションも一緒に変わります。** カットオーバー後、クエリ・JOIN・アップサートは複合キーを使う必要があり、先頭に追加した列は決して変更できません (Aurora DSQL の主キーはインプレース更新ができないため)。先頭列の一覧には、Aurora DSQL のキー制限を満たす列 (`NOT NULL`、インデックス化できる型、合計 8 列・1 KiB 以内) だけが表示されます。
- **Full Load と CDC の両方で対応します** (どちらのエンジンでも)。CDC にはこのバージョンがデプロイしたインフラが必要です ([第 6 章](06-limitations.md))。**PostgreSQL** ソースでは、さらに **実行中ずっとテーブルとすべてのパーティションに `REPLICA IDENTITY FULL`** が必要です。そうでなければ `DELETE` が追加されたキー列を運ばないためです。これがないと前提条件チェックが Start をブロックし、CDC の実行中は CDC モニターが再確認します ([§5.6](05-validation.md#56-リキーされた-postgresql-テーブルとカットオーバー))。

## 7.2 並列度のチューニング

フェーズが遅すぎてハードウェアに余裕があるときは設定を引き上げ、忙しいソースを保護したいときは引き下げます。**Full Load** と **Validation** は環境変数または **Settings** (§7.6) でチューニングし、**CDC** はツールが自動でサイジングします。Full Load で効く設定は *Tables in parallel* です: キー範囲と進行中のバッチ数は、§7.5 の実測に基づいてすでに決めてあります。

### Full Load

| 設定 (env var) | デフォルト | 上限 | 効果 |
|---|---|---|---|
| `DSQL_MIGRATOR_FULL_LOAD_TABLE_PARALLELISM` | 4 | ≤ 16 | 同時にロードするテーブル (または大きなテーブルの部分) の数。それぞれがワーカープロセス 1 つとソース接続 1 つを使います。大規模な実行ではタスクの vCPU 数に設定します。 |
| `DSQL_MIGRATOR_FULL_LOAD_BATCH_PARALLELISM` | 8 | ≤ 32 | テーブル (または部分) ごとの進行中のバッチ数で、それぞれが自身の Aurora DSQL 接続を使います。ツールはさらにキー範囲あたり 2 (テーブルまたは部分あたり最低 4)、実行あたり 128 に制限するため、1 つか 2 つのキー範囲で読むテーブルでは 4 より大きい値は何も変えません。 |
| `DSQL_MIGRATOR_FULL_LOAD_BATCH_ROWS` | 2000 | ≤ 3000 | バッチ書き込みごとの行数 (DSQL の 3000 行上限でハードキャップ)。 |
| `DSQL_MIGRATOR_FULL_LOAD_READER_SHARDS` | `0`（自動） | ≤ 32 | **大きな**テーブルを読み書きする主キー区間の数 K（[§3.8](03-full-load.md#38-並列ロード)）。`0`: 推定 5,000,000 行から 2,500,000 行ごとに 1 区間、最大 32。`1`: 無効。`2`–`32`: その数ちょうど。*Tables in parallel* が 1 より大きいことと、整数の先頭主キー列が必要。**Settings → Full Load** の *Reader shards per large table* でも設定可。 |
| `DSQL_MIGRATOR_FULL_LOAD_SHARD_MIN_ROWS` | 1000000 | — | この推定行数以上のテーブルのみ分割 (自動の場合はさらに 5,000,000 行以上が必要)。小さいテーブルは単一リーダー。 |

> **キー範囲: なぜ役立ち、何が代償になるか。** Aurora DSQL はテーブルの 1 つのキー範囲を、バッチサイズや進行中のバッチ数にかかわらず約 20,000 rows/s で書き込むため、大きなテーブルは書き込みを複数のキー範囲に分散すると速くロードされます (150M 行の PostgreSQL テーブルを 32 区間で約 205,000 rows/s、§7.5)。区間の読み方はソースによって異なります:
>
> - **PostgreSQL:** 区間は 1 つのスナップショットを共有し、実行全体の推定行数に占めるそのテーブルの割合に応じた数 (最大 *Tables in parallel*) のワーカープロセスが読みます。
> - **MySQL:** 1 つのリーダーセッションがすべての区間を 1 つのスナップショットから読むため、テーブルはソース接続 1 つとワーカープロセス 1 つを使い、ほぼ 1 コアを使い切ります: 巨大な MySQL テーブルは 1 コアの速さでロードされます (私たちの実行ではホストによって約 25,000–55,000 rows/s)。binlog の開始位置からの **Full load + CDC** では、2 以上を明示的に指定すると、すべてのユニークキーが先頭のキー列を含むテーブルは、代わりに別々のスナップショットで読む部分に分け、部分ごとにプロセスを 1 つ使います (150M 行を 16 部分で全体約 164,000 rows/s、1 セッションでは定常約 55,500)。そのコピーは CDC が再生して初めて一貫するため、ツールはその再生を飛ばす経路、つまりそのテーブルのチェックを外すこと、Full load only への切り替え、より後の位置からの CDC の開始を拒否します ([§3.8](03-full-load.md#38-並列ロード))。
>
> **トレードオフ:** PostgreSQL と、MySQL の別々のスナップショットで読む部分では、K > 1 は空いていた slot を同じテーブルへの同時読み取りに変え、そのテーブルを読み終えるまで続くので、その間ソースの読み取り速度・DSQL 接続・メモリが最大 `TABLE_PARALLELISM` 倍まで増え、PostgreSQL ソースは最後の区間を読み終えるまで共有スナップショットを保持します。まだ本番トラフィックを処理しているソースでは、`Threads_running` スロットル (`FULL_LOAD_MAX_SOURCE_THREADS_RUNNING`、§7.3) と組み合わせてください。*Batches per table* を上げても、1 つのキー範囲は速くなりません (§7.5): 巨大な MySQL テーブルを 1 コアの速さより速くロードするには、上記の別々のスナップショットで読む部分を使ってください。

> **接続クォータのガードレール。** 実行が使う Aurora DSQL 接続は、多くても進行中のバッチ数 (ツールがキー範囲あたり 2、テーブルまたは部分あたり最低 4、実行あたり 128 に制限します) に、実行中のテーブルまたは部分ごとに 1 つを足した数です。DSQL は **クラスターあたり最大 10,000 接続** を許可しますが、**新規接続は 1 秒あたり 100** のみなので、この上限で実行はクォータに十分収まります。キー範囲がこなせる以上の進行中のバッチは、rows/s を増やさず、コミットレイテンシと Aurora DSQL のコンピュートコスト (`ComputeDPU`) を増やすだけです: キー範囲あたり 2 の代わりに 4 にすると、同じ rows/s のまま両方が約 2 倍になりました (§7.5)。

### Validation

| 設定 (env var) | デフォルト | 上限 | 効果 |
|---|---|---|---|
| `DSQL_MIGRATOR_VALIDATE_MAX_WORKERS` | 4 | ≤ 32 | 同時に比較するテーブル数 (それぞれ独自の読み取り専用のソース + ターゲット接続を使用)。`1` = 順次。 |

多すぎる同時スキャンからソースを保護するために 32 に制限しています。

### CDC (データプレーン)

**CDC のサイジングはツールが行うため、UI で設定するものはありません。** キャプチャ対象のテーブルごとに Kafka トピックが 1 つあり、シンクはトピックのパーティションごとにタスクを 1 つ実行するため、シンクの並列度 = トピックあたりのパーティション数 × テーブル数 です。ツールはこの積がシンクタスク 8 個という上限に達する最小のパーティション数を選び、そこで止めます:

| キャプチャテーブル数 | トピックあたりパーティション | `SinkTasksMax` | 実効並列度 |
|---|---|---|---|
| 1 | 8 | 8 | 8 |
| 2 | 4 | 8 | 8 |
| 3 | 3 | 8 | 8 |
| 4 | 2 | 8 | 8 |
| ≥ 8 | 1 | 8 | 8 |

**偏ったワークロードでは大きいテーブルにパーティションを多く割り当てます。** 上の規則は負荷が均等であると仮定しています。テーブル数が多いとトピックあたり 1 パーティションになり、1 パーティションは最大 1 つのシンクタスクにしか消費されないため、ホットテーブルが単一タスクでストリーミングされ、残りはアイドルになります。そこでツールは、スキャン不要のテーブル別行数見積り (Full Load ウォーターマークの値、または Full Load 前に CDC インフラをデプロイした場合は `information_schema` からの即時見積り) を読み取り、大きいテーブルに 2 または 4 パーティションを割り当てます。これは **自動** で、実際に偏ったキャプチャでのみ作動し、負荷が均等なら何もしません。トピックのパーティション数は作成時に固定されるため、変更するには CDC を再デプロイする必要があります。

主キーを保つ変更であれば、行単位の順序は守られます (Debezium が各レコードを主キーでキー付けします)。パーティションをまたぐ変更は 2 種類あります: 主キーを変える `UPDATE` と、ある行から別の行へ渡される一意の値です。主キー以外に一意インデックスがあるテーブルでは、このバージョンがデプロイした CDC インフラがそのような変更を、もう一方の行の変更が適用されるまで保留します: 保留された変更ごとに最大 5 分です。ほかのパーティションは流れ続け、待機はそのテーブルの Stream lag として表れます。以前のバージョンがデプロイした CDC インフラはその変更を即座にデッドレターにするため、待機の動作を得るには CDC インフラを Delete して再度 Deploy してください ([第 6 章](06-limitations.md))。

**推論の上書き (上級)。** 上書きする理由はほとんどありません: シンクタスクが 8 個を超えると、パーティションを増やしてもスループットはほとんど伸びず MCU コストだけが増えます (4 → 8 パーティションで 2 倍ではなく約 1.4 倍)。シンクが Aurora DSQL の書き込みレイテンシに律速されるためです。それでも必要な場合は、ツールが cdc-stack をデプロイする前に以下の環境変数を設定してください (空/無効な値は推論されたデフォルトにフォールバックします):

| 環境変数 | 上書き対象 | 備考 |
|---|---|---|
| `DSQL_MIGRATOR_CDC_TOPIC_PARTITIONS` | テーブルごとのトピックのパーティション数 | トピック作成後は**不可逆**。さらに**均等なパーティション数を強制** — 上記のサイズ比例割り当てを無効化します。 |
| `DSQL_MIGRATOR_CDC_SINK_TASKS_MAX` | シンクコネクタの `tasks.max` | 実効値はパーティション数で上限。 |
| `DSQL_MIGRATOR_CDC_MCU_COUNT` | ワーカーあたりの MSK Connect MCU、**ソース**コネクタ | 1 / 2 / 4 / 8 のいずれか。 |

#### シンクのコンピュート（最初に触るべきノブ）

シンクが追いつかない場合は、ソースではなく **シンクの** コンピュートを上げてください。高負荷ではシンクが CPU バウンドになる一方、シングルタスクのソースは CPU に余裕があります。**Settings → CDC → "Sink compute (MCU)"** (または `DSQL_MIGRATOR_CDC_SINK_MCU_COUNT`) で設定し、ワーカーあたり 1 / 2 / 4 / 8 MCU が選べます (1 MCU = 1 vCPU + 4 GiB、デフォルトは 4)。測定曲線は付録 (§12) を参照してください。

**いつ反映されるか。** Full Load のノブとは異なり、Start CDC がシンクコネクタを作成/更新するときに適用されます:

| パイプラインの状態 | 値を変更した場合 |
|---|---|
| CDC 未デプロイ | 次のインフラデプロイと Start CDC で使用されます。 |
| インフラのみデプロイ済み、未開始 | 次の Start CDC で使用されます。 |
| **すでにストリーミング中** | **次の Start CDC まで何も変わりません: Stop CDC の後に Start CDC。** |

CDC のストリーミング中、CDC ステップには **Stop CDC** しかないため、新しいシンク容量は Stop CDC の後にもう一度 Start CDC したときに反映されます。そのときコネクタはその容量で作り直され（コネクタの作成・削除のたびに MSK Serverless のパーティションを使います）、Stop の時点でシンクが適用していなかった変更は CDC トピックから適用されるため、その再起動にギャップがないのはトピックがまだその変更を保持している間だけです（[§4.3](04-cdc-and-dsql-constraints.md#43-ギャップのない-full-load--cdc-ハンドオフ)）。

> **ソースの再起動は自動的に処理されます。** ソースコネクタが 10 分間再試行するため、ソース RDS/Aurora の再起動（メンテナンス、フェイルオーバー、リサイズ）は吸収されます: コネクタが再起動ウィンドウの間再試行し、コミット済み binlog オフセットからギャップなく再開します — オペレータ操作不要。再起動後に CDC を Stop/Start する**必要はありません**。

### AWS (ECS Fargate) の場合

Full Load と Validation の環境変数は、タスク定義のコンテナ `environment` ブロック (`deploy/cloudformation.yaml` または独自のタスク定義) に設定して再デプロイします。CDC の設定は、ツールが cdc-stack をデプロイするときに渡されます。

> **再デプロイなしで実行の合間に再チューニング。** サイドバー下部の **Settings** を開き、**Full Load** または **Validation** タブへ移動します。ローダーとバリデーターは実行のたびに設定を読み直すため、そこで設定した値は **次の** 実行にすぐ反映されます。アプリ全体に効き、再起動でリセットされるため、保持したい値はタスク定義に設定し、**Settings** は実験に使ってください。

ロードの規模に合わせてタスクのサイズを決め、*Tables in parallel* をその vCPU 数に設定してください: 同時にロードするテーブル (または大きなテーブルの部分) 1 つがワーカープロセス 1 つです。**メモリはハード制限です。**

| 設定 | 評価用途 | 実運用の大規模 Full Load |
|---|---|---|
| `ContainerCpu` | 0.5–1 vCPU (`512`–`1024`) | 4–16 vCPU (`4096`–`16384`) |
| `ContainerMemory` | `1024` MiB | 4 vCPU では ≥ `8192` MiB、16 vCPU では ≥ `32768` (その CPU に対する Fargate の最小値) |

- **MySQL のロードはタスクの CPU に律速されます。** MySQL の行の読み取りと変換は、実行中のテーブルまたは部分ごとにほぼ 1 コアを使うため、スループットは *Tables in parallel* までは vCPU 数とともに伸びます (16 vCPU で 20M 行のテーブル 16 個: 約 193,000 rows/s、全コアが稼働)。
- **PostgreSQL のロードは Aurora DSQL に律速されます。** 値がほぼそのまま通過するため、タスクが必要とするコアは少なく (336,000 rows/s で約 3.5 コア)、スループットはキー範囲 (上記) から得られます。
- **ホストによって差があります。** Fargate はタスクを CPU の異なるホストに配置するため、同じ MySQL のロードがタスクによって最大約 1.8 倍速く動きました: 変更の効果は複数回の実行で判断してください。
- **メモリ。** `ContainerMemory` を超えるとカーネルがタスクを OOM-kill し、アプリの終了ログはありません (CloudWatch のスパイクと ELB タイムアウトのみ)。広い行 (大きな `TEXT`/`BLOB` 値) がバッチを約 8 MiB の上限まで満たすため、デフォルトの `512` CPU / `1024` MiB は同時にソース書き込みがある実運用ロードで OOM-kill された事例があります。アプリはメモリの high-water と上限の約 80% の圧迫警告をログ (タスクが死んでも残るアクティビティログを含む) に残すので、根拠を見て適切なサイズを決められます。

どちらを上げる場合も再デプロイが必要です。Fargate はタスクのメモリを自動スケールしません。CPU↔メモリの完全な組み合わせ表は [DEPLOYMENT.ja.md → タスクのサイジング](../../../deploy/DEPLOYMENT.ja.md#タスクのサイジング--containercpu--containermemory) を参照してください。

> **ローカル実行** も同じ環境変数を読み取ります — `mysql-dsql-migrator ui` を起動する前に、シェルまたは `.env` に設定してください。

## 7.3 ソースへの負荷を最小化する

**ソースの読み取りはすでに軽量です。** keyset ストリーミング (`OFFSET` の再スキャンなし)、テーブルごとに同時に 1 ページだけ in-flight、グローバルロックなし、`COUNT(*)` の代わりにスキャン不要の行数見積り。残る管理対象は同時読み取りの負荷で、そのほとんどを設定 1 つで制御できます。

### 唯一のレバー: テーブル並列度

`DSQL_MIGRATOR_FULL_LOAD_TABLE_PARALLELISM` (デフォルト **4**、最大 **16**) は、ソースから同時に読み取るテーブル (または大きなテーブルの部分) の数で、それぞれがソースへのストリーミング接続を 1 つ使います (PostgreSQL では、テーブルがスナップショットを共有している間はさらに 1 つ)。`BATCH_PARALLELISM` と `BATCH_ROWS` が変えるのは Aurora DSQL 側だけで、ソースの読み取り負荷は変えません。オプトインの `Threads_running` 上限が 2 つ目の安全弁です (下のノートを参照)。並列度は **Settings → Full Load** で実行の合間に試すか、環境変数で設定して永続化します (§7.2)。

### 控えめに始め、観察しながらチューニング

並列度を **スループットのダイヤルではなくスロットル** として扱ってください — テーブル数ではなく、測定された余裕に合わせて上げます:

1. **低く始める(2〜4)** — 大きなインスタンスでも。遅く終わる方が、本番のレイテンシ障害を引き起こすよりはるかに安価です。
2. **ソースを観察** — 瞬間的なスパイクではなく 5〜10 分の持続的なウィンドウで。
3. **明確な余裕があるときだけ小刻みに上げ**、再観察。(並列度は実行ごとに 1 回読まれるため、変更は **次の** 実行から適用)

**観察すべきシグナル**(Amazon RDS/Aurora — CloudWatch + Performance Insights):

- **上げてよいシグナル:** `CPUUtilization` が線のはるか下、`ReadIOPS` が上がっても `ReadLatency` が平坦、 `DiskQueueDepth` が低い、`BurstBalance` / `EBSIOBalance%` / `CPUCreditBalance` が 100% 付近、Aurora `BufferCacheHitRatio` が安定(~99%)。
- **今すぐ下げるシグナル:** `CPUUtilization` が持続的に > ~85〜90%;`ReadLatency` が IOPS 頭打ちの中で 2〜5 倍に上昇;いずれかの burst/credit balance が **0 に向かって低下**(0 になる *前に* スロットル — 回復が遅い); `FreeableMemory` がほぼゼロ / `SwapUsage`;Aurora `BufferCacheHitRatio` の低下(コールドスキャンが本番の hot page を追い出している);そして何より **アプリケーション自身のクエリレイテンシの上昇** — インスタンス指標に関係なく最終的な back-off トリガー。

> [!note] ソース負荷の安全弁 **QPS リミッターはありません**が、任意の同時実行スロットルが **あります**: `DSQL_MIGRATOR_FULL_LOAD_MAX_SOURCE_THREADS_RUNNING`(デフォルト `0` = オフ、**Settings → Full Load** でも設定可)は、ソースのグローバル `Threads_running` が上限を超えている間、新しいソース読み取りを一時停止します — gh-ost の `--max-load` 相当のガードです。それ以外はテーブル並列度を下げることが制御手段です。バルクロードは **オフピーク** にスケジュールし、インスタンスのバックアップ/メンテナンスウィンドウと重ならないようにしてください(スナップショット + フルスキャンの同時実行は gp2 `BurstBalance` にとって最悪のケースです)。

### 開始前の余裕チェックリスト

代表的なピークで以下をベースライン化し、ロードを追加する余裕があるか確認してください: **CPU** の余裕;**ストレージ** — gp2 `BurstBalance`(持続スキャンがこれを 0 まで消費するとベースライン IOPS に崩落 — 本番を害する最も一般的な経路)、および `ReadIOPS`/`ReadThroughput`/`ReadLatency`/`DiskQueueDepth`(Aurora: `VolumeReadIOPS`); **バッファプール** `BufferCacheHitRatio`;**接続** `DatabaseConnections` vs `max_connections`(16-way + アプリプールが余裕を持って上限以下);**空き容量/メモリ**。ビジーな RDS ソースでは、gp3 + 余裕のある IOPS がフルスキャンで最も頻繁に足を引っ張る gp2 バースト崖を取り除きます。

### 書き込みの多いソースでの大きなテーブル

各テーブルの読み取りは、そのテーブルの読み取りが終わるまで開いたままの `REPEATABLE READ` スナップショット内で実行されます。`READ-COMMITTED` に設定された MySQL ソースでも同じです (ツールが自身のセッションを `REPEATABLE READ` に設定します: [§3.2](03-full-load.md#32-ストリーミングエクスポート--テーブルサイズによらず一定のメモリ))。Validation も、比較するテーブルごとに同じです。書き込みの多いソースでは、開いた read view が InnoDB の undo 履歴 (**History List Length**) の purge を妨げるため、undo/ディスク使用量が増えて読み取りが遅くなり、多数のテーブルが in-flight のときは **最も古い** read view が purge 境界を決めます。抑えるには:

- 並列度を下げます (開く read view が減ります)。
- 大きなテーブルの read view は、そのテーブルを読み終えるまで続くものと考えてください: 自動の分割は、すべての区間を 1 つのセッションで 1 つのスナップショットから読みます。binlog の開始位置からの Full load + CDC では、*Reader shards per large table* に 2 以上を明示的に指定するとこれを短くでき、各 read view はそれぞれの区間を読む間だけ保たれます。その代わり、そのテーブルへの同時読み取り (§7.2) と [§3.8](03-full-load.md#38-並列ロード) の拒否が伴います。
- History List Length を監視し、開始前に空き容量を確保して、undo の増加がストレージフルを引き起こさないようにします。

### リードレプリカから読むのはどうか?

Full Load を **RDS リードレプリカ / Aurora リーダーエンドポイント** に向けると、スキャン IOPS・CPU・バッファプール churn がすべてプライマリから外れます — 本番を保護する最も強力な方法で、並列度もより強く押せます。

|  | Full Load のみ | Full Load + CDC |
|---|---|---|
| **読み取り元** | **リードレプリカ** (gp3、必要なら期間中だけスケールアップ) | **プライマリ/ライター**。レプリカは不可 |
| **開始時の並列度** | 4〜8。明確な余裕があるときだけ段階的に引き上げ | 2〜4。明確な余裕があるときだけ段階的に引き上げ |
| **その他** | スナップショットがレプリカラグ分だけ少し過去の時点を反映するのは正常です | **オフピーク** に実行し、binlog リテンションを Full Load 全体より長く設定 |

**CDC を使うときにレプリカを使えない理由。** ツールは CDC ハンドオフの **ウォーターマーク** (binlog ファイル/位置、GTID、`server_uuid`) を接続したソースから取得し、CDC コネクタも同じホストからストリーミングします。レプリカの binlog 座標はプライマリとは **別の名前空間** にあり、RDS のレプリカは binlog が無効または保持されないことが多いため、レプリカから取得したウォーターマークは気づかないうちに **CDC のデータギャップ** を生むことがあります (スナップショット時点から CDC 開始までの変更が失われます)。リテンションは `CALL mysql.rds_set_configuration('binlog retention hours', N)` で設定します。

## 7.4 個々のクエリのチューニング

上記の並列度のノブに加えて、Aurora DSQL の分散実行モデルに合わせて個々のクエリをチューニングできます — そこではプライマリキーが *まさに* テーブルであり、フィルタのプッシュダウンがコストを左右し、単位は (PostgreSQL の `cost=` ではなく) **DPU** です。オプションの **Query Converter** は MySQL クエリを変換し、`EXPLAIN` / `EXPLAIN ANALYZE` で読み取り専用でプローブし、そして AI 支援をオンにすると **AI DBA** が DSQL の効率のためにそれを書き換え、書き換えを再テストして DPU の改善を証明します。

> 完全なワークフローについては [第 9 章 — Query Converter と AI DBA](09-query-validation.md) を参照してください。

## 7.5 ライブインフラでの実測 — §7.1 と §7.2 の裏付け

これらの実行は、上記の設計が実際に表れることを確かめたものです。**パフォーマンスの仕様や保証ではなく、手法を示す例** として読んでください: ソース、タスクのホスト、Aurora DSQL の状態がいずれも数値を動かします。`scripts/measure_performance.py` を使えば自分の環境で再現できます (下記)。

> [!note] この数値が得られた条件 ソウル (`ap-northeast-2`)、16 vCPU / 120 GB の ECS Fargate タスク 1 つで動くツール、`db.r8g.16xlarge` の Aurora MySQL と Aurora PostgreSQL のソース、そして *Tables in parallel* 16 以外はすべてデフォルトの設定 (Reader shards は行に別の記載がない限り自動、Batches per table は 8)。

| ロード | 結果 |
|---|---|
| PostgreSQL、16 テーブル × 20M 行 | 全体で約 336,000 rows/s、定常状態で 600,000 |
| PostgreSQL、150M 行の 1 テーブル (32 区間) | 全体で約 205,000 rows/s |
| MySQL、16 テーブル × 20M 行 | 全体で約 193,000 rows/s、タスクの 16 vCPU が飽和 |
| MySQL、150M 行の 1 テーブル、Full load only (1 セッション) | 定常で約 55,500 rows/s (1 コアの 1 プロセス。25 分で停止、75M 行まで) |
| MySQL、同じテーブルを Full load + CDC で、Reader shards 16 | 全体で約 164,000 rows/s (以前のコピーの DROP と並行、下記) |

これらと、`db.r7g.large` のソースと 4 vCPU のタスクでのより小さな実行からわかること:

- **壁はバッチではなく 1 つのキー範囲です。** テーブルへの主キー順の流れ 1 つは、進行中のバッチが 8 でも 32 でも、3,000 行のバッチでも約 20,000 rows/s でした。進行中のバッチを増やしても、同じ rows/s のまま Aurora DSQL のコミットレイテンシ (軽い負荷で 26 ms、進行中 8 で 0.7 秒、32 で 3 秒) とコンピュートコスト (`ComputeDPU`、約 4 倍) が上がるだけでした。31–32 のキー範囲に分け、プロセスごとに 2 つずつ読んだ 80M 行の PostgreSQL テーブルは、キー範囲あたりの進行中のバッチが 2 でも 4 でも約 150,000 rows/s でロードされ、2 のときはコミットレイテンシ (1.4–1.6 秒対 2.8 秒) と `ComputeDPU` が約半分でした (行あたりの `TotalDPU` は約 5% 低い)。そのためツールはキー範囲あたり 2、テーブルまたは部分あたり最低 4 を保ちます: 1 つのキー範囲は 4 で 20,000 rows/s に達しました。4 つのキー範囲に分散すると、10M 行のテーブルは全体で約 37,000–40,000 rows/s (ピークで 54,000–60,000)、エンジンごとに 1 つずつのそのようなテーブル 2 つは合わせて 127,000 rows/s で、まだ伸びていました。1 つのキー範囲の約 20,000 rows/s と比べ、上記の 150M 行のテーブルは PostgreSQL で約 10 倍、部分に分けた MySQL で 8 倍 (いずれも全体)、1 セッションの MySQL で 2.8 倍 (定常) 速くロードされました。
- **二次インデックスは空のテーブルに作成します。** 8.5M 行に対する 25 個の二次インデックス (MySQL) では、行より先にインデックスを作成した Drop & reload は開始から終了まで 512 秒で終わり、インデックスをロードの後に構築した場合は 873 秒でした。インデックスのあるテーブルへの行のロードは遅くなりました (485 秒対 262 秒) が、構築は空のテーブルで 13–41 秒、ロードの後では 10–11 分かかりました。
- **新しいテーブルにはウォームアップがあります。** Aurora DSQL は新しいテーブルをパーティション 1 つで始め、大きくなるにつれて分割するため、ロードの最初の 1〜2 分は 1 つのキー範囲ほどの速さで進みます: 短いテストは定常状態で判断してください。
- **以前のコピーの DROP は動き続けます。** ロード済みのテーブルの DROP (Drop & reload も行います) は Aurora DSQL のバックグラウンドジョブです: 数分間、75M 行のコピーでは 1 時間以上、次にロードされるものと並行して続きました。

**CDC レプリケーションラグ — レイテンシの下限。** 別に計測しました (RDS MySQL 8.0 ソース、MSK、`us-east-1`、1 MCU・ワーカー 1 つのシンク、単一カラムのテーブル): ソースのコミット → DSQL 上での可視化は、持続的な負荷ではおよそ p50 0.8 秒 / p95 1.3 秒、バースト負荷では p50 0.5 秒 / p95 0.7 秒でした。多数のテーブルや高い変更率では大きくなり得ます。スループットが必要なときは、§7.2 の CDC パラメータでスケールしてください。

> **再現する:** `scripts/measure_performance.py full-load` は、スループット (テーブルごと、時間ウィンドウごと)、書き込み経路のリトライとレイテンシ、Aurora DSQL がインデックスの構築を終えた時点を報告します。上の表の各行は `--table-parallelism`、`--reader-shards`、`--cdc-mode` で再現でき、`scripts/measure_performance.py cdc-lag` はレプリケーションラグを計測します (アクティブな CDC パイプラインが必要です)。`full-load` はターゲットテーブルを **DROP して再作成** する (`--yes` が必要) ので、**非本番のターゲットでのみ** 使用してください。公平に比較するには、先に以前のコピーを DROP し、Aurora DSQL のバックグラウンドジョブが終わるのを待ってください (`--wait-sys-jobs` は実行を始める前にそれらを待ちます)。

## 7.6 Settings ダイアログ（チューニング・診断・アクティビティログ）

上記のノブは、再起動なしに **UI からも**編集できます。**Settings**（サイドバー下部）がタブ付きダイアログを開きます —

- **Full Load**、**CDC**、**Validation** タブ — §7.2 のチューニングノブ。各タブの冒頭に、変更がいつ反映されるかが表示されます（*Changes apply to the next run.*。CDC タブでは *the next Start CDC*）:
  - **Full Load**: *Tables in parallel*、*Batches per table*、*Rows per batch*、*Reader shards per large table*、*Source-load throttle (max Threads_running)*。その上に通知 *Batches in flight are capped at 2 per key range (at least 4 per table or part) and 128 per run* が表示されます。
  - **CDC**: *Sink compute (MCU)*。
  - **Validation**: *Tables in parallel*。
- **Activity log** タブ — 1 つのアクティビティ/監査ログに関するすべてを 1 か所に: アプリの **ログレベル**（DEBUG / INFO）設定、**「Mirror to CloudWatch Logs」** の切り替え（ログをコンテナの stdout にもストリーミング → ECS では CloudWatch に転送され、タスク置換後も残る永続コピーを確保）、そしてセッションのアクティビティログの**ダウンロード**（AI DBA が読むのと同じフィード）。

ダイアログでの変更は**再起動で元に戻ります**。永続化するには、対応する `DSQL_MIGRATOR_*` 環境変数（§7.2 の一覧）を設定してください。
