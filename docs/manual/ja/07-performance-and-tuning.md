## 7.1 この設計の理由 (技術的な根拠)

### バッチ単位ではなくステートメント単位の OCC リトライ

Aurora DSQL は **ロックフリー (lock-free)** です。行ロックをまったく取得せず、書き込み競合を **コミット時点** で
検出して `SQLSTATE 40001` (直列化失敗 — `OC000` データ競合、または `OC001` スキーマ競合) を返します。競合に
敗れたトランザクションは **再実行** しなければならず、AWS は OCC 環境ではアプリケーションがロックベースの DB よりも
このロジックを「**より頻繁に**」通す必要があると明記しています。

標準的な JDBC シンクは `40001` に対して **バッチ全体** をリトライします。並列度が限定された TB 規模では、これは
誤った単位です。約 3000 行すべてを再送信すると、競合しなかった 99% 超の行についても読み取り/書き込み作業を
再度支払うことになり、さらにトランザクションがまたがるキー範囲が広いほど、リトライがコミットされる前に *別の* ワーカーが
その範囲に触れる確率が高まります — こうして負荷の高いロードはライブロックに向かっていきます。本ツールは
**ステートメント単位** でリトライします。競合した `INSERT … ON CONFLICT` だけを再実行するので、各競合はローカルで
範囲が限定されます。これこそが、標準的な JDBC シンクではなくカスタム DSQL シンクコネクタが存在する理由です
([第 4 章 §4.1](04-cdc-and-dsql-constraints.md#41-パイプライン) を参照)。

### プライマリキー戦略 — ホットパーティションの回避

DSQL は **プライマリキーによってストレージをパーティショニングし分散** します。ドキュメントは明確です。
**「ランダムなプライマリキーを選択してください… 単一キーへの競合を増やすパターンは避けてください。」** MySQL の
`AUTO_INCREMENT` PK は単調増加するため、すべての挿入が同じ「最も右側」のキー範囲を狙います。その結果、高スループットの
ロード中はすべてのワーカーが 1 つのパーティションに収束し、OCC 競合率が急増して、**行が論理的に競合していなくても**
書き込みのホットスポットが生じます。

本ツールは、これを **Evaluation** で明らかにし (`AUTO_INCREMENT` → `MANUAL`)、**Schema Conversion** で PK 戦略を
提供します — 整数 PK を維持する、**UUID** に変換する、または **キャッシュを備えた identity カラム** を使う — ので、
書き込みをキー範囲全体に分散できます。これは、同一エンジン (MySQL→MySQL) のマイグレーションでは決して考える必要のない、
DSQL 特有の関心事です。

#### 複合キーオプション — サーバー側の壁を動かせる唯一のレバー

このオプションが存在する理由: in-VPC での実測では、大きなテーブルの Full Load は **クライアント** をどれだけチューニングしてもほぼ同じスループットの頭打ちに達しました — 読み取り先行 prefetch キュー、PK 範囲による読み取りのシャーディング、バッチサイズ / 書き込み並列度の増加は、それぞれスループットを ~0% しか改善しませんでした。壁はクライアント側ではありませんでした。DSQL の `CommitLatency` は健全な ~50 ms p50 を保っていましたが、定期的なロングテールで **数秒(p99)から数十秒(max)** に急騰し、一方で OCC 競合率はほぼゼロに留まっていました。このロングテールは書き込み**ホットパーティション**のシグネチャです。単調増加する `AUTO_INCREMENT` キーでは、すべての挿入が同じ「最も右側」のキー範囲に集中するため、行が論理的に競合していなくても 1 つのパーティションが書き込みを直列化してしまいます。ホットパーティションは*サーバー側*の制限であるため、書き込みをパーティション間に分散させる変更のみがそれを解決でき、複合キーがまさにその変更です。

そこで Schema Conversion は 4 つ目の**テーブルごとの**戦略を提供しています。テーブルのターゲット主キーを、あなたが選んだ高カーディナリティの列を元のキーの先頭に追加した**複合キー** — 例えば `(id)` の代わりに `(customer_id, id)` — に切り替えるものです。DSQL は主キー順に行を格納するため、先頭に `customer_id` を置くことで、挿入を単一の最右端パーティションに集中させるのではなく多数のキー範囲(顧客ごとに 1 つ)に分散させます。ポイントは以下のとおりです。

- **ソースの MySQL スキーマは一切変更されません** — 変更されるのは DSQL のターゲットキーのみです。これはターゲット側のマイグレーション上の決定であり、MySQL に押し戻すスキーマ再設計ではありません。
- **元のキーの一意性は保持されます。** ツールは複合 PK と並行して元のキーに対して `CREATE UNIQUE INDEX ASYNC` を発行するため、元のキーによる参照や制約は引き続き有効です。
- **ツールが選択内容を検証します。** 先頭列は `NOT NULL` であること、既存のキーの一部でないこと、複合キーが ≤ 8 列かつ ≤ 1 KiB の範囲に収まること — これらを適用前に DSQL のキー制限に照らして検証し、選択時に影響を明示します。**カットオーバー後、アプリケーションのクエリ・JOIN・アップサートは新しい複合キーを使用しなければならず、先頭列は不変でなければなりません**(DSQL の主キーはインプレース更新ができないため)。
- **Full Load と CDC の両方で対応します。** Full Load の冪等な `INSERT ... ON CONFLICT` はターゲットの複合キーをキーとして使用し、CDC はコネクターやプラグインの変更が**一切不要**です — Debezium ソースが(`message.key.columns` 経由で)リキーされることで各変更レコードのキーがターゲットの複合キーに一致し、シンクのアップサート/削除はそのまま適用されます。

このオプションを使うのは、テーブルの書き込みが明らかにホットパーティション化されている場合(低 OCC かつ負荷下での `CommitLatency` ロングテール)**かつ**自然な高カーディナリティのグルーピング列がある場合です。負荷のボトルネックが他のもの — クライアント CPU やホットパーティションではない書き込みラウンドトリップレイテンシ — であれば、複合キーは何も得られません。動かせるサーバー側の壁がないからです。まず計測してください(§7.5 参照)。

### DSQL のトランザクション上限に合わせたバッチロード

DSQL はトランザクションごとにハードな上限を強制します。**≤ 3000 行**、**変更データ ≤ 10 MiB**、**≤ 5 分**、
トランザクションあたり DDL は 1 つです。ローダーは **≤ 3000 行** と **8 MiB** のバイト予算 (10 MiB 上限の下に
マージンを取ったもの) でバッチ化し、さらに 65,535 のバインドパラメータ上限によってクランプされます。これにより
2 つの落とし穴を回避します。

- **行単位** のローダーは、*すべての行* について DSQL のトランザクションごとのオーバーヘッド (および書き込みごとの
  DPU 最小値) を支払います — バッチにまたがって償却するより何倍も高価です。
- **テーブル全体を 1 トランザクションに** 入れるローダーは、そもそも **成功できません** — 3000 行の上限 (および
  大きなテーブルでは 5 分の上限) に達して、そのまま失敗します。

### ロード *後* に非同期でインデックスを構築

DSQL は **ノンブロッキング** なインデックス構築のために `CREATE INDEX ASYNC` を提供します。本ツールはデータを
**先に** ロードし、その後に `CREATE INDEX ASYNC` (トランザクションあたり DDL 1 つ) でセカンダリインデックスを
構築します。ロード中にインデックスを構築すると、すべての `INSERT` がセカンダリインデックスの各エントリの書き込みコストも
支払うことになり (カットオーバー前に後続の CDC 変更が上書きする行についても)、さらにすべての書き込みに一意性の
読み取りが追加されます。後回しにすれば、安定したデータセットの上でそのコストを一度だけ支払います。

### コピーにはバルクローダー、カットオーバーにはストリーミング CDC

DSQL はシェアードナッシングかつサーバーレスであり、ターゲットにできる PostgreSQL の論理レプリケーションスロットが
存在しません。汎用ツールの「full load」は内部的には JDBC の `INSERT` であり、DSQL 特有の OCC 処理は **ありません**。
本ツールの専用ローダーは、keyset ストリーミング (再開可能、メモリ有界)、DSQL 上限を意識したバッチ化、ステートメント
単位の OCC リトライ、そして PK リマッピングを 1 つの経路にまとめています。カットオーバーには、**Debezium → MSK
→ カスタムシンク** がソースの binlog と適用を分離します。Kafka が変更を耐久性をもってバッファリングするため、シンクは
OCC リトライのバースト中に遅れても、イベントを失ったりソースの binlog ローテーションを止めたりすること **なく** 済みます。

### 書き込みプールに先行して読み込む (bounded prefetch キュー)

1 つのソーステーブルは **1 本の** MySQL 接続からストリーミングされます。次の keyset ページの
取得には次の `SELECT … WHERE pk > :last LIMIT :page` と行ごとの型変換が必要です。この読み込みが
書き込みをディスパッチするのと同じスレッドでインラインに走ると、ページ *N+1* の読み込みはページ
*N* のバッチが送信された **後** にしか始まりません — 読み書きが直列化され、各読み込みの間、有界の
書き込みプールが遊んでしまいます。ローダーは代わりに **専用のリーダースレッド** が **bounded
キュー**（深さ ≈ 書き込み並列度の 2 倍）を満たし、ページ *N* の `INSERT … ON CONFLICT` バッチが
まだ排出中の **間に** ページ *N+1* を読み込みます。上限がストリーミングのメモリ保証を維持し
（キューが満杯になるとリーダーが停止 — 無制限に先行できない）、ロード順序は不変です（バッチは
依然として固定 PK 範囲にマッピングされ、stop/retry は決定的）。

このオーバーラップは、実際の移行が走る場所 — **in-VPC、十分なタスク CPU** — で最も効果を発揮
します。リーダーが背後に隠せる書き込み側（DSQL へのネットワーク往復、すでに並列で発行済み）が
そこで支配的だからです。in-VPC 4 vCPU の実測ではキューを無効にした場合より **約 19% 高速** でした。
既定で有効で、計測用の seam（`DSQL_MIGRATOR_FULL_LOAD_PREFETCH=0`）で無効化すると pre-prefetch
経路を再現して A/B ベンチマークができます。**CPU が不足した** タスク（§7.2）や、読み込みがクリティカル
パスにない **高 RTT** リンクでは効果が 0 に近づきます — だからこそツールはこの最適化単体ではなく
十分な CPU に依拠します。

### 長時間実行の CDC における短命な IAM トークンの更新

DSQL は **IAM トークン認証のみ** (静的パスワードなし) を使い、トークンは **短命** (約 15 分) で、**接続は 60 分後に
タイムアウト** します。トークンを 1 つキャッシュした長時間実行の CDC シンクは、プールからの追い出し (eviction) や
60 分のタイムアウトの後に *再接続* に失敗します — ネットワークエラーのように見えて、実際は期限切れのトークンが原因の
失敗です。カスタムシンクは **新しい接続ごとに新しいトークン** を発行 (15 分の TTL、2 分の更新マージン) するため、
数時間に及ぶ CDC が認証で止まることはありません。

## 7.2 並列度のチューニング

4 つのマイグレーションフェーズはすべて、妥当な有界のデフォルト値で実行されます。大きなハードウェアでスループットを
上げたい場合は引き上げ、忙しいソースを保護したい場合は引き下げられます。**フェーズごとにチューニング方法が異なります** —
Full Load と Validation はアプリの環境変数で、CDC は CloudFormation パラメータで設定します。

### Full Load

| 設定 (env var) | デフォルト | 上限 | 効果 |
|---|---|---|---|
| `DSQL_MIGRATOR_FULL_LOAD_TABLE_PARALLELISM` | 4 | ≤ 16 | 同時にロードするテーブル数。 |
| `DSQL_MIGRATOR_FULL_LOAD_BATCH_PARALLELISM` | 8 | ≤ 32 | テーブルごとに進行中の `INSERT … ON CONFLICT` バッチ数。 |
| `DSQL_MIGRATOR_FULL_LOAD_BATCH_ROWS` | 2000 | ≤ 3000 | バッチ書き込みごとの行数 (DSQL の 3000 行上限でハードキャップ)。 |
| `DSQL_MIGRATOR_FULL_LOAD_PREFETCH` | `1`（有効） | 有効/無効 | 先読み prefetch キュー（§7.1）。**有効のままに** — A/B ベンチマークで pre-prefetch 経路を再現する場合のみ `0`。 |
| `DSQL_MIGRATOR_FULL_LOAD_READER_SHARDS` | `1`（無効） | ≤ 8 | リーダー範囲シャーディング: **大きな単一整数 PK** テーブルの読み込みを K 個の並行リーダーに分割（§7.1）。**既定で無効、有効化する価値はまれ** — 下記の注意参照。 |
| `DSQL_MIGRATOR_FULL_LOAD_SHARD_MIN_ROWS` | 1000000 | — | この推定行数以上のテーブルのみシャーディング。小さいテーブルは常に単一リーダー。 |

> **リーダーシャーディングはいつ効くか? まれ — in-VPC テストでは ~0% だった。** 行ごとの
> 型変換は純粋 Python で GIL を保持するため、K 個のリーダー*スレッド*でも変換スループットは
> ~1 コアを超えられません。スレッドシャーディングはリーダーの I/O 待ちを重ねるだけ（それは
> prefetch が既に行う）で、変換に 2 つ目のコアを追加できません。in-VPC 4vCPU の実測で
> `reader_shards=4` は単一リーダー比 **~0%** で CPU は ~1 コアに張り付きました。その負荷が
> リーダーではなく **DSQL 書き込みラウンドトリップ遅延**に律速されていたためです。run が
> read/convert 飢餓（リーダーが書き込みプールを満たせない）だという*証拠*があるときだけ
> 上げてください。壁が書き込み側なら代わりに **`BATCH_PARALLELISM`** を上げます。ソース
> リーダー総数 = `table_parallelism × reader_shards` で、ソース接続上限保護のため上限が
> かかります。

> **接続クォータのガードレール。** DSQL への同時接続数の合計は
> `table_parallelism × batch_parallelism` におよそ等しくなります (デフォルトは 4 × 8 = 32)。DSQL は
> **クラスターあたり最大 10,000 接続** を許可しますが、**新規接続は 1 秒あたり 100** のみです。したがって
> この積をクォータの範囲内に十分な余裕をもって収め、理由なく両方のノブを最大に設定しないでください。並列度を
> 上げると、ホットなキー範囲での **OCC 衝突率** も上がります — 良い PK 戦略 (上記) とセットで使ってください。

### Validation

| 設定 (env var) | デフォルト | 上限 | 効果 |
|---|---|---|---|
| `DSQL_MIGRATOR_VALIDATE_MAX_WORKERS` | 4 | ≤ 32 | 同時に比較するテーブル数 (それぞれ独自の読み取り専用のソース + ターゲット接続を使用)。`1` = 順次。 |

多すぎる同時スキャンからソースを保護するために 32 に制限しています。

### CDC (データプレーン)

CDC の並列度はアプリの env ではなく、**cdc-stack CloudFormation パラメータ** で設定します (コネクタはアプリではなく
マネージド MSK Connect 上で実行されるため)。

| CloudFormation パラメータ | デフォルト | 効果 |
|---|---|---|
| `SinkTasksMax` | 2 | シンクコネクタの書き込み並列度 (**トピックのパーティション数で上限**)。 |
| `SourceTasksMax` | 1 | Debezium ソースタスク — MySQL はサーバーごとに実質的にシングルタスク。1 のままにしてください。 |
| `ConnectorMcuCount` | 1 | ワーカーあたりの MSK Connect コンピュートユニット (MCU) (1/2/4/8)。 |
| `ConnectorWorkerCount` | 1 | コネクタあたりの MSK Connect ワーカー数。 |
| `SinkBatchMaxRows` | 3000 | シンクの DSQL 書き込みトランザクションあたりの行数 (**3000 を超えないこと**)。 |

CDC のスループットは **MSK パーティション数 × シンクの `tasks.max` × ワーカーの MCU/数** に比例してスケールし、
最終的にはパーティション数によって上限が定まります。ただし負荷がかかったときの実際の上限は、ホットなプライマリキーで
発生する OCC です — ここでも PK 戦略が最も重要です。

### AWS (ECS Fargate) 上でも — はい、これらすべてもそこでチューニングできます

Full Load と Validation のノブは、ごく普通の `DSQL_MIGRATOR_*` **環境変数** であり、アプリが実行時に読み取ります。
Fargate デプロイでは、これらは **ECS タスク定義のコンテナ `environment` ブロック** (テンプレートがすでに
`DSQL_MIGRATOR_LOG_LEVEL` や `/tmp` の状態パスなどを設定しているのと同じ場所) で設定します — 上記のキーを
`deploy/cloudformation.yaml` のコンテナ environment (または独自のタスク定義) に追加して再デプロイしてください。CDC の
ノブは cdc-stack CloudFormation パラメータであり、ツールが cdc-stack をデプロイする際に渡されます。

> **再デプロイせずに実行間で再調整。** これらの Full Load / Validation 値を試行錯誤する際は、サイドバー
> フッターの **Performance tuning** コントロール (Diagnostics の隣) を使ってください。ローダーとバリデータは
> 実行ごとに設定を読み直すため、ここで設定した値は **次の** Full Load / Validation に即座に反映されます —
> タスク定義の編集や再デプロイは不要です。アプリ全体 (単一タスク) に適用され、再起動でデプロイ/起動時の値に
> リセットされるので、再起動をまたいで**永続化**したい値はタスク定義の `environment` に設定し、UI コントロールは
> **実験**用に使ってください。

また、**Fargate タスクの CPU** (`ContainerCpu`) を十分に確保してください — **Full Load は
ネットワークではなく CPU バウンド** です。ソースリーダーが各行の MySQL 型を DSQL 形式へ Python で
（セル単位、GIL 保持）変換するため、スループットは CPU に比例します: payments+orders ロードの実測で
**同一データの 0.5 vCPU (512) デフォルトより 4 vCPU で約 3.8 倍高速** でした。**評価用途は 0.5–1 vCPU**、
**実際の TB 級 Full Load には 2–4 vCPU** を使ってください。単一の大きなテーブルでは ~4 vCPU を超えると
効果が逓減します — リーダーは 1 スレッドで 1 コア付近が上限になるため、次のレバーは vCPU 増ではなく
PK 範囲での読み込みシャーディング（将来の拡張）です。**メモリ** (`ContainerMemory`) はテーブルサイズ
ではなく行バッファの `table_parallelism × batch_parallelism × 約 8 MiB` で有界であり、Fargate の
CPU/メモリの組み合わせ（2 vCPU で ≥ 4 GiB、4 vCPU で ≥ 8 GiB）が既にこれをカバーします。

> **ローカル実行** も同じ環境変数を読み取ります — `mysql-dsql-migrator ui` を起動する前に、シェルまたは `.env` に
> 設定してください。

## 7.3 ソースへの負荷を最小化する

Full Load は本番ソースを読み取るため、自然な懸念が生まれます: **「多数のテーブルを一度にロードすると重い読み取りに
なるが、ソースに影響しないか?」** 設計自体がその読み取りをすでに軽く保っています(keyset ストリーミング、`OFFSET`
の再スキャンなし、テーブルごとに一度に ~1000 行のページ 1 つだけを in-flight、グローバルロックなし、`COUNT(*)` の
代わりにスキャン不要の `information_schema` 推定値、そして暗黙のバックプレッシャー — 現在のページがロードされてから
次のページを読む)。残る管理対象は **同時読み取り圧力** であり、これはほぼ完全に **1 つのレバー** で決まります。

### 唯一のレバー: テーブル並列度

`DSQL_MIGRATOR_FULL_LOAD_TABLE_PARALLELISM`(デフォルト **4**、最大 **16**)は *ソースから同時に何個の
テーブルを読むか* — 同時テーブルごとにソースのストリーミング接続 1 つ。同時読み取り圧力のダイヤルです。
`BATCH_PARALLELISM`・`BATCH_ROWS` は **DSQL 書き込み** 圧力であってソース読み取り負荷ではないため、DSQL が
ボトルネックでない限りそのままにしてください。(ソース読み取りの **ページサイズは 1000 行で固定** されており調整
不可 — ソース読み取りのスロットルはテーブル並列度が唯一です。)

> サイドバーの **Performance tuning** コントロールで実行間に試すか、永続化するには環境変数で設定します(§7.2)。

### 控えめに始め、観察しながらチューニング

並列度を **スループットのダイヤルではなくスロットル** として扱ってください — テーブル数ではなく、測定された余裕に
合わせて上げます:

1. **低く始める(2〜4)** — 大きなインスタンスでも。遅く終わる方が、本番のレイテンシ障害を引き起こすよりはるかに安価です。
2. **ソースを観察** — 瞬間的なスパイクではなく 5〜10 分の持続的なウィンドウで。
3. **明確な余裕があるときだけ小刻みに上げ**、再観察。(並列度は実行ごとに 1 回読まれるため、変更は **次の** 実行から適用)

**観察すべきシグナル**(Amazon RDS/Aurora — CloudWatch + Performance Insights):

- **上げてよいシグナル:** `CPUUtilization` が線のはるか下、`ReadIOPS` が上がっても `ReadLatency` が平坦、
  `DiskQueueDepth` が低い、`BurstBalance` / `EBSIOBalance%` / `CPUCreditBalance` が 100% 付近、Aurora
  `BufferCacheHitRatio` が安定(~99%)。
- **今すぐ下げるシグナル:** `CPUUtilization` が持続的に > ~85〜90%;`ReadLatency` が IOPS 頭打ちの中で 2〜5 倍に
  上昇;いずれかの burst/credit balance が **0 に向かって低下**(0 になる *前に* スロットル — 回復が遅い);
  `FreeableMemory` がほぼゼロ / `SwapUsage`;Aurora `BufferCacheHitRatio` の低下(コールドスキャンが本番の hot
  page を追い出している);そして何より **アプリケーション自身のクエリレイテンシの上昇** — インスタンス指標に
  関係なく最終的な back-off トリガー。

> [!note] 組み込みのレートリミッターなし
> このツールには **スループット/QPS 制限がありません** — ソース読み取り圧力はテーブル並列度に線形比例します。レバーを
> 下げることが制御手段です。バルクロードは **オフピーク** にスケジュールし、インスタンスのバックアップ/メンテナンス
> ウィンドウと重ならないようにしてください(スナップショット + フルスキャンの同時実行は gp2 `BurstBalance` にとって
> 最悪のケースです)。

### 開始前の余裕チェックリスト

代表的なピークで以下をベースライン化し、ロードを追加する余裕があるか確認してください: **CPU** の余裕;**ストレージ**
— gp2 `BurstBalance`(持続スキャンがこれを 0 まで消費するとベースライン IOPS に崩落 — 本番を害する最も一般的な
経路)、および `ReadIOPS`/`ReadThroughput`/`ReadLatency`/`DiskQueueDepth`(Aurora: `VolumeReadIOPS`);
**バッファプール** `BufferCacheHitRatio`;**接続** `DatabaseConnections` vs `max_connections`(16-way + アプリ
プールが余裕を持って上限以下);**空き容量/メモリ**。ビジーな RDS ソースでは、gp3 + 余裕のある IOPS がフルスキャンで
最も頻繁に足を引っ張る gp2 バースト崖を取り除きます。

### 書き込みの多いソースでの大きなテーブル

各テーブルの読み取りは `REPEATABLE READ` スナップショット内で実行され、**そのテーブルの読み取り中ずっと** 開いた
ままです。書き込みの多いソースでは、これが InnoDB の undo 履歴(**History List Length**)のパージを妨げ —
undo/ディスクの増加と読み取りの遅延 — 16 テーブルが in-flight の場合、**最も古い** read view がパージの地平を
決めます。緩和策: 並列度を下げる(開いた read view を減らす);**最大のテーブルを PK 範囲で分割** し、別々の短い
実行にする(ページサイズのノブがないため、個々のスナップショットを短くするにはテーブルセットを分割);History List
Length を監視し、開始前に空き容量の余裕を確保して undo の増加が storage-full を引き起こさないようにする。

### リードレプリカから読むのはどうか?

Full Load を **RDS リードレプリカ / Aurora リーダーエンドポイント** に向けると、スキャン IOPS・CPU・バッファプール
churn がすべてプライマリから外れます — 本番を保護する最も強力な方法で、並列度もより強く押せます。

- ✅ **Full Load のみの移行: リードレプリカは良い選択肢です。** ローダーは一貫スナップショット内で読み取り専用の
  keyset `SELECT` のみを行い、CDC がオフの場合、watermark はキャプチャされるだけで使われません。(レプリカラグにより
  スナップショットがやや過去の時点を反映するのは正常です。)
- ⛔ **CDC も実行する場合は、レプリカから読まないでください — プライマリ(ライター)を使ってください。** このツールは
  CDC ハンドオフの **watermark**(binlog ファイル/位置、GTID、`server_uuid`)を接続したソースからキャプチャし、
  CDC コネクターも同じホストからストリーミングします。レプリカの binlog 座標はプライマリとは **別の名前空間** にあり、
  RDS レプリカは binlog が **無効または未保持** の場合が多いため — レプリカ由来の watermark は静かに **CDC データ
  ギャップ** を生む可能性があります(スナップショット時点と CDC 開始の間の変更が失われる)。Full Load + CDC の移行では
  **プライマリ/ライター** に接続し、それを単一のソースとして維持し、**binlog リテンションを Full Load 全体より長く**
  設定してください(`CALL mysql.rds_set_configuration('binlog retention hours', N)`)。

> [!tip] ビジーな本番ソースへのクイック推奨
> **Full Load のみ:** **リードレプリカ** から読む(gp3、必要ならウィンドウ中に up-size);並列度を 4〜8 で始め、
> 明確な余裕があればランプ。**Full Load + CDC:** **プライマリ/ライター** から読む(レプリカ禁止)、並列度を **2〜4**
> で始め、明確な余裕があるときだけランプ、**オフピーク** 実行、binlog リテンションをロードより長く。いずれの場合も、
> 最大のテーブル数個は PK 範囲の実行に分割してください。

## 7.4 個々のクエリのチューニング

上記の並列度のノブに加えて、Aurora DSQL の分散実行モデルに合わせて個々のクエリをチューニングできます — そこでは
プライマリキーが *まさに* テーブルであり、フィルタのプッシュダウンがコストを左右し、単位は (PostgreSQL の `cost=` では
なく) **DPU** です。オプションの **Query Playground** は MySQL クエリを変換し、`EXPLAIN` / `EXPLAIN ANALYZE` で
読み取り専用でプローブし、そして AI 支援をオンにすると **AI DBA** が DSQL の効率のためにそれを書き換え、書き換えを
再テストして DPU の改善を証明します。

> 完全なワークフローについては [第 9 章 — クエリ検証と AI DBA](09-query-validation.md) を参照してください。

## 7.5 実測例 — §7.1 と §7.2 を裏付ける 1 回の実行

以下は、上記の設計上の根拠が実際に観測されるかどうかを確認するために、ライブインフラで 1 回実行したものです。
**パフォーマンスの仕様や保証ではなく、手法を示す例** として読んでください — `scripts/measure_performance.py` を使えば
誰でも自分の環境で再現できます。

> [!note] これらの数値が得られた条件
> RDS MySQL 8.0.42 ソース + Aurora DSQL ターゲット + MSK、`us-east-1`、単一の実行。**ハードウェア (ソースの
> RDS クラス、Fargate/ローカルの CPU とメモリ、DSQL のウォーム状態、ネットワーク RTT) は固定していない** ため、
> 絶対的なスループットとラグは環境依存であり、別の環境では異なります。またこの実行は `AUTO_INCREMENT` の整数 PK
> スキーマ — §7.1 で説明した **ホットパーティションの最悪ケース** — を使用しており、一方でこの章が推奨する
> **UUID / キャッシュ付き identity PK** は競合を下げます。あなたの数値は異なるでしょう。

**Full Load — 並列度を上げると、スループットよりも先に競合が上がる (§7.2 のガードレール)。** テーブルとバッチの
両方の並列度を 2 倍に (4×8 = 32 → 8×16 = 128 接続) すると、スループットの向上は **わずか約 +5%** にとどまった一方で、
**少なくとも 1 回のリトライが発生したバッチの割合** は約 3 分の 1 増加しました (約 9.6% → 12.8%)。論理的に競合しない
行であっても、書き込みは単調増加 PK の同じキー範囲に収束します — まさに §7.1 のホットパーティション効果です。教訓:
**並列度をやみくもに上げる前に、PK 戦略を修正してください。**

**CDC レプリケーションラグ — デフォルトのサイジングにおけるレイテンシの下限。** ソースのコミット → DSQL 上での
可視化は、持続的な負荷ではおよそ p50 0.8 秒 / p95 1.3 秒、バースト負荷では p50 0.5 秒 / p95 0.7 秒と計測されました。
これは **デフォルトの CDC サイジング (MCU=1、ワーカー 1、単一カラムのテーブル) における良好なケースの下限** であり、
多数のテーブルや高い変更率では大きくなり得ます。スループットが必要なときは、§7.2 の CDC パラメータでスケールしてください。

> **再現する:** `scripts/measure_performance.py full-load` (スループット + 競合) と
> `scripts/measure_performance.py cdc-lag` (レプリケーションラグ) を使うと、自分のソース/ターゲットに対して同じ
> メトリクスが得られます。ただし `full-load` はターゲットテーブルを **DROP して再作成** する (`--yes` が必要) ので、
> **非本番のターゲットでのみ** 使用してください。また `cdc-lag` にはアクティブな CDC パイプラインが必要です。
