# 3. Full Load の仕組み

_言語: [English](../en/03-full-load.md) | [한국어](../ko/03-full-load.md) | **日本語**_

> **前へ:** [2. Evaluation と Schema Conversion](02-evaluation-and-schema-conversion.md)
>
> **テーブルや列を移行から外すには** [13. テーブルと列の除外](13-excluding-tables-and-columns.md)を参照してください。除外した列は Aurora DSQL に NULL としてロードされます。

**Full Load** は、ソースデータベース — RDS / Aurora **MySQL** または RDS / Aurora **PostgreSQL** — の
既存の行を Aurora DSQL へコピーする、本ツール独自のバルクコピーです。
これは Debezium のスナップショットでは**ありません** — データをストリーミングしながら DSQL の制約を守る、
専用に作られたローダーです。テーブルを選択したあと、**Data Migration** ステップで実行します。

> **メンタルモデル:** ローダーはソースを PK 順に 1 ページずつ読み取り、小さく、冪等で、リトライ可能な
> バッチとして DSQL に書き込みます — テーブルがどれだけ大きくてもメモリは一定に保たれ、中断されても
> 再開できます。

## 3.1 全体像

```
Source (MySQL / PostgreSQL)          Aurora DSQL
  │  keyset page (PK > last, LIMIT)      ▲  idempotent batched INSERT
  │  streaming server-side cursor        │  (≤3000 rows, ≤8 MiB, OCC retry)
  └──────────►  convert types  ──────────┘
       (read-only, consistent snapshot)
```

1. **ウォーターマークをキャプチャ**します(ソースの履歴における一貫した地点)。
2. 主キーのページ単位でソースから**行をストリーミング抽出**します。
3. 流れてくる各値を DSQL の形式へ**変換**します。
4. 一定サイズで冪等なバッチとして、DSQL へ並行に**ロード**します。
5. そのあとで二次**インデックス**を構築します。

ソースは一貫したスナップショットの中で**読み取り専用**として読み取られ、ローダーがそれを変更することは
決してありません。MySQL ソース — そして PostgreSQL の Full Load のみのマイグレーション — に書き込むことは
決してありません。唯一の例外は **PostgreSQL CDC** です。ウォーターマークの地点(§3.5)で、ツールは論理
レプリケーションスロットと、移行対象テーブルだけに厳密にスコープされた publication(`FOR TABLE ONLY`: テー
ブルの継承の子テーブルは一緒に追加されず — Full Load もそのテーブル自身の行だけを読みます(`FROM ONLY`。
[§6.1](06-limitations.md#61-aurora-dsql-の機能制限スキーマがこれらに適合している必要があります) を参照) —
パーティション化されたテーブルのパーティションは追加されます)を作成し、teardown 時に削除します。また、再
キー化したテーブルに `REPLICA IDENTITY FULL` を設定し、publication の
`publish_via_partition_root` を修正します。修正するのは、Full Load では再利用する publication(スロットを作成
する前に)、Start CDC のたび(publication がまだない場合 — 初回の CDC only の Start や、Full Load のみの実行の
後の Start など — は、その設定で空の publication を作成し、コネクタがテーブルを追加します)、そして Full Load
の後に選択したテーブルを追加する前です。そのようなテーブル(Full load + CDC、CDC を開始する前)は、コピーの
直前に publication に追加され、ツールはその時点で開いていたトランザクションを待つためにトランザクション ID を
1 つ取得します。いずれも autocommit で、小さな allowlist に制限され、監査されます。これらが、ツールがいずれの
ソースに対して行う唯一の書き込みです。ウォーターマークの地点で publication
を作成する(またはテーブルを追加する)前に、追加するすべてのテーブルに使用可能な
`REPLICA IDENTITY` があること(さらに PostgreSQL 18 では、再キー化したテーブルに生成列がないこと — そのテーブ
ルに必要な `FULL` が壊れるため)を確認し、ない場合はソースで何も変更する前に実行を止めて、そのテーブルと、原因
に応じた修正方法を示します。同じ名前のレプリケーションスロットが使用中、別のデータベースに属している、または論
理 `pgoutput` スロットでない場合(たとえば同じ CDC スタック名を使う別のマイグレーションのスロット)も、書き込み
の前に止まります。このデータベースの非アクティブなスロットは、このスタックの以前のスロットとみなして置き換えま
す。選択したテーブルにパーティション化されたテーブルがあるのに Full Load での `publish_via_partition_root`
の修正が失敗した場合は、スロットを作成する前に実行を止め、publication の所有者として実行する
`ALTER PUBLICATION` 文を示します。Start CDC では、修正が失敗しても、セッションにソースのパスワードがなく
修正を実行できなくても Start は止まらず、そのログが同じ文を示します。
Full Load の後に選択したテーブルも、追加する前に同じ確認を受けます。ない場合はそのテーブルはロードされず、
その行に理由が表示されます([13.7](13-excluding-tables-and-columns.md))。

## 3.2 ストリーミングエクスポート — テーブルサイズによらず一定のメモリ

ローダーは `OFFSET` ではなく、**主キーによる keyset ページネーション**で読み取ります。

```sql
SELECT <cols> FROM <table>
WHERE pk > :last           -- composite PKs: the cursor the source's PK index serves (below)
ORDER BY pk
LIMIT :batch_size          -- DEFAULT_BATCH_SIZE = 5000
```

各ページの最後の行まで `:last` を進めていき、短いページが終端を知らせるまで繰り返します。このクエリは
単一の repeatable-read スナップショットトランザクション(MySQL: InnoDB の `START TRANSACTION WITH
CONSISTENT SNAPSHOT`、PostgreSQL: `REPEATABLE READ` トランザクション)の中で、**サーバーサイド /
ストリーミングカーソル**として実行されます。したがって次のようになります。

- テーブル全体が**RAM にロードされることは決してなく** — メモリは 1 ページ分に一定に保たれます。
- 稼働中のソースが変化し続けても、読み取りは**単一の一貫したスナップショット**になります（分割して
  読む MySQL テーブルは部分ごとに 1 つのスナップショット、[§3.8](#38-マルチプロセス並列化gil-バイパス)）。

**MySQL はソース自体の設定にかかわらず `REPEATABLE READ` で読み取ります。** ツールが開くすべての MySQL
ソースセッションは、最初に `SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ` を実行します。セッションの
設定なので、サーバーの `transaction_isolation` はそのままで、権限も必要ありません。MySQL は `REPEATABLE READ`
未満では `WITH CONSISTENT SNAPSHOT` を無視する(warning 138)ため、これがなければ `READ-COMMITTED` に設定された
ソースでは各ページが実行時点でコミット済みの行を読み、読み取り中にキーが変わった行が 2 回コピーされたり、
まったくコピーされなかったりすることがあります。ウォーターマークの取得と Validation のテーブルごとの
読み取りも同じ種類のスナップショットを開きます。そのため、そのようなソースでも各テーブルの読み取りは終わるまで
InnoDB の read view を 1 つ保持します — `REPEATABLE READ` のソースと同じです。書き込みの多いソースでは、
大きなテーブルを読み取る間 History List Length が増えます
([§7.3](07-performance-and-tuning.md#書き込みの多いソースでの大きなテーブル))。

**カーソルの書き方。** カーソルは主キーインデックスの順序に従い、そのインデックスが範囲として処理できる形で
書かれます。MySQL の複合キーでは明示的な辞書式 OR 展開
`(k0 > :last_0) OR (k0 = :last_0 AND k1 > :last_1) OR …` を使います(MySQL 5.7 は行値比較を
インデックスで処理できません)。PostgreSQL では行値比較 `(k0, k1, …) > (:last_0, :last_1, …)` を使い、
これは主キーと各パーティションの主キーに対するインデックス条件になります(PostgreSQL では OR 展開は
フィルターにすぎず、ページごとにキーを先頭から読み直すことになります)。

MySQL の `ENUM` / `SET` のキー列は、ラベルではなく MySQL がソートする順序 — メンバーのインデックス
またはビットマスク — でページを進めます。

- **`ENUM` 列で始まる**キーは、宣言順にメンバーを 1 つずつ読みます。各ページは `col = <メンバー>`、
  またはそのメンバーかつカーソルより後のキーの残りで、ページが短く返ると次のメンバーに進みます —
  最後のメンバーの短いページだけがテーブルの読み取りを終えます。主キーがテーブルのすべての列を含む
  場合でも、すべてのページがインデックスのルックアップまたは範囲になります。
- 後ろの位置の `ENUM` キー列はカーソルのメンバーの後に宣言されたメンバー(`col IN (…)`)で、`SET`
  キー列はビットマスク(`CAST(col AS UNSIGNED) > n`、64 個のメンバーすべてで正確)でページを進めます。
  ビットマスクはインデックスでは処理できないため、`SET` 列で始まるキーはページごとにキーを先頭から
  読み直します。
- メンバーは各テーブルの読み取りの開始時にソースのカタログ(`information_schema.COLUMNS`)から
  読むため、Evaluation の後に追加された、または順序が変わったメンバーも正しい順序で読まれます。
  ターゲットの `CHECK` には Evaluation が見たメンバーが残っているため、メンバーを追加した後は
  Evaluation と Schema Conversion を再実行してください。
- メンバーを正確に読めないとき(たとえば NUL を含むメンバーや、二重に宣言されたメンバー)、キー値が
  そのメンバーのいずれでもないとき、またはソースが 2 つのメンバーを等しいと比較し(たとえば大文字と
  小文字を区別しない照合順序)、ページが読み取りの通過済みの行を返すとき、読み取りは行が欠けたまま
  ロードする代わりにテーブルを停止します。

**後ろに別のキー列が続く** 単精度の MySQL `FLOAT` キー列は、1 ページを超えるテーブルの読み取りを
停止します。MySQL はその値を有効数字 6 桁に丸めて返し、その値は格納された float と等しいと比較されない
ため、その上のカーソルは同じ値の残りの行を黙って飛ばしてしまいます。ソースで列を `DOUBLE` または
`DECIMAL` に変更するか、テーブルに別の主キーを与えてから、そのテーブルを再試行してください。最後の
(または唯一の)キー列であれば通常どおり読み取ります。有効数字 6 桁より後ろだけが異なる 2 つのキーは
同じ値として読み取られ、Aurora DSQL に両方を格納することはできません(Validation が行数の差を示します)。
また、MySQL が格納値より小さく返す値でページが終わると、次のページはその値として読み取られる行
(ロード済みの行か、Aurora DSQL が同じキーとして保持する行)から始まり、読み取りはそれらの行を飛ばします
(`ENUM` または `SET` のキー列もある場合は、照合順序が等しいとみなすメンバーの場合と同様に、代わりにテーブルを
停止します)。
`TIME` キー列(負の値を含む)と `BIT` キー列は、ほかの列と同様にキーの順に読み取ります。カーソルはそれらを
MySQL が正確に比較する期間のテキストと整数としてバインドします。PostgreSQL の `real` キー列も同様です。
カーソルはその値をテキストとしてバインドし、PostgreSQL はそれを格納された `real` の値として読み取ります。

**主キーが必須です。** PK を持たないテーブルは keyset ページネーションできないため拒否されます(DSQL も
PK を要求するため、Evaluation でも `UNSUPPORTED` としてフラグ付けされます)。単一列 PK と複合 PK の
どちらもサポートされます — そして複合キーは単に許容されるだけでなく、単調増加するキーによる書き込みホットパーティションに対してツールが推奨する解決策です([第 7 章 §7.1](07-performance-and-tuning.md#プライマリキー戦略--ホットパーティションの回避) 参照)。

> **ビジーな本番ソースへの読み取り負荷が心配ですか?** 多数のテーブルを一度にロードしても 1 つのレバー
> (テーブル並列度)で制限され、ソースを健全に保つ具体的な手順があります —
> [第 7 章 §7.3 — ソースへの負荷を最小化する](07-performance-and-tuning.md#73-ソースへの負荷を最小化する)を参照。

## 3.3 その場でのタイプ変換

行がストリーミングされる際、各値は DSQL が保存する形式へ変換されます。これは Schema Conversion の
マッピングを踏襲しているため(列の型と値が食い違いません)。**MySQL ソース**が生成する例をいくつか
挙げます。

- `TINYINT(1)` → DSQL の **boolean**(`0/1` → `false/true`)。
- `BIT(n)` → 整数(ソースのバイト列からデコード)。
- `DATETIME` → UTC に正規化された `timestamp`、`TIMESTAMP` → `timestamptz`。
- `BLOB`/`BINARY`/`VARBINARY` 系 → `bytea`。

**PostgreSQL ソース**では、Full Load 中に MySQL 方式の値変換は**行われません**。両端がともに
PostgreSQL-16 wire(両側とも psycopg)であるため、DSQL がサポートする値はそのまま通過します。PostgreSQL の
型の扱い — 未サポート型は remodel 対象としてフラグ付け、`numeric` の精度クランプ、`DEFAULT`/serial/identity
は出力しない — は、その場での値変換ではなく **Schema Conversion** で行われます。

マッピングの全体(および値あたり 1 MiB 制限のような DSQL 制約の扱い方)は
[第 2 章 §2.3](02-evaluation-and-schema-conversion.md#23-mysql--dsql-の型と制約の処理-リファレンス)と
Schema Conversion ステップにあります。

## 3.4 バッチ化・冪等・並列数を制限したロード

行はそのまま**冪等なバッチ INSERT** へ流れ込み、小さく上限のある DSQL
コネクションプールをまたいで**並行に**ロードされます。ここにあるすべての上限は実際の DSQL 制約であり、
ツールが代わりに処理します。

| 制約 | ローダーの動作 | デフォルト値 / 上限 |
|---|---|---|
| トランザクションあたり ≤ 3000 行 | バッチの行数を制限 | `DEFAULT_BATCH_ROWS = 2000`、ハード上限 `3000` |
| バインドパラメータの上限 | 収まるようにバッチを制限 | `MAX_STATEMENT_PARAMETERS = 65535`(`65535 // columns`) |
| 書き込みトランザクションあたりのサイズ | 幅の広い行を分割 | `MAX_BATCH_BYTES = 8 MiB` |
| 楽観的並行性制御(`40001`) | バックオフ + ジッターでバッチをリトライ — 一時的な接続断と Aurora DSQL の一時的な `XX000`(server unavailable)でも適用 | 最大 20 回 |
| リソース使用量の制限 | 同時実行バッチ数を制限 | テーブルあたり `DEFAULT_PARALLELISM = 8`、同時に `4` テーブル |

**設計上、冪等です。** クリーンなロードは新規作成した空のターゲットへ通常の複数行 `INSERT` で投入し、
データがすでに存在しうる場合(リトライ、または行がすでにあるテーブルへの append)は **「既存はスキップ」**
モードに切り替えます — insert し、既存キーは上書きせずスキップ — そのため再実行しても重複は生じず、**より
新しい CDC 適用済みの行を決して上書きしません**。(DSQL の *複数行* `ON CONFLICT DO NOTHING` は非衝突行を
静かに取りこぼすことが観測されたため、意図的に避けています。) ただし CDC が削除したばかりの行と最初から
なかった行は区別できないため、CDC がターゲットへストリーミングしている間は Full Load は実行されず、Start
CDC は実行中の Full Load を待ちます ([§3.5](#35-ウォーターマーク--cdc-への橋渡し)): そうしないと、テーブル
のコピー中にソースが削除した行が書き戻されます。

**完全なロードの後に identity シーケンスを前進させます。** テーブルのキーをキャッシュ付き identity 列
(`GENERATED BY DEFAULT AS IDENTITY`)に変換した場合、ロード完了時に `ALTER TABLE … RESTART WITH max(pk)+1`
を実行し、**カットオーバー後の最初の insert** が移行済みキーと**衝突しない**ようにします。**完全な(または
ギャップを受容した)ロードでのみ**実行され、部分的/失敗したロードでは実行されません。通常の整数キーは
シーケンスを持たないため触れられません。

**インデックスは最後です。** 二次インデックスは、すべてのデータバッチが成功した**あとで**、それぞれ
`CREATE INDEX ASYNC` として独自の単一 DDL トランザクションで作成されます(DSQL はトランザクションあたり
1 つの DDL を許容し、インデックスを非同期に構築します)。Aurora DSQL が `XX000` ("server unavailable")
を返した、または実行中に接続が切れたインデックスのステートメントも同じようにリトライします。リトライで同じ名前のインデックスが
すでにある場合は、作成済みとは数えません: Aurora DSQL ではインデックス名がスキーマ単位なので、別の
テーブルのインデックスかもしれないためです。Full Load の画面とエラーログには、欠落ではなく
**not confirmed** (未確認) として、先の試行が作成した可能性があるという注記付きで表示されるので、
インデックスを追加する前にターゲットを確認してください。画面の通知が制約の欠落を伝えるのは、`UNIQUE`
インデックスが作成されなかったことが確かな場合だけで、欠落したインデックスと未確認のインデックスが混在する
場合は両方を示します。

## 3.5 ウォーターマーク — CDC への橋渡し

ロードの前に、ツールは**ウォーターマーク**をキャプチャします。これはソースの変更ストリームにおける一貫
した地点で、同じ一貫スナップショットのトランザクションの中で記録されます。どのウォーターマークも
**UTC のスナップショットタイムスタンプ**と、テーブルごとの**概算**行数(スキャンを伴わない
`information_schema` の推定値。単に数えるだけのためにソースをフルスキャンしません)を保持します。エンジン
固有の座標は次のように異なります。

- **MySQL** — **binlog ファイル + 位置**、および **GTID セット**(`@@GLOBAL.gtid_executed`)、
  ソースの **`gtid_mode`**、`server_uuid`。これらは `SHOW BINARY LOG STATUS`(MySQL 8.2+/8.4、
  `SHOW MASTER STATUS` が削除されたバージョン)で読み取り、それ以下(≤ 8.0.x)では `SHOW MASTER STATUS`
  にフォールバックします。`gtid_mode=ON` のソースでは CDC はウォーターマークの GTID セットの次から開始し、
  それ以外ではそのファイル + 位置から開始します。ウォーターマークは位置を読む直前に、移行対象テーブル
  ごとの列定義の短いフィンガープリントも記録するため、Start CDC はそれ以降にテーブルが変更されたかを
  判断できます([第 6 章](06-limitations.md) を参照)。
- **PostgreSQL** — binlog 座標ではなく **WAL LSN**(`Watermark.wal_lsn`)。一貫性の地点で、ツールは
  **publication**(移行対象テーブルに厳密に対する `FOR TABLE`。`FOR ALL TABLES` は決して使いません)と
  `pgoutput` の**論理レプリケーションスロット**を作成し、スロットが返した一貫 LSN を、スロット名・
  publication 名とともに記録します。この LSN が WAL を固定し、ギャップのない `snapshot.mode=never` の
  CDC 引き継ぎを可能にします。PostgreSQL には GTID / `server_uuid` の概念はなく、`SHOW BINARY LOG STATUS`
  もありません — LSN は作成されたスロットから得られます。

このウォーターマークによって、後続の **CDC へのギャップのない引き継ぎ**が可能になります。CDC は
スナップショットが終了したまさにその地点から変更のストリーミングを開始します — ギャップも重複も
ありません([第 4 章](04-cdc-and-dsql-constraints.md)を参照)。CDC の前提条件が満たされない場合 —
MySQL ではバイナリロギングが無効か権限が制限されている場合、PostgreSQL では `wal_level` が `logical` で
ないか、スロット / publication を作成できない場合(レプリケーション権限の不足、または standby エンドポイント)
— 座標は穏当に劣化し、その場合は単に CDC の引き継ぎが受けられなくなるだけです(Full Load は引き続き
動作します)。

> ウォーターマークの行数は**意図的に概算**です(ソースへの負担を抑えるため)。正確な `COUNT(*)` と
> チェックサムは **Validation**([第 5 章](05-validation.md))の役割であり、Full Load の役割では
> ありません。

### 新しい開始位置には新しい CDC トピックが必要です

**新しい** ウォーターマークをキャプチャすることは CDC についての決定でもあるため、CDC スタックが **ストリーミングしたことのある** **Full load + CDC** のマイグレーション — Start の後に停止した、コネクタがそのまま残っている、または CloudFormation が Start をロールバックしたスタック — では、新しいウォーターマークを取る操作はすべて **拒否されます**: **Start Full Load**、**Re-run Full Load**、**Re-run all tables** は無効になり、ページヘッダーの **Run** は何も開始しません。Stop CDC (およびロールバックされた Start) は sink をドレインせずに削除するため、その sink のコンシューマグループは新しいスナップショットより古い変更を再ロードしたテーブルの上に再適用し、その一方でソースは以前の停止位置と新しいスナップショットの間の変更をスキップします — 何も表示されないまま進み、CHECKSUM の検証だけがそれを明らかにします。そこで通知は代わりに方法を示します: **Delete CDC infrastructure** して再デプロイ (新しいスタックは空のトピックで始まります)、次に **Drop & reload** で **Re-run Full Load** (PostgreSQL ではレプリケーションスロットが自身のスナップショット位置に作り直されます)、次に **Start CDC** です。

- **ページヘッダーの Run も同じように制限されます。** Start / Re-run Full Load とまったく同じく新しい開始位置を取るためです。ストリーミングしたことのあるスタックでは何も開始しません: 警告のトーストが同じ方法を示し、ジョブは作成されず、ウォーターマークもキャプチャされず (PostgreSQL ではレプリケーションスロットも置き換えられません)、ステップのステータスと以前の Full Load の記録もそのまま残ります。まだ **ストリーミング中** のスタックもここに含まれます。
- **CDC が動いている間** は、Full Load の操作に自身のゲートが先にかかります: *Stop CDC first (CDC step → Stop CDC), then Delete CDC infrastructure and deploy it again before a new Full Load.* 元の開始位置を維持する **Retry unfinished tables**、**Reload specific tables**、テーブルごとの **Reload** も無効になり、そのいずれかのためにすでに開いている確認ダイアログは確定できません。これらは代わりに、先に Stop CDC してからその操作を実行し、もう一度 Start CDC するよう示します: CDC はその後、停止した位置から続き、ギャップがないのは sink が適用していなかった変更を CDC トピックがまだ保持している間 (MSK での保持期間) だけです。ストリーミング中の sink のそばでのロードはターゲットにない行だけを insert するため、テーブルのコピー中にソースが削除した行が、CDC がその削除を適用した後に Aurora DSQL に届き、そのまま残ることがあります。COUNT か CHECKSUM の検証だけが示す余分な行です。同じ理由で、Start CDC がまだ進行中の間はページヘッダーの **Run** も何も開始せず、Full Load の実行中は Start CDC が待ちます ([§4.3](04-cdc-and-dsql-constraints.md#43-ギャップのない-full-load--cdc-ハンドオフ))。**Start CDC**、**Stop CDC**、**Delete CDC infrastructure** がまだ進行中の間も、Full Load ステップの操作は無効のままですが、示される理由は、先に Stop CDC することではなく、その操作が終わるまで待つことです (CDC ステップに進行状況が表示されます)。このときページヘッダーの **Run** も何も開始せず、ストリーミングしたことのあるスタックでは、待つ代わりに上記の削除と再デプロイの方法を示します。Stop または Delete が終わると Retry や Reload が実行でき、Start で CDC がストリーミングを始めると、再び Stop CDC が先になります。
- **このセッションで CDC の状態をまだ読み取っていない間** (画面を開いた直後やアプリの再起動の直後)、または読み取れなかった場合、新しい開始位置は推測せずに **待ちます**: 通知がそう述べ、CDC ステップの **Re-check CDC state** を示します (読み取りに失敗した場合は、先に AWS のアクセス権を直してください)。
- **新しい開始位置では制限されないもの** (CDC が動いている間は、上のとおりこれらも無効になります): **Retry unfinished tables**、**Reload specific tables**、テーブルごとの **Reload**、**Change & reload** はいずれも **元の** 開始位置を維持するため、CDC は止まったところから続き — Stop CDC 後のあらゆる再起動と同じく、sink が適用していなかった変更を CDC トピックがまだ保持している間だけギャップがありません ([§4.3](04-cdc-and-dsql-constraints.md#43-ギャップのない-full-load--cdc-ハンドオフ)) — 再ロードしたテーブルは収束します。Full Load ステップは **Full load only** と **CDC only** のマイグレーションを制限しませんが、それらに切り替えてもこのゲートは回避できません (次の項目)。
- **Start CDC もより新しい開始位置を拒否します (MySQL)。** MySQL ソースでは、Start CDC は、ストリーミングしたことのある CDC スタックを、マイグレーションの種類にかかわらず、スタックが最後に開始した位置より新しい開始位置へ (または、停止したスタックの最後の Start が開始位置を渡さなかった場合は、どの開始位置へも) 進めることを拒否します: たとえば Full load + CDC から **Full load only** に切り替えた後の Re-run Full Load が取ったウォーターマークや、より後の **Manual** の位置です。開始位置カードと Start CDC カードが *This CDC stack cannot start from a newer start point* とともに方法 — 上記の方法、CDC only では **Delete CDC infrastructure** して再デプロイしてから新しいスタックで **Start CDC** — を示し、Start CDC は無効になります。Start CDC のダイアログ、Start または Retry CDC のクリック、そして何かを変更する前にその時点で読み取ったスタックで判断する Start CDC のジョブ (*Start CDC blocked: This CDC stack has streamed, so Start CDC does not move it forward to a newer start point …*) も拒否します。拒否された Manual の位置は、開始位置を **Automatic** に戻せばストリームが続く場合、そのことも示します。その位置と同じかそれより前の開始位置、または開始位置のない Start はストリームを続け、拒否されません。CloudFormation がロールバックした初回の Start の後は、ロールバックがスタックのパラメータを元に戻すため、パラメータにはその Start が渡した開始位置がもう残っていませんが、スタックの CloudFormation イベントにはまだ残っています (オフセットシーダーのプロパティ): アプリは次の Start を、自分が記録したその位置と比較し、アプリの再起動後 (または別のセッションで行った Start の場合) はそのイベントから読み取ったその位置と比較します。それより後の開始位置は拒否され、同じ開始位置からの再試行は拒否されず、それより前の開始位置は Start CDC をクリックした時点で、またはこのセッションがその位置をまだ読み取っていなかった場合は Start CDC のジョブで拒否されます (*This start point cannot be applied*: そのオフセットはシードされたまま残り、シーダーは巻き戻さないためです)。イベントからもその位置が得られない場合 — たとえばイベントを読み取れない場合や、その Start がオフセットシーダーの Lambda ではなくアプリの中で Kafka をシードした場合 (単一 EC2 ホストはそうします。[§1.4](01-setup.md#14-単一-ec2-ホストで実行する-ソースから)) — は、どの開始位置もその位置と比較できないため、そのスタックでは同じ開始位置も含めてすべての開始位置が同じ方法とともに拒否されます (*This CDC stack's last start point is not known*: *CloudFormation rolled back this stack's last Start, and the start offset that Start offered is no longer known …*)。CDC only の方法は新しいスタックを Full Load のウォーターマークから開始するため、拒否された位置がそのウォーターマーク (Automatic) の場合は、拒否がその方法の条件を付け加えます: その Full Load がターゲットに既にあった行に append した場合は、その Start の前に **Drop & reload** でもう一度実行してください。CDC only には Full Load ステップがないため、その実行の間はマイグレーションの種類を Full load only に切り替え、その後 CDC only に戻します (append はそれらの行をそのまま残し、ウォーターマークからの CDC はその後の変更しか運びません)。無効になった Start のツールチップとジョブのエラーでは、その方法は *Delete CDC infrastructure and deploy it again, then Start CDC (if the Full Load appended to rows already on the target, re-run it choosing 'Drop & reload' first)* と表示されます。新しいスタックではその Start は拒否されず、このセッションが、その Full Load が以前のコピーに append した可能性があることを示していれば、CDC ステップがその Start の前にその条件を示します ([§4.3](04-cdc-and-dsql-constraints.md#43-ギャップのない-full-load--cdc-ハンドオフ))。PostgreSQL にはこの拒否はありません: Start CDC は Full Load のウォーターマークにかかわらずスタック自身のレプリケーションスロットから続け、Full load only の実行はそのスロットに触れないため、スタックの source connector がストリーミングしていれば、CDC は Stop CDC 後のあらゆる再起動と同じく (上記) 停止したところから続きます (そうでなければ Debezium が先に選択したすべてのテーブルをスナップショットします)。
- クリックとジョブの開始の間にスタックがストリーミングを始めた場合は、エンジンがジョブスレッドで何も読み書きする前に拒否します: その実行は *FullLoadRefusedError* と同じ 1 行の理由で失敗として記録されます。

## 3.6 障害はどのように隔離されるか — そして隔離されない 1 つの障害

ここは、2 つの障害挙動が意図的に異なるため、よく理解しておくべき部分です。

### 行単位の隔離(quarantine)(テーブルはロードを継続)

適用時に **DSQL が特定の行を拒否した**場合(SQLSTATE を伴うエラー — 例: DSQL の 1 MiB 上限を超える値、
制約違反)、ローダーはそのテーブルを失敗として扱うことは**ありません**。バッチを問題の 1 行になるまで
二分割していき、その行を**隔離**(quarantine)して(その**主キーと理由のみを記録し、値は決して記録
しません**)、残りをロードします。隔離された行は、ダウンロード可能なエラーログに表示されます。

Aurora DSQL の一時的な状態は拒否ではありません: `40001`、切断された接続、`XX000`("server unavailable")は
バッチ全体をリトライし(§3.4)、リトライを使い切ったバッチは失敗になります — テーブルは
**Retry unfinished tables** で再試行でき、そのために隔離される行はありません。

### テーブル致命(テーブル全体が停止)

値を**ひそかに変えずには書き込めない**場合、エクスポーターは `ValueConversionError` を送出します:

- `boolean` にマッピングされた `TINYINT(1)` が `{0,1}` の範囲外の値(例: `2`)を保持している場合(エクスポート中に
  値が変換される MySQL ソースのみ);
- 両エンジンで、`numeric(p,s)` 列が保持するより小数桁の多い値、または整数列に入る小数。テーブルを読むときに
  1 回、ソース列の実際の型から検出するため、型が一致するテーブルにはコストがかかりません。Step 1 の後でソースの
  型が広げられたか、Schema Conversion でより狭い型を選んだときに起こります。精度なしの PostgreSQL `numeric` を
  精度なしの `numeric` ターゲットに入れる場合は拒否せず(Aurora DSQL の文書化された `numeric(18,6)` 既定値)、
  `numeric` 列に入る `FLOAT`/`DOUBLE` のソース値は確認せず、引き続き丸められます;
- 00:00:00–23:59:59.999999 の範囲外の MySQL `TIME`。

これには **SQLSTATE がなく**(DSQL に問い合わせる前、読み取り / 変換の途中で発生するため)、そのため行単位の
隔離では**なく**、そのテーブルのロードを**明示的に**停止します。これは意図された挙動です — ツールは `2` を
`true` につぶしたり `1.2345` を `1.23` に丸めたりして、あなたのデータをひそかに破損させることを拒否します。
メッセージには列、その型、ルールだけが記され、値は決して記されません。Schema Conversion で値を保持できる型を
列に指定するか(ソースの型が変わった場合は先に Step 1 を再実行してから **Replace** で再適用)、ソースデータを
修正するか列を除外してから、そのテーブルを再試行してください。

> **なぜ「明示的な」失敗が「サイレントな」失敗に勝るのか:** DSQL の `boolean` は `2` を表現できません。
> ツールは、ひそかに誤った値を残すよりも、目に見えて修正可能な失敗を選びます。

### 実行レベルの判定

**いずれか**の行を隔離したテーブルは、**失敗**(未完了)として報告され、その実行は成功として報告されません
— そのため、未完了のロードがクリーンなロードと取り違えられることは決してありません — **ただし「隔離された
行を受容して続行」を明示的に選んだ場合は**、ギャップを認識したうえで実行が完了します(Validation には引き続き
表示)。リトライ可能なテーブル失敗は常にブロックします。ダウンロード可能なエラーログには、どの PK がなぜ
隔離されたかが正確に列挙されます。

## 3.7 再開可能性

中断された Full Load が再開する単位は、PK 範囲ではなく**テーブル**です。

- 完了したテーブルは `DONE` として記録され、そのまま保持されます。
- 停止、クラッシュ、タスクの置き換えの後は、未完了の各テーブルを「既存はスキップ」モード(§3.4)で、または
  **Drop & reload** の場合は先にテーブルを作り直して、**最初からロードし直します**。そのため、終わり近くで
  中断された非常に大きなテーブルも、最初から読み直されます。
- `INSERT ... ON CONFLICT` により、バッチの再実行は冪等になります(重複なし)。

**Retry unfinished tables** の経路は、未完了のテーブルのみを保留(pending)状態にリセットし、
**元のウォーターマークを再利用**し、完了したテーブルはそのまま保持します — したがって、完了したテーブルを
ロードし直したり、CDC の引き継ぎ地点を失ったりすることはありません。

ロード後に選択したテーブル(Full load only ではテーブル集合を変更できます。
[13.7](13-excluding-tables-and-columns.md) を参照)も同じリトライがロードしますが、元のウォーターマークは
そのテーブルを含まないため、CDC の引き継ぎは元の集合に対してのみ有効です。Re-run Full Load が現在の集合に
対して新しいウォーターマークを取得するまで(またはそれ以降に選択したテーブルのチェックを外すまで)、移行タイプは Full load only のまま
です。その再実行は **Drop & reload** で行ってください: CDC はそのウォーターマークから開始しますが、*Append* は
以前のロードが書いた行を、その後のソースの UPDATE や DELETE を反映しないまま残します。

この移行で CDC を既に開始している場合を除き、テーブルのチェックを外すだけでは移行タイプはロックされません。CDC はロード済みのテーブルのうち、まだ選択されているものをキャプチャします。Full load + CDC では、ロード後、CDC を開始するまでテーブルのチェックを外せます。そのテーブルは Aurora DSQL 上にそのまま残され、CDC はキャプチャせず、ウォーターマークはキャプチャされるすべてのテーブルを引き続きカバーし(引き継ぎはギャップのないまま)、チェックを外したテーブルだけで起きた失敗はもうステップを止めません。

Full load + CDC では、CDC を開始するまで、ロード後にテーブルにチェックを入れることもできます。Retry unfinished tables が [13.7](13-excluding-tables-and-columns.md) の確認(CDC を一度も開始していない、Aurora DSQL のテーブルが空であるか drop して reload される、CDC がそのテーブルをギャップなくキャプチャできる: MySQL ではウォーターマーク以降そのテーブルの定義が変わっていない、PostgreSQL では使える replica identity があり、コピーの前に CDC の publication に加わる)を経てから、元のウォーターマークの下でそのテーブルをロードします。するとウォーターマークがそのテーブルを含むようになり、CDC は他のテーブルとともにそのウォーターマークからそのテーブルをキャプチャするため、そのテーブルの引き継ぎもギャップのないままです。MySQL で Full Load が開始点の定義を記録しなかったテーブル(以前のバージョンの Full Load、またはロードの後に変換したテーブル)は、代わりに Re-run all tables がロードします。その際は **Drop & reload** を選んでください: すべてのテーブルに新しい開始点を取りますが、append はロード済みの行をそのまま残すためです。Full load only は変わりません: そこでのロードがウォーターマークを広げることはありません。

> **コマンドラインから Full Load を実行(任意)。** 同じバルクローダーは CLI スクリプトとしても
> 利用できます — `scripts/run_full_load.py`(まずプランを表示し、次に `--yes`。任意で `--clean`、
> CDC ウォーターマークを取得する `--watermark-out`)— Web UI なしでの自動化や TB 規模の実行に便利です。
> 詳細は [`scripts/README.md`](../../../scripts/README.md) を参照。ソースは読み取り専用で(唯一の例外は
> §3.1 で述べた PostgreSQL-CDC のスロットと publication)、ロードは UI と同様に冪等です。

## 3.8 マルチプロセス並列化（GIL バイパス）

Python の GIL (Global Interpreter Lock) は、単一プロセスを CPU 1 コアに制限します。
Full Load の行ごとの型変換とバッチ組み立ては CPU バウンドな Python であるため、以前は
8 vCPU の Fargate タスクでも約 15,000 rows/s が上限でした。

v0.1.68 から、ローダーは **`ProcessPoolExecutor`** を使用します — 各テーブル（または
シャード）が独自の OS プロセスで独自の GIL + CPU コアを使って実行されます。

### 動作方式

- **小規模テーブル**（シャード不可または行数閾値未満）：テーブルごとに 1 ワーカー。
- **大規模テーブル**（先頭の PK 列が整数の場合 — 単一整数 PK、または `(tenant_id, id)` の
  ように先頭列が整数の複合 PK）：読み取りを K 個の主キー区間に分割し、それぞれ別のワーカー
  プロセスがソースの重ならない区間をロードできます。このリーダーレンジシャーディングは
  **デフォルトで無効**（`full_load_reader_shards=1`、**Settings → Full Load** の *Reader shards
  per large table*）で、このマルチプロセスの経路（`TABLE_PARALLELISM` が 1 より大きい場合）で、
  推定行数が `SHARD_MIN_ROWS` 以上のテーブルにだけ動作します。K は設定値で、最大 32 ÷
  `TABLE_PARALLELISM` です。
  - **PostgreSQL**: すべての実行で。すべての区間が 1 つの共有スナップショットを取り込むので、
    リーダー 1 つの場合と同じく、コピーは 1 時点のものです。
  - **MySQL**: 開始位置に binlog ファイルと位置がある **Full load + CDC** でのみ、そして Aurora
    DSQL 上のすべてのユニークキーが先頭のキー列を含むテーブルだけ（主キー、適用済み DDL の各 UNIQUE
    制約と UNIQUE インデックス、そして append なら実テーブルの各ユニークインデックス）。MySQL は
    スナップショットを共有できず、区間ごとに自身のスナップショットを読むため、読み取り中にキーが
    変わった行は 2 回コピーされるか、まったくコピーされないことがあり、2 つの区間にまたがる
    トランザクションは半分だけ反映されることがあります — 行数は等しいまま。ロード後に、すべての
    読み取りより前に取った開始位置（[§3.5](#35-ウォーターマーク--cdc-への橋渡し)）から開始した CDC が
    それ以降のすべての変更を再生し、異なる時点に読んだテーブルを正すのと同じようにこれを正します。
    先頭列を含まないユニークキー（`UNIQUE (email)` など）は 1 行の 2 つのコピーを見ることになるため、
    そのようなテーブルはリーダー 1 つのままです。**Full load only** はすべての MySQL テーブルを
    リーダー 1 つで読みます: 分割したコピーを正すものがないためです。
  - 適用済みの主キーがソースと異なる append テーブルは、実テーブルのキーが適用済みのキーと等しい
    ときだけ分割されます。そうでなければリーダー 1 つの場合と同じく 1 つの単位としてロードされ、
    適用済みのキーで空のテーブルを作り直すか、ロードを拒否します。
  - MySQL の区間は、ソース接続が切れた後にその場で読み直しません: 1 つの区間の中の 2 つ目の
    スナップショットは、先頭列を含むユニークキー（`(tenant_id, email)` など）も壊しうるためです。
    その区間は失敗し、テーブルはその理由（*range 2 of 4*）とともに *Failed* になり、**Retry
    unfinished tables** がもう一度ロードします。PostgreSQL の区間は共有スナップショットを読み直します。
  - Reader shards と `TABLE_PARALLELISM` がどちらも 1 より大きいと、アクティビティログが分割できる
    大きさのテーブル（整数の先頭キー列と、推定行数 `SHARD_MIN_ROWS` 以上）ごとに *read in K
    primary-key ranges* または *read with one reader* とその理由を記録し、Full Load の表は分割して
    読んだテーブル名の下に *read in K parts* を表示します。
- **すべてのワークユニットが 1 つの bounded pool を共有** —
  `table_parallelism` が同時ワーカー数を制御し、各区間が slot を 1 つ使います。

```
ProcessPoolExecutor(max_workers=table_parallelism)     例: 8
  ├─ customers（小規模）            → work unit 1 つ
  ├─ orders（9M, int PK）           → K = 4 の区間 unit
  └─ order_items（33.6M, int PK）   → K = 4 の区間 unit
                                      同時に最大 8 unit を実行、
                                      unit ごとにソースリーダー 1 つ
```

### 分割して読んだテーブルには CDC の再生が必要です（MySQL）

CDC が再生するまで、分割して読んだ MySQL テーブルはずれた（torn）状態なので、その再生から
テーブルを外す経路はすべてテーブル名とともに拒否され、拒否を終わらせる方法が示されます。
Settings で *Reader shards per large table* を 1 にし、Full Load ステップがそのテーブルに示す
コントロールでロードし直してから（リーダー 1 つ、スナップショット 1 つ — テーブルが終わっていなければ
**Retry unfinished tables**、すべてのテーブルがロードされた後は **Reload specific tables**）操作を
行います。Full load only とより後の開始位置には 2 つ目の方法があります: CDC がテーブルを再生した後に
*Fast sweep* をオフにして **CHECKSUM** モードで Validation を実行します: 一致すればコピーが証明され、
拒否は終わります。テーブルのチェックを外すには、CDC を開始する前にロードし直すしかありません: 再生には
CDC の開始が必要で、CDC の最初の Start からテーブルの集合は固定されるからです（変更できるのは
Start over だけです、[§13.7](13-excluding-tables-and-columns.md)）。コントロールは、ステップがいま一覧に示す
テーブルに従います: ロード後にチェックしてまだロードしていないテーブルは終わっていないものとして
数え、ロード後にチェックを外したテーブルは数えません。

- ロード後にテーブル一覧で**チェックを外す**、または *Exclude tables & columns* のテーブルルールで
  選択を外す: チェックボックスがロックされ、ロックアイコンに理由が表示されます。
- ロード後に**移行タイプを Full load only に切り替える**（CDC only からも: そのときの経路は、
  Full Load ステップがテーブルをロードし直す Full load + CDC を経由します）。
- **より後の開始位置から Start CDC**: Full Load のウォーターマークより後の Manual 位置（入力したもの、
  または *Fetch current position* で埋めたもの）— 削除された binlog への対処の manual の経路も含み、
  *Fetch current position* を勧める開始位置・GTID の対処もこのことを示します。Automatic、または
  ウォーターマークと同じかそれより前の Manual 位置はすべての読み取りを再生するので拒否されず、
  停止したストリームを再開する Start も拒否されません。拒否のメッセージはこの方法を最初に示します。
- ロード前、*Too many tables for one CDC pipeline* の経路（すべてのテーブルをロードしてから CDC に
  不要なテーブルのチェックを外す）は、Reader shards と `TABLE_PARALLELISM` がどちらも 1 より大きい
  とき、このことも示します。ロード後の Deploy CDC infrastructure、Start CDC、Retry CDC の同じ保留は、
  そのようなテーブルを選択を外せないテーブルとして示し、Full load only を示しません。

テーブルの印は、次の 2 つのどちらかで消えます: そのテーブルを作り直すロード（**Drop & reload**）、
またはそのテーブルの最後のロードが終わった後に始まった Validation の **CHECKSUM** 比較が一致した
場合です — ROW_COUNT の実行や、行数が同じだったため *Fast sweep* が省いた CHECKSUM では消えません。
Append、失敗または停止した再試行、あるいはテーブルを 1 つの単位として読むロードは、分割して読んだ行を
Aurora DSQL にそのまま残すので、印も残ります。分割した部分が 1 行も書かなかったことが確かなテーブル
（どの部分も実行されなかった、または停止や失敗の前にどの部分も行を読まなかった場合）には印は付き
ません。そのため、リーダー 1 つで読む Retry や Reload は、そのようなテーブルを、行があっても空でも、
Append / Drop & reload の選択にかかわらず削除してロードし直します（ダイアログが理由を示します）。
Reader shards がまだ 1 より大きければ、ロードし直すときにもう一度分割して読むので Append のままです。
すべてのテーブルの再実行（**Re-run Full Load** または **Re-run all tables**）も、選択や Reader shards の
設定にかかわらず、そのようなテーブルを削除してロードし直します: 再実行は新しい開始位置を取り、その位置
からの CDC はそれより前の変更を再生しないので、Append では分割して読んだ行がそのまま残るからです。

Start CDC は、ストリーミングした場合でも拒否を終わらせません: ツールはそれだけでは CDC がテーブルを
再生したかどうかを判断できません。ストリーミングしなかった Start（ワーカーが拒否した、または
コネクターが失敗した場合）の後は、**Automatic**（または Full Load のウォーターマークと同じかそれより
前の Manual 位置）から CDC をもう一度開始してください: それが再生であり、拒否されません。CDC が
追いついた後は、CHECKSUM の一致が Full load only とより後の開始位置への拒否を終わらせます。最初の
Start 以降、テーブルの集合はいずれにしても固定されます（[§13.7](13-excluding-tables-and-columns.md)）。

### チューニング

大規模な移行では worker 数をタスクの vCPU 数に合わせてください — whole-table unit と区間 unit が
同じ slot を待ちます。Reader shards は、いくつかの大規模テーブルのために slot が空く場合に役立ち、
その代わりに同じテーブルへの同時読み取りが発生します（[§7.2](07-performance-and-tuning.md#72-並列度のチューニング)）。関連する設定
(`TABLE_PARALLELISM`、`BATCH_PARALLELISM`、`SHARD_MIN_ROWS`、`FULL_LOAD_READER_SHARDS`)とその上限、そしてソース負荷との
関係は [第 7 章 §7.2 — 並列度のチューニング](07-performance-and-tuning.md#72-並列度のチューニング)
にまとまっています。この設計が実際に達成したスループット(および置き換えられた ThreadPool の
ベースライン)は [付録: パフォーマンステスト結果](12-performance-test-results.md) にあります。
