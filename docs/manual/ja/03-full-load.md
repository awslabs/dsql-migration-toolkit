# 3. Full Load の仕組み

_言語: [English](../en/03-full-load.md) | [한국어](../ko/03-full-load.md) | **日本語**_

> **前へ:** [2. Evaluation と Schema Conversion](02-evaluation-and-schema-conversion.md)
>
> **テーブルや列を移行から外すには** [13. テーブルと列の除外](13-excluding-tables-and-columns.md)を参照してください。除外した列は Aurora DSQL に NULL としてロードされます。

**Full Load** は、ソースデータベース — RDS / Aurora **MySQL** または RDS / Aurora **PostgreSQL** — の既存の行を Aurora DSQL へコピーする、本ツール独自のバルクコピーです。これは Debezium のスナップショットでは**ありません**。テーブルを選択したあと、**Data Migration** ステップで実行します。

> **メンタルモデル:** ローダーはソースを PK 順に 1 ページずつ読み取り、小さく、冪等で、リトライ可能なバッチとして DSQL に書き込みます — テーブルがどれだけ大きくてもメモリは一定に保たれ、中断されても再開できます。

**最短ルート:** **Data Migration** ステップでテーブルを選択して **Start Full Load** をクリックし、進捗の表を見守り、隔離(quarantine)された、または失敗したテーブルがあれば [§3.6](#36-障害はどのように隔離されるか--そして隔離されない-1-つの障害) に従います。そのあとは、(選んだ場合は) CDC([第 4 章](04-cdc-and-dsql-constraints.md))と Validation([第 5 章](05-validation.md))です。

## 3.1 全体像

```
Source (MySQL / PostgreSQL)            Aurora DSQL
  │  主キーのページ単位で読み取り      ▲  小さくリトライ可能なバッチ
  └──────────►  値の変換  ─────────────┘
       (読み取り専用、一貫したスナップショット)
```

1. **ウォーターマークをキャプチャ**します(ソースの履歴における一貫した地点)。
2. 主キーのページ単位でソースから**行をストリーミング抽出**します(大きなテーブルは複数の主キー区間に分けて読むため、書き込みが分散します。§3.8)。
3. 流れてくる各値を DSQL の形式へ**変換**します。
4. 二次**インデックス**をすでに持つ DSQL のテーブル(§3.4)へ、一定サイズで冪等なバッチとして並行に**ロード**します。

**ツールがソースに書き込む内容。** ソースは一貫したスナップショットの中で**読み取り専用**として読み取られ、ローダーがそれを変更することは決してありません。読み取り以外でソースに触れるのは CDC だけで、次の場合に限られます。

| 実行 | ツールがソースに書き込む内容 |
|---|---|
| `gtid_mode=ON` でないソースでの MySQL の **Full load + CDC** | **`FLUSH BINARY LOGS`** を 1 つだけ、CDC の開始位置を記録した直後、どのテーブルも読む前に実行します。`RELOAD` が必要で、データは書き込まず、テーブルはロックせず、binlog は新しいファイルに移ります(§3.5)。 |
| PostgreSQL **CDC** | 移行対象テーブルだけに厳密にスコープされた論理レプリケーションスロットと publication(ウォーターマークの地点(§3.5)で作成し、teardown 時に削除)。再キー化したテーブルの `REPLICA IDENTITY FULL`。そして、修正が必要な場合の publication の `publish_via_partition_root` の設定。 |
| それ以外の実行 | 読み取り以外はありません。 |

いずれも autocommit で、小さな allowlist に制限され、監査されます。これらが、ツールがいずれのソースに対して行う唯一の書き込みです。

PostgreSQL では、ツールは書き込む前に確認します。ウォーターマークの地点で publication を作成する(またはテーブルを追加する)前に、追加するすべてのテーブルに使用可能な `REPLICA IDENTITY` があること(さらに PostgreSQL 18 では、再キー化したテーブルに生成列がないこと — そのテーブルに必要な `FULL` が壊れるため)を確認し、ない場合はソースで何も変更する前に実行を止めて、そのテーブルと、原因に応じた修正方法を示します。同じ名前のレプリケーションスロットが使用中、別のデータベースに属している、または論理 `pgoutput` スロットでない場合(たとえば同じ CDC スタック名を使う別のマイグレーションのスロット)も、書き込みの前に止まります。このデータベースの非アクティブなスロットは、このスタックの以前のスロットとみなして置き換えます。パーティション化されたテーブルがあるのに publication の `publish_via_partition_root` を設定できない場合は、スロットを作成する前に実行を止め、publication の所有者として実行する `ALTER PUBLICATION` 文を示します。Start CDC では、修正が失敗しても、セッションにソースのパスワードがなく修正を実行できなくても Start は止まらず、そのログが同じ文を示します。Full Load の後に選択したテーブルも、追加する前に同じ確認を受けます。ない場合はそのテーブルはロードされず、その行に理由が表示されます([13.7](13-excluding-tables-and-columns.md))。

## 3.2 ストリーミングエクスポート — テーブルサイズによらず一定のメモリ

ローダーは `OFFSET` ではなく**主キーのページ**でテーブルを読み取ります。各ページは前のページの最後のキーの次から、キーの順に始まり、短いページが終端を知らせるまで繰り返されます。ページは単一の一貫したスナップショットの中でソースからストリーミングされるため、次のようになります。

- テーブル全体が**RAM にロードされることは決してなく** — メモリは 1 ページ分に一定に保たれます。
- 稼働中のソースが変化し続けても、読み取りは**単一の一貫したスナップショット**になります（分割して読む MySQL テーブルは部分ごとに 1 つのスナップショット、[§3.8](#38-並列ロード)）。

**MySQL はソース自体の設定にかかわらず `REPEATABLE READ` で読み取ります。** ツールはこれを自分が開くセッションにだけ設定するため(サーバーの `transaction_isolation` はそのままで、権限も必要ありません)、`READ-COMMITTED` に設定されたソースでもテーブルごとに 1 つの一貫したスナップショットが得られます。そのため各テーブルの読み取りは終わるまで InnoDB の read view を 1 つ保持します。書き込みの多いソースでは、大きなテーブルを読み取る間 History List Length が増えます([§7.3](07-performance-and-tuning.md#書き込みの多いソースでの大きなテーブル))。

**主キーが必須です。** PK を持たないテーブルはページ送りできないため拒否されます(DSQL も PK を要求するため、Evaluation でも `UNSUPPORTED` としてフラグ付けされます)。単一列 PK と複合 PK のどちらもサポートされます — そして複合キーは単に許容されるだけでなく、単調増加するキーによる書き込みホットパーティションに対してツールが推奨する解決策です([第 7 章 §7.1](07-performance-and-tuning.md#プライマリキー戦略--ホットパーティションの回避) 参照)。

正確にページを進められないキー列は、行が欠けたままロードする代わりに、修正方法を示すメッセージとともにそのテーブルを停止します。メンバーを正確に読めない、またはソースが等しいと比較する(たとえば大文字と小文字を区別しない照合順序)MySQL の `ENUM` / `SET` キー列、そして 1 ページを超えるテーブルで**後ろに別のキー列が続く**単精度の MySQL `FLOAT` キー列が該当します(ソースで列を `DOUBLE` または `DECIMAL` に変更するか、テーブルに別の主キーを与えてから、そのテーブルを再試行してください)。`TIME` / `BIT` のキー列はほかの列と同様に読み取ります。ソースで `ENUM` / `SET` のメンバーを追加した後は、Evaluation と Schema Conversion を再実行して、ターゲットの `CHECK` にそのメンバーが載るようにしてください。

> **ビジーな本番ソースへの読み取り負荷が心配ですか?** 多数のテーブルを一度にロードしても 1 つのレバー(テーブル並列度)で制限され、ソースを健全に保つ具体的な手順があります — [第 7 章 §7.3 — ソースへの負荷を最小化する](07-performance-and-tuning.md#73-ソースへの負荷を最小化する)を参照。

## 3.3 その場でのタイプ変換

行がストリーミングされる際、各値は DSQL が保存する形式へ変換されます。これは Schema Conversion のマッピングを踏襲しているため(列の型と値が食い違いません)。**MySQL ソース**が生成する例をいくつか挙げます。

- `TINYINT(1)` → DSQL の **boolean**(`0/1` → `false/true`)。
- `BIT(n)` → 整数。
- `DATETIME` → `timestamp`、壁時計をそのままコピー(タイムゾーンを適用したりずらしたりしないため、別のタイムゾーンのソースはそのタイムゾーンの壁時計を保ちます: 第 2 章の `SOURCE_TIME_ZONE`)、`TIMESTAMP` → `timestamptz`、その時点。
- Aurora DSQL にない値であるゼロや不正な `DATE`/`DATETIME`/`TIMESTAMP`(`0000-00-00`、`2024-00-15`、`ALLOW_INVALID_DATES` での `2024-02-31`)→ CDC コネクタがゼロの日付に書き込む値: NULL、列の `DEFAULT` または `1970-01-01`(その月にない日も `1970-01-01` になり、CDC はその代わりにそうした値で停止します。詳細は [第 6 章 §6.2](06-limitations.md#62-移行プロセスの制限))。そのテーブルには、列ごとの件数を記した WARNING 行がアクティビティログに 1 行残ります(値は残しません)。主キー列のそうした値は保存されたままになり(一意キーの列の値も同様です)、Aurora DSQL がそれを拒否するため、その行は隔離されます。
- `BLOB`/`BINARY`/`VARBINARY` 系 → `bytea`。

**PostgreSQL ソース**では、Full Load 中に MySQL 方式の値変換は**行われません**。両端がともに PostgreSQL であるため、DSQL がサポートする値はそのまま通過します。PostgreSQL の型の扱い — 未サポート型は remodel 対象としてフラグ付け、`numeric` の精度クランプ — は、その場での値変換ではなく **Schema Conversion** で行われます。

マッピングの全体(および値あたり 1 MiB 制限のような DSQL 制約の扱い方)は [第 2 章 §2.3](02-evaluation-and-schema-conversion.md#23-型マッピング-リファレンス)と Schema Conversion ステップにあります。

## 3.4 バッチ化・冪等・並列数を制限したロード

行はそのまま**冪等なバッチ INSERT** へ流れ込み、小さく上限のある DSQL コネクションプールをまたいで**並行に**ロードされます。ツールがすべてのバッチを Aurora DSQL のトランザクションあたりの上限に合わせて自動的に調整し、楽観的並行性制御の競合、切断された接続、一時的な "server unavailable" に当たったバッチはバックオフを置いてリトライします(最大 20 回)。

**設計上、冪等です。** クリーンなロードは新規作成した空のターゲットへ投入し、データがすでに存在しうる場合(リトライ、または行がすでにあるテーブルへの append)は **「既存はスキップ」** モードに切り替えます — insert し、既存キーは上書きせずスキップ — そのため再実行しても重複は生じず、**より新しい CDC 適用済みの行を決して上書きしません**。ただし CDC が削除したばかりの行と最初からなかった行は区別できないため、CDC がターゲットへストリーミングしている間は Full Load は実行されず、Start CDC は実行中の Full Load を待ちます ([§3.5](#35-ウォーターマーク--cdc-への橋渡し)): そうしないと、テーブルのコピー中にソースが削除した行が書き戻されます。

**完全なロードの後に identity シーケンスを前進させます。** テーブルのキーをキャッシュ付き identity 列(`GENERATED BY DEFAULT AS IDENTITY`)に変換した場合、ロード完了時にツールがそのシーケンスを移行済みの最大キーの次から始まるように調整し、**カットオーバー後のアプリケーションの最初の insert** が移行済みキーと**衝突しない**ようにします。**完全な(またはギャップを受容した)ロードでのみ**実行され、部分的/失敗したロードでは実行されません。通常の整数キーはシーケンスを持たないため触れられません。

**二次インデックスが先です。** Aurora DSQL では、インデックスはロード済みの行に対してより空のテーブルに対してのほうがはるかに速く構築されるため([§7.5](07-performance-and-tuning.md#75-ライブインフラでの実測--71-と-72-の裏付け))、テーブルの二次インデックスは行より先に存在します: Schema Conversion の適用がテーブルと一緒に作成し、**Drop & reload** は作り直したテーブルにもう一度作成してから、最初の行をロードする前に Aurora DSQL が構築するのを最大 10 分待ちます。実行が行より先に手を付けられなかったインデックス(たとえば実行の途中で作り直すテーブルのもの)だけが、すべてのテーブルのデータがロードされた後で作成されます。インデックスがあるため、主キー以外の `UNIQUE` インデックスが拒否した行は隔離(quarantine)され(§3.6)、テーブルの残りはロードされます。

失敗したインデックスのステートメントはリトライします。リトライで同じ名前のインデックスがすでにある場合は、作成済みとは数えず(Aurora DSQL ではインデックス名がスキーマ単位なので、別のテーブルのインデックスかもしれないためです)、Full Load の画面に欠落ではなく **not confirmed** (未確認) として表示するので、インデックスを追加する前にターゲットを確認してください。画面の通知が制約の欠落を伝えるのは、`UNIQUE` インデックスが作成されなかったことが確かな場合だけです。

Aurora DSQL は各インデックスをバックグラウンドで構築します。Full Load が構築を待つのは Drop & reload が行をロードする前だけで、それも最大 10 分なので、実行が完了を報告した時点でもまだ構築が続いていることがあります。**Data Migration** ステップに構築の状況が表示されます。

| ステップの表示 | 意味 | 対処 |
|---|---|---|
| *Waiting for Aurora DSQL to build the secondary indexes of N recreated table(s) before loading* | Drop & reload が空のテーブルにインデックスを作成し、その構築を待っています | 不要: 構築が終わればロードが始まります。10 分経っても終わらない構築があれば、その構築を続けたままロードが始まります |
| *Aurora DSQL is building secondary indexes: n of m built* | データはロード済みです。インデックスが必要なクエリは、その構築が終わるまで遅くなります | 不要: 次のステップに進めます |
| *Secondary indexes built: all m* | 実行が発行したすべてのインデックスが構築されました | — |
| *UNIQUE index build failed: a constraint is missing*、または *Secondary index builds failed* | Aurora DSQL がインデックスを構築できませんでした。失敗した `UNIQUE` インデックスは制約の欠落です | カットオーバーの前に、通知が示す原因を直し(`UNIQUE` なら重複を取り除きます)、テーブルにまだそのインデックスがあれば削除してから、もう一度作成します |
| *Secondary indexes not created yet (N table(s))* | それらのテーブルのインデックスを発行する前に実行が終わりました(その段階での停止やアプリの再起動、または Aurora DSQL が応答しなかった場合)。データの欠落はありません | **Retry unfinished tables**: データをロードし直さずにインデックスを発行します |

## 3.5 ウォーターマーク — CDC への橋渡し

ロードの前に、ツールは**ウォーターマーク**をキャプチャします。これは CDC が開始するソースの変更ストリーム上の地点で、どのテーブルも読む前に記録されます。どのウォーターマークも **UTC のスナップショットタイムスタンプ**と、テーブルごとの**概算**行数(ソースをフルスキャンしないための推定値)を保持します。開始位置そのものはエンジンごとに異なります。

- **MySQL** — **binlog ファイル + 位置**、および **GTID セット**、ソースの **`gtid_mode`**、`server_uuid`。`gtid_mode=ON` のソースでは CDC はウォーターマークの GTID セットの次から開始し、それ以外ではそのファイル + 位置から開始します。ウォーターマークは移行対象テーブルごとの列定義の短いフィンガープリントも記録するため、Start CDC はそれ以降にテーブルが変更されたかを判断できます([第 6 章](06-limitations.md) を参照)。
- **PostgreSQL** — binlog 座標ではなく **WAL LSN**。一貫性の地点で、ツールは **publication**(移行対象テーブルに厳密に対する `FOR TABLE`。`FOR ALL TABLES` は決して使いません)と `pgoutput` の**論理レプリケーションスロット**を作成し、スロットが返した一貫 LSN を、スロット名・publication 名とともに記録します。この LSN が WAL を固定し、ギャップのない CDC の引き継ぎを可能にします。PostgreSQL には GTID はありません。

このウォーターマークによって、後続の **CDC へのギャップのない引き継ぎ**が可能になります。各テーブルはウォーターマークの後に開いた自身の一貫スナップショットから読み取られ、CDC はウォーターマーク以降のすべての変更を再適用します。スナップショットと CDC の両方にある変更は 2 回適用されますが、主キーによる冪等な upsert / delete のため無害です([第 4 章](04-cdc-and-dsql-constraints.md)を参照)。そのため、ウォーターマークはスナップショットから見えないトランザクションを含んではいけません。MySQL ではツールが次のようにそれを保証します。

- `gtid_mode=ON` のソースでは何も必要ありません。GTID セットにはコミットが終わったトランザクションだけが入ります。
- binlog ファイル + 位置は、binlog には入ったがまだコミットされていないトランザクションを含み得ます。そこで **Full load + CDC** の実行は、位置を記録した直後、どのテーブルも読む前に **`FLUSH BINARY LOGS`** を実行します。MySQL は新しい binlog ファイルに切り替える前に、すでに binlog に入ったトランザクションがすべてコミットされるまで待ちます(通常は数ミリ秒で、その間は新しいコミットも待ちます)。**RELOAD** 権限が必要で、テーブルはロックせず、アクティビティログに記録されます。**enhanced binlog** を使う Aurora MySQL ではツールはこの待機に依存しないため、そのソースでの Full load + CDC の実行には `gtid_mode=ON` が必要です(または enhanced binlog を無効にします)。前提条件 **CDC start point can be made exact** が Full load + CDC の各実行の前に両方を確認します。
- ウォーターマークより前に `XA PREPARE` され、テーブルを読んだ後にコミットされたトランザクションはどちらにもコピーされないため、実行は見つけた準備状態の XA トランザクションを最大 30 秒待ち、それでも残っていれば停止します。MySQL 8.0.19 以降ではこの確認に `XA_RECOVER_ADMIN` が必要で、この権限がなければ実行は警告を記録して続行します。

**Full load only** の実行は `FLUSH` を実行しません。スナップショットだけをコピーし、それ以降はコピーしないため、すべての変更を含める必要があるなら先にソースへの書き込みを止めてください。`FLUSH` を実行しないため、`gtid_mode=ON` でないソースでは、そのウォーターマークは(以前のバージョンのツールが記録したものと同じく)正確にされず、後でそこから Start CDC すると *This start point was recorded without waiting for in-flight commits* が表示されます。CDC only が Full Load の再実行を Full load + CDC で行うのはこのためです。CDC の前提条件が満たされない場合 — MySQL ではバイナリロギングが無効か権限が制限されている場合、PostgreSQL では `wal_level` が `logical` でないか、スロット / publication を作成できない場合(レプリケーション権限の不足、または standby エンドポイント)— CDC の引き継ぎが受けられなくなるだけで、Full Load は引き続き動作します。例外は、binlog の位置を正確にできない MySQL の **Full load + CDC** 実行です(`RELOAD` がない、`gtid_mode=ON` なしで enhanced binlog を使っている、またはまだ準備状態の XA トランザクションがある)。この実行はどのテーブルも読む前に停止して解決方法を示すので、原因を直してからもう一度開始してください。

> ウォーターマークの行数は**意図的に概算**です(ソースへの負担を抑えるため)。正確な `COUNT(*)` とチェックサムは **Validation**([第 5 章](05-validation.md))の役割であり、Full Load の役割ではありません。

### 新しい開始位置には新しい CDC トピックが必要です

**新しい** ウォーターマークをキャプチャすることは CDC についての決定でもあるため、CDC スタックが **ストリーミングしたことのある** **Full load + CDC** のマイグレーション — Start の後に停止した、コネクタがそのまま残っている、または CloudFormation が Start をロールバックしたスタック — では、新しいウォーターマークを取る操作はすべて **拒否されます**: **Start Full Load**、**Re-run Full Load**、**Re-run all tables** は無効になり、ページヘッダーの **Run** は何も開始しません。Stop CDC (およびロールバックされた Start) は sink をドレインせずに削除するため、その sink のコンシューマグループは新しいスナップショットより古い変更を再ロードしたテーブルの上に再適用し、その一方でソースは以前の停止位置と新しいスナップショットの間の変更をスキップします — 何も表示されないまま進み、CHECKSUM の検証だけがそれを明らかにします。そこで通知は代わりに方法を示します: **Delete CDC infrastructure** して再デプロイ (新しいスタックは空のトピックで始まります)、次に **Drop & reload** で **Re-run Full Load** (PostgreSQL ではレプリケーションスロットが自身のスナップショット位置に作り直されます)、次に **Start CDC** です。

Full Load の各操作がどうなるかは CDC の状態によって異なります。

| CDC の状態 | 新しい開始位置: **Start Full Load**、**Re-run Full Load**、**Re-run all tables**、ヘッダーの **Run** | 元の開始位置: **Retry unfinished tables**、**Reload specific tables**、テーブルごとの **Reload**、**Change & reload** |
|---|---|---|
| まだストリーミングしていない | 許可 | 許可 |
| **稼働中**(ストリーミング中) | 無効: *Stop CDC first (CDC step → Stop CDC), then Delete CDC infrastructure and deploy it again before a new Full Load.* | 無効: 先に Stop CDC してからその操作を実行し、もう一度 Start CDC してください。CDC は停止した位置から続き、ギャップがないのは sink が適用していなかった変更を CDC トピックがまだ保持している間 (MSK での保持期間) だけです。 |
| **Start**、**Stop**、**Delete CDC infrastructure** が進行中 | 無効: 終わるまで待ってください (CDC ステップに進行状況が表示されます)。 | 無効: 終わるまで待ってください。 |
| ストリーミングした後に**停止** | 拒否: 上記の方法に従ってください。 | 許可: CDC は止まったところから続き(上と同じ)、再ロードしたテーブルは収束します。 |

Full Load ステップは **Full load only** と **CDC only** のマイグレーションを制限しませんが、それらに切り替えてもこのゲートは回避できません: MySQL では Start CDC も拒否します (下記)。**このセッションで CDC の状態をまだ読み取っていない間** (画面を開いた直後やアプリの再起動の直後)、または読み取れなかった場合、新しい開始位置は推測せずに **待ちます**: 通知がそう述べ、CDC ステップの **Re-check CDC state** を示します (読み取りに失敗した場合は、先に AWS のアクセス権を直してください)。

**Start CDC もより新しい開始位置を拒否します (MySQL)。** MySQL ソースでは、Start CDC は、ストリーミングしたことのある CDC スタックを、マイグレーションの種類にかかわらず、スタックが最後に開始した位置より新しい開始位置へ (または、停止したスタックの最後の Start が開始位置を渡さなかった場合は、どの開始位置へも) 進めることを拒否します: たとえば Full load + CDC から **Full load only** に切り替えた後の Re-run Full Load が取ったウォーターマークや、より後の **Manual** の位置です。開始位置カードと Start CDC カードが *This CDC stack cannot start from a newer start point* とともに方法 — 上記の方法、CDC only では **Delete CDC infrastructure** して再デプロイしてから新しいスタックで **Start CDC** — を示し、Start CDC は無効になります。その位置と同じかそれより前の開始位置、または開始位置のない Start はストリームを続け、拒否されません。

CloudFormation がロールバックした初回の Start の後も、同じ規則がその Start が渡した開始位置に対して適用されます。その位置も得られない場合は、そのスタックでは同じ開始位置も含めてすべての開始位置が同じ方法とともに拒否されます (*This CDC stack's last start point is not known*)。

CDC only の方法は新しいスタックを Full Load のウォーターマークから開始するため、拒否された位置がそのウォーターマーク (Automatic) の場合、その方法には条件が 1 つあります: その Full Load がターゲットに既にあった行に append した場合は、その Start の前に **Drop & reload** でもう一度実行してください。CDC only には Full Load ステップがないため、その実行の間はマイグレーションの種類を Full load + CDC に切り替えます。その実行の Full Load が CDC の開始位置を正確にします (append はそれらの行をそのまま残し、ウォーターマークからの CDC はその後の変更しか運びません)。新しいスタックではその Start は拒否されず、このセッションが、その Full Load が以前のコピーに append した可能性があることを示していれば、CDC ステップがその Start の前にその条件を示します ([§4.3](04-cdc-and-dsql-constraints.md#43-ギャップのない-full-load--cdc-ハンドオフ))。

PostgreSQL にはこの拒否はありません: Start CDC は Full Load のウォーターマークにかかわらずスタック自身のレプリケーションスロットから続け、Full load only の実行はそのスロットに触れないため、スタックの source connector がストリーミングしていれば、CDC は Stop CDC 後のあらゆる再起動と同じく (上記) 停止したところから続きます (そうでなければ Debezium が先に選択したすべてのテーブルをスナップショットします)。

## 3.6 障害はどのように隔離されるか — そして隔離されない 1 つの障害

ここは、2 つの障害挙動が意図的に異なるため、よく理解しておくべき部分です。

### 行単位の隔離(quarantine)(テーブルはロードを継続)

適用時に **Aurora DSQL が特定の行を拒否した**場合(例: 1 MiB 上限を超える値、主キー以外の `UNIQUE` インデックスに対する重複値のような制約違反)、ローダーはそのテーブルを失敗として扱うことは**ありません**。問題の行だけを切り分けて**隔離**(quarantine)し(その**主キーと理由のみを記録し、値は決して記録しません**)、残りをロードします。隔離された行は、ダウンロード可能なエラーログに表示されます。

Aurora DSQL の一時的な状態は拒否ではありません: 競合、切断された接続、"server unavailable" はバッチ全体をリトライし(§3.4)、リトライを使い切ったバッチは失敗になります — テーブルは **Retry unfinished tables** で再試行でき、そのために隔離される行はありません。

### テーブル致命(テーブル全体が停止)

値を**ひそかに変えずには書き込めない**場合、そのテーブルのロードは、列、その型、ルールだけを記したメッセージ(値は決して記されません)とともに**明示的に**停止します。

- `boolean` にマッピングされた `TINYINT(1)` が `{0,1}` の範囲外の値(例: `2`)を保持している場合(MySQL ソースのみ);
- 両エンジンで、`numeric(p,s)` 列が保持するより小数桁の多い値、または整数列に入る小数。Step 1 の後でソースの型が広げられたか、Schema Conversion でより狭い型を選んだときに起こります。`numeric` 列に入る `FLOAT`/`DOUBLE` のソース値は確認せず、引き続き丸められます;
- 00:00:00–23:59:59.999999 の範囲外の MySQL `TIME`。

これは意図された挙動で、読み取り中に見つかり DSQL に問い合わせる前なので、行単位の隔離では**ありません**。ツールは `2` を `true` につぶしたり `1.2345` を `1.23` に丸めたりして、データをひそかに破損させることを拒否します: 目に見えて修正可能な失敗は、ひそかに誤った値よりも優れています。

### 実行レベルの判定

**いずれか**の行を隔離したテーブルは、**失敗**(未完了)として報告され、その実行は成功として報告されません — そのため、未完了のロードがクリーンなロードと取り違えられることは決してありません — **ただし「隔離された行を受容して続行」を明示的に選んだ場合は**、ギャップを認識したうえで実行が完了します(Validation には引き続き表示)。リトライ可能なテーブル失敗は常にブロックします。ダウンロード可能なエラーログには、どの PK がなぜ隔離されたかが正確に列挙されます。

### 対処方法

| 状況 | 対処 |
|---|---|
| 行が隔離(quarantine)された | ダウンロードしたエラーログ(主キーと理由のみで、値はなし)を見てその行を修正するか、「隔離された行を受容して続行」を選んでギャップを認識したうえで実行を完了します(Validation には引き続き表示されます)。 |
| リトライを使い切ってテーブルが失敗した(Aurora DSQL の一時的な状態) | **Retry unfinished tables**。そのために隔離される行はありません。 |
| 値をひそかに変えずには書き込めず、テーブルが停止した | Schema Conversion で値を保持できる型を列に指定するか(ソースの型が変わった場合は先に Step 1 を再実行してから **Replace** で再適用)、ソースデータを修正するか列を除外してから、そのテーブルを再試行します。 |
| 実行が中断された(停止、クラッシュ、タスクの置き換え) | **Retry unfinished tables**: 完了したテーブルは保持され、未完了のテーブルは最初からロードし直され、元のウォーターマーク(CDC の引き継ぎ地点)が再利用されます([§3.7](#37-再開可能性))。 |
| *Secondary indexes not created yet*(データの欠落はありません) | **Retry unfinished tables**: データをロードし直さずに、それらのテーブルの足りないインデックスだけを発行します(§3.4)。 |
| 新しいコピーと新しい開始位置が必要 | **Re-run Full Load** で **Drop & reload** を選びます。CDC スタックがストリーミングしたことのある Full load + CDC のマイグレーションでは、先に [新しい開始位置には新しい CDC トピックが必要です](#新しい開始位置には新しい-cdc-トピックが必要です) を参照してください。 |

## 3.7 再開可能性

中断された Full Load が再開する単位は、PK 範囲ではなく**テーブル**です。

- 完了したテーブルは `DONE` として記録され、そのまま保持されます。
- 停止、クラッシュ、タスクの置き換えの後は、未完了の各テーブルを「既存はスキップ」モード(§3.4)で、または **Drop & reload** の場合は先にテーブルを作り直して、**最初からロードし直します**。そのため、終わり近くで中断された非常に大きなテーブルも、最初から読み直されます。

**Retry unfinished tables** の経路は、未完了のテーブルのみを保留(pending)状態にリセットし、**元のウォーターマークを再利用**し、完了したテーブルはそのまま保持します — したがって、完了したテーブルをロードし直したり、CDC の引き継ぎ地点を失ったりすることはありません。

**ロード後のテーブルのチェックの入れ外し。** **Full load only** ではテーブル集合を変更でき、**Full load + CDC** では CDC を初めて開始するまで変更できます。ルールと確認は [13.7](13-excluding-tables-and-columns.md) にあります。ロード後に選択したテーブルも同じリトライがロードしますが、元のウォーターマークはそのテーブルを含まないため、CDC の引き継ぎは元の集合に対してのみ有効です。Re-run Full Load が現在の集合に対して新しいウォーターマークを取得するまで(またはそれ以降に選択したテーブルのチェックを外すまで)、移行タイプは Full load only のままです。その再実行は **Drop & reload** で行ってください: CDC はそのウォーターマークから開始しますが、*Append* は以前のロードが書いた行を、その後のソースの UPDATE や DELETE を反映しないまま残します。Full load + CDC でロード後にチェックを入れたテーブルは、CDC が Full Load 以降のギャップなくそのテーブルをキャプチャできるようになれば、Retry unfinished tables が元のウォーターマークの下でロードします。MySQL で Full Load が開始点の定義を記録しなかったテーブル(以前のバージョンの Full Load、またはロードの後に変換したテーブル)は、代わりに Re-run all tables がロードします。その際は **Drop & reload** を選んでください: すべてのテーブルに新しい開始点を取りますが、append はロード済みの行をそのまま残すためです。ロード後にチェックを外したテーブルは Aurora DSQL 上にそのまま残り、もうステップを止めません。

> **コマンドラインから Full Load を実行(任意)。** 同じバルクローダーは CLI スクリプトとしても利用できます — `scripts/run_full_load.py`(まずプランを表示し、次に `--yes`。任意で `--clean`、CDC ウォーターマークを取得する `--watermark-out`)— Web UI なしでの自動化や大規模な実行に便利です。詳細は [`scripts/README.md`](../../../scripts/README.md) を参照。ソースは読み取り専用で(`--watermark-out` を指定した実行は Full load + CDC の実行なので、ソースが `gtid_mode=ON` でない限りウォーターマークの直後に `FLUSH BINARY LOGS` を実行し、これには `RELOAD` が必要です。§3.5)、ロードは UI と同様に冪等です。

## 3.8 並列ロード

テーブルは並列にロードされ、各テーブルは独自のワーカープロセスで実行されるため、Full Load は実行中のタスクのすべての vCPU を使えます。`table_parallelism`（*Tables in parallel*）が同時に動くワーカー数を決めます。大きなテーブルはさらに主キー区間に分けて読みます。Aurora DSQL はテーブルの 1 つのキー範囲を約 20,000 rows/s で書き込むため、複数のキー範囲に分散すると書き込みが速くなるからです（[§7.2](07-performance-and-tuning.md#72-並列度のチューニング)）。

### 動作方式

- **小規模テーブル**（分割の閾値未満、または整数の先頭主キー列がない）：テーブルごとに 1 ワーカー、リーダー 1 つ。
- **大規模テーブル**（先頭の PK 列が整数の場合 — 単一整数 PK、または `(tenant_id, id)` のように先頭列が整数の複合 PK）：K 個の主キー区間に分けて読みます。K は *Reader shards per large table*（**Settings → Full Load**、`FULL_LOAD_READER_SHARDS`）で決まります: `0` = 自動（デフォルト）で、推定 5,000,000 行から 2,500,000 行ごとに 1 区間、最大 32（10M 行なら 4 区間）。`1` = 無効。`2`–`32` = その数ちょうど（下記）。推定値は開始位置でのスキャン不要の推定です。MySQL 8.0 以降（Aurora MySQL 3）では、MySQL がキャッシュするコピー（デフォルトで 1 日、`information_schema_stats_expiry`）ではなく InnoDB から読むため、その間に大きくなったテーブルも現在のサイズで分割します。`TABLE_PARALLELISM` が 1 のときは何も分割しません。
  - **PostgreSQL**: すべての区間を 1 つのスナップショットから読み、テーブルのワーカーはそのスナップショットを共有するので、リーダー 1 つの場合と同じく、コピーは 1 時点のものです。テーブルは、実行全体の推定行数に占めるそのテーブルの割合に応じた数（最大 `TABLE_PARALLELISM`）のワーカーが読み、各ワーカーが区間のひとまとまりを読みます。
  - **MySQL**: 1 つのリーダーセッションがすべての区間を 1 つのスナップショットから、各区間を 1 ページずつ順番に読むので、Full load only でも Full load + CDC でも、リーダー 1 つの場合と同じくコピーは 1 時点のものです。テーブルはソース接続 1 つとワーカー 1 つを使います。
- **2 から 32 を明示的に指定**すると、推定行数が `SHARD_MIN_ROWS` 以上のテーブルをその数ちょうどの区間に分け、同じように読みます。例外は MySQL の別々のスナップショットで読む部分です:
  - **MySQL**: 開始位置に binlog ファイルと位置がある **Full load + CDC** でのみ、そして Aurora DSQL 上のすべてのユニークキーが先頭のキー列を含むテーブルだけ: このとき各区間は 1 つの部分となり、それぞれ自身のワーカーが自身のスナップショットから読みます。MySQL はスナップショットを共有できないため、読み取り中にキーが変わった行は 2 回コピーされるか、まったくコピーされないことがあります。すべての読み取りより前に取った開始位置（[§3.5](#35-ウォーターマーク--cdc-への橋渡し)）から開始した CDC がそれ以降のすべての変更を再生し、これを正します。それ以外の MySQL テーブルは、上記のとおり 1 つのセッションで読みます。
- **ソース接続が切れると**、1 つのセッションで読むテーブルは新しいスナップショットから全体を読み直し、PostgreSQL の区間は共有スナップショットを読み直します。MySQL の部分はその場で読み直しません: テーブルはその理由（*range 2 of 4*）とともに *Failed* になり、**Retry unfinished tables** がもう一度ロードします。
- **同時にロードされるテーブル（またはテーブルの部分）は最大 *Tables in parallel* 個**で、読む行数の多いものから実行されます。

### 分割して読んだテーブルには CDC の再生が必要です（MySQL）

これは上記の別々のスナップショットで読む部分だけに当てはまり、そのためには *Reader shards per large table* に 2 以上を明示的に指定する必要があります: デフォルトの設定では、どのテーブルもこのような部分に分けて読まれません。CDC が再生するまで、分割して読んだ MySQL テーブルはずれた（torn）状態なので、その再生からテーブルを外す経路はすべてテーブル名とともに拒否され、拒否を終わらせる方法が示されます。

- ロード後にテーブル一覧で**チェックを外す**、または *Exclude tables & columns* のテーブルルールで選択を外す: チェックボックスがロックされ、ロックアイコンに理由が表示されます。
- ロード後に**移行タイプを Full load only に切り替える**（CDC only からも: そのときの経路は、Full Load ステップがテーブルをロードし直す Full load + CDC を経由します）。
- **より後の開始位置から Start CDC**: Full Load のウォーターマークより後の Manual 位置（入力したもの、または *Fetch current position* で埋めたもの）。Automatic、またはウォーターマークと同じかそれより前の Manual 位置はすべての読み取りを再生するので拒否されず、停止したストリームを再開する Start も拒否されません。
- テーブルを選択から外せないときの **Deploy CDC infrastructure、Start CDC、Retry CDC**: そのようなテーブルを選択を外せないテーブルとして示し、Full load only を示しません。

**拒否を終わらせる方法。** Settings で *Reader shards per large table* を 0（自動）または 1（無効）にし、Full Load ステップがそのテーブルに示すコントロールでロードし直してから（リーダーセッション 1 つ、スナップショット 1 つ — テーブルが終わっていなければ **Retry unfinished tables**、すべてのテーブルがロードされた後は **Reload specific tables**）操作を行います。Full load only とより後の開始位置には 2 つ目の方法があります: CDC がテーブルを再生した後に *Fast sweep* をオフにして **CHECKSUM** モードで Validation を実行します: 一致すればコピーが証明され、拒否は終わります。テーブルのチェックを外すには、CDC を開始する前にロードし直すしかありません: 再生には CDC の開始が必要で、CDC の最初の Start からテーブルの集合は固定されるからです（変更できるのは Start over だけです、[§13.7](13-excluding-tables-and-columns.md)）。

テーブルの印は、次の 2 つのどちらかで消えます: そのテーブルを作り直すロード（**Drop & reload**）、またはそのテーブルの最後のロードが終わった後に始まった Validation の **CHECKSUM** 比較が一致した場合です。そのため、リーダー 1 つで読む Retry や Reload は、そのようなテーブルを、Append / Drop & reload の選択にかかわらず削除してロードし直します（ダイアログが理由を示します）。すべてのテーブルの再実行（**Re-run Full Load** または **Re-run all tables**）も、選択や Reader shards の設定にかかわらず、そのようなテーブルを削除してロードし直します: 再実行は新しい開始位置を取り、その位置からの CDC はそれより前の変更を再生しないからです。

Start CDC は、ストリーミングした場合でも拒否を終わらせません: ツールはそれだけでは CDC がテーブルを再生したかどうかを判断できません。ストリーミングしなかった Start（ワーカーが拒否した、またはコネクターが失敗した場合）の後は、**Automatic**（または Full Load のウォーターマークと同じかそれより前の Manual 位置）から CDC をもう一度開始してください: それが再生であり、拒否されません。CDC が追いついた後は、CHECKSUM の一致が Full load only とより後の開始位置への拒否を終わらせます。

### チューニング

大規模な移行では *Tables in parallel* をタスクの vCPU 数に合わせてください (本番トラフィックを処理しているソースでは 2〜4 から始めます: [§7.3](07-performance-and-tuning.md#73-ソースへの負荷を最小化する))。分割そのものには設定は要りません。関連する設定 (`TABLE_PARALLELISM`、`BATCH_PARALLELISM`、`SHARD_MIN_ROWS`、`FULL_LOAD_READER_SHARDS`)とその上限、そしてソース負荷との関係は [第 7 章 §7.2 — 並列度のチューニング](07-performance-and-tuning.md#72-並列度のチューニング)にまとまっています。この設計が実際に達成したスループットは [付録: パフォーマンステスト結果](12-performance-test-results.md) にあります。
