# 0. はじめる前に

_言語: [English](../en/00-before-you-begin.md) | [한국어](../ko/00-before-you-begin.md) | **日本語**_

マイグレーションを始める**前に**、この短いページを読んでください。Aurora DSQL は MySQL や PostgreSQL を
そのまま置き換えられるドロップイン代替では**なく**、独自のルールを持つ分散型エンジンなので、
**異種（heterogeneous）マイグレーション**として扱ってください。（PostgreSQL ソースは、両者とも
PostgreSQL-16 のワイヤプロトコルを話すため DSQL により近いものの、DSQL の制約はそのまま適用されます。）
このツールは、差異を最初に明示し（**Evaluation**）、決定論的に変換できるものを変換し
（**Schema Conversion**、**Full Load**、**CDC**）、その結果を証明します（**Validation**）。以下の各項目は、
短い「必ず知っておくべきこと」と、それを詳しく扱う章へのポインタです。強制される全体の制限は
[第 6 章 — 制限](06-limitations.md) にあります。

---

## プリフライトチェックリスト

**範囲とアクセス**

- [ ] **ソースとターゲットは同一の AWS リージョンにあること** — ツールもそのリージョンで実行して
      ください。クロスリージョンのマイグレーションは**サポートされず**、オプションの CDC パイプラインも
      単一のリージョン/VPC で実行されます。
      → [§1.5](01-setup.md#15-ソースとターゲットへの接続),
      [§6.2](06-limitations.md#62-移行プロセスの制限)

- [ ] **2 つのソースエンジンをサポートします:** **RDS for MySQL** / **Aurora MySQL**（**5.7 / 8.0 /
      8.4**）と **RDS for PostgreSQL** / **Aurora PostgreSQL**（PG **13–18** はすべてエンドツーエンドで
      検証済み。バージョン固有のエッジは [§6.2](06-limitations.md#62-移行プロセスの制限) を参照）。
      どちらのエンジンもパスワードまたは **AWS Secrets Manager** のユーザー名/パスワードで認証します —
      IAM 認証はターゲット DSQL 専用です。 → [§1.1](01-setup.md#11-前提条件)

- [ ] **ソースはほぼすべての経路で読み取り専用です** — 読み取り可能なユーザーで十分です。書き込みは
      CDC だけで起きます。`gtid_mode=ON` でないソースでの MySQL の **Full load + CDC** 実行は
      `FLUSH BINARY LOGS` を 1 回実行し（そのユーザーには `RELOAD` が必要）、**PostgreSQL CDC** は
      論理レプリケーションスロットと publication を作成し（teardown 時に削除）、CDC キーが変わった
      テーブルに `REPLICA IDENTITY FULL` を設定し、Full Load の後に選択したテーブルを publication に
      追加します（自動コミット、小さな allowlist に限定、監査記録あり）。これ以外の書き込みは
      ありません。 → [§1.1](01-setup.md#11-前提条件)

- [ ] **DSQL は PostgreSQL 互換・IAM 認証・分散型です。** PostgreSQL のワイヤプロトコルを話し、
      **短命の IAM トークン**（パスワードなし）と **OCC(楽観的並行性制御)**（ロックなし）を用います。
      ツールには DSQL の**クラスターエンドポイント**と、それに接続できる AWS アイデンティティを渡します。
      → [§1.1](01-setup.md#11-前提条件),
      [§1.5](01-setup.md#15-ソースとターゲットへの接続)

- [ ] **認証情報はセッションメモリ内にのみ存在します。** ディスク、ログ、レポートに書き込まれることは
      決してなく、セッション終了時に破棄されるため、再起動後は接続情報を再入力します。
      → [§1.5](01-setup.md#15-ソースとターゲットへの接続)

**スキーマ**

- [ ] **移行するすべてのテーブルには主キーが必須です。** DSQL は主キーでデータを分散し、Full Load も PK 順に
      読み取るため、PK のないテーブルはマイグレーションできません — Evaluation が `UNSUPPORTED` として
      フラグし、Full Load も拒否します。ロード前に PK を追加してください（単一カラム・複合 PK のいずれも
      サポート）。
      → [§6.1](06-limitations.md#61-aurora-dsql-の機能制限スキーマがこれらに適合している必要があります)

- [ ] **DSQL はソースエンジンが持ちうる機能の一部を意図的に省いています:** **トリガー / ストアド
      プロシージャ / イベント**なし、**トランザクションあたりの行数制限（≤ 3000）**、**値あたり 1 MiB
      制限**、**空間型なし**。（**外部キーはサポートされます** — Aurora DSQL が外部キーを強制します — ので、
      ツールはこれらを保持し、データロード後に、CDC マイグレーションならカットオーバー時に再作成します。）
      自分で見つける必要はありません — **Evaluation** がそれぞれを推奨アクションとともに
      `AUTO` / `MANUAL` / `UNSUPPORTED` としてフラグします。**PostgreSQL ソース**では DSQL が格納できない
      PG 固有のカラム型も扱います: 大半は同じデータを保持できる型に置き換えて（配列 → `jsonb`、
      `money` → `numeric`、`inet`/`enum` → `text`）確認を促し、代わりの型がないもの（composite、domain、
      pgvector などの拡張型）だけが `UNSUPPORTED` です。データをロードする前に、`UNSUPPORTED` 項目を
      解決し、`MANUAL` 項目を判断してください。
      → [第 2 章](02-evaluation-and-schema-conversion.md), [第 6 章](06-limitations.md)

- [ ] **PostgreSQL の行レベルセキュリティには、すべての行を読める移行ユーザーが必要です。** Aurora DSQL
      には行レベルセキュリティがないため、Evaluation はポリシーのあるテーブルを `UNSUPPORTED` と判定します
      （ルールはアプリケーションに移す必要があります）。ツールは `pg_dump` と同様に `row_security = off`
      でソースを読むため、移行ユーザーはスーパーユーザー、`BYPASSRLS` を持つロール、またはテーブルの所有者
      （`FORCE ROW LEVEL SECURITY` でない場合）である必要があります — そうでなければ、Full Load と
      Validation は一部の行だけをコピーするのではなく、そのテーブルで停止します。
      → [第 2 章](02-evaluation-and-schema-conversion.md), [第 6 章](06-limitations.md)

**CDC の選択**

- [ ] **CDC はオプションであり、実行中は課金されます。** ストリーミング CDC が必要になるのは、
      大規模なカットオーバーや、ほぼゼロダウンタイムのカットオーバーの場合だけです。CDC は MSK +
      MSK Connect（場合によっては NAT ゲートウェイ）をプロビジョニングし、それらを撤去するまで
      費用がかかります。短い凍結（フリーズ）を伴う一回限りのマイグレーションであれば、**Full Load
      単独**で十分であり、ストリーミングインフラをプロビジョニングしません。
      → [第 4 章](04-cdc-and-dsql-constraints.md),
      [§10.1](10-conclusion.md#101-どの経路が必要か)

- [ ] **CDC はまずソース側の設定が必要で — エンジンごとに異なります。** 前提条件ゲートは準備が整うまで
      CDC を**ブロック**し、Full Load 単独では不要です。**MySQL:** ROW フォーマット・フルローイメージの
      バイナリロギング、**レプリケーション権限**を持つユーザー、十分な binlog 保持期間（ゲートは**警告する
      のみ**ですが、保持期間が短すぎると実際に silent-gap のリスクがあります）。**PostgreSQL:**
      `wal_level=logical`、レプリケーション権限を持つユーザー、クラスターの **writer** エンドポイント、
      複製対象のすべてのテーブルに使用可能な `REPLICA IDENTITY`（`FULL` はどのテーブルでも動作しますが、
      PostgreSQL 18 で生成列を持つテーブルは例外）。RDS/Aurora では、パラメータグループと
      `mysql.rds_*` ストアドプロシージャを使います — `my.cnf`/`SET GLOBAL` ではありません。
      → [§1.6](01-setup.md#16-cdc-のためのソース準備)

- [ ] **CDC が複製するのはスキーマではなくデータです。** CDC 中、ソースの **DDL** 変更は DSQL に
      **伝播されません** — 対応する変更を Aurora DSQL に自分で行います(追加または名前変更された列は
      **Fix target schema…**、NULL を許可するようになった列は `ALTER … DROP NOT NULL`、型・キーの変更は CDC を
      停止した状態での作り直し。CDC のストリーミング中は Schema Conversion の Apply がブロックされます)。一部の
      変更はデッドレターなしに書き込まれるため、検証してください。
      → [§4.2](04-cdc-and-dsql-constraints.md#42-cdc-は-スキーマ-ではなく-データ-を複製する--重要)

**ツールの実行**

- [ ] **AI アシストはオプションで、Amazon Bedrock 専用です。** **デフォルトでオフ**です。有効にすると、
      AWS 認証情報（`bedrock:InvokeModel` と `bedrock:InvokeModelWithResponseStream` の権限）を使って
      **もっぱら Amazon Bedrock を通じてのみ**動作し、選択したモデルは AWS アカウントで 1 回有効化されて
      いる必要があります（モデルの AWS Marketplace の契約（agreement）を承諾 — 第 2 章）。**直接 API キーを
      入力する手段はありません。** すべての提案は**レビュー専用**であり、AI がデータ経路に入ることは決して
      ありません。同じアシスタントが**すべてのステップ**で読み取り専用の **AI DBA** パネルとして利用できます。
      → [第 2 章](02-evaluation-and-schema-conversion.md), [第 9 章](09-query-validation.md)

- [ ] **（AWS にデプロイする場合）オプションの認証を備えた単一タスクのコントロールプレーンです。**
      通常の形態は ALB の背後にある **ECS Fargate** タスク 1 つで、ALB の**オプションの Cognito** ゲートを
      使います（インターネットに面するデプロイでは必ず有効にしてください）。ジョブ/セッション状態はマネージド
      S3 バケットに保持され、タスク入れ替え後も再開できます。**単一 EC2 ホスト（ソースから）** モード
      （状態は保持される EBS ボリューム、SSM ポートフォワード、ALB/Cognito なし）もあります。
      → [§1.4](01-setup.md#14-単一-ec2-ホストで実行する-ソースから),
      [§6.3](06-limitations.md#63-デプロイの制限aws-ホスト形態)
