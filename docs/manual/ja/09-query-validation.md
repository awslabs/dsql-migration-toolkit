# 9. Query Converter と AI DBA

_言語: [English](../en/09-query-validation.md) | [한국어](../ko/09-query-validation.md) | **日本語**_

> **前へ:** [8. テストと検証](08-testing-and-verification.md)

スキーマとデータを移行するだけでは終わりではありません。アプリケーションの
**クエリ**も Aurora DSQL で動作する必要があり、しかも*快適に*動作しなければなりません。
**Query Converter**（サイドバーにある任意のツール）は、1 つの MySQL クエリを
Aurora DSQL に変換し、ターゲットで読み取り専用でテストし、そして AI 補助を有効にすると
**AI DBA** が DSQL 向けに効率的に書き換え、その改善を証明する場所です。

この章ではそのワークフローを扱います。ソースには決して書き込まず、ターゲットに DML を
実行することもありません。

---

## 9.1 クエリを変換する

MySQL 文を貼り付けると、スキーマ変換と同じ決定論優先（deterministic-first）エンジン
（`sqlglot`）を使って Aurora DSQL（PostgreSQL）へ変換し、次のように分類します。

- **AUTO** — 決定論的に変換完了。すぐにテストできます。
- **MANUAL** — 変換はされましたが、確認が必要です（DSQL で注意点のあるイディオム）。

また、MySQL のイディオムを**書き換え**、DSQL で問題となるものを**フラグ**します。例:
`ON DUPLICATE KEY UPDATE` → `INSERT ... ON CONFLICT DO UPDATE`(MANUAL — 競合ターゲットは自分で確認)、
`JSON_UNQUOTE(JSON_EXTRACT(...))` → `JSON_EXTRACT_PATH_TEXT`、MySQL の `HAVING` エイリアス参照のインライン化、
そして `SELECT ... FOR UPDATE`（DSQL の楽観的並行性制御のもとで異なる動作）。これらの指摘はすべて **MANUAL**
に分類されます。アプリケーションコード全体のアンチパターンスキャン（外部キー/`AUTO_INCREMENT`/トリガー依存、
未対応関数）は [第 2 章](02-evaluation-and-schema-conversion.md) を参照してください。

元の SQL と変換後の SQL を並べて表示するため、何が変わったのかを正確に確認できます。

---

## 9.2 ターゲットでテストする（読み取り専用）

変換された **SELECT** については、**Test on target** が検証済みの DSQL ターゲット上で
`EXPLAIN` を使って計画を立てます。クエリは計画されるだけで**実行はされない**ため、行は
読み取られません。**EXPLAIN ANALYZE** トグルをオンにすると、（読み取り専用の）クエリを
実際に実行し、実測の所要時間・行数、そして Aurora DSQL の文単位の
**DPU コスト見積もり**を取得します。

テストできるものとできないもの:

- **SELECT** → `EXPLAIN`（計画のみ）または `EXPLAIN ANALYZE`（読み取り専用で実行）。
- **DDL** → トランザクション内でドライランし、**ロールバック**します（コミットしません）。
- **DML**（INSERT/UPDATE/DELETE） → ターゲットに対して**決して実行しません**。

判定には、DSQL が文を受け入れたかどうか、受け入れなかった場合は正確なエラー（SQLSTATE
付き）、取得したクエリプラン、そして ANALYZE の場合は DPU コストが表示されます。

**どのスキーマでテストされるか。** スキーマ修飾のないテーブル名（`FROM orders`）はセッションの
`search_path` でスキーマに解決されます。ツールは接続元ソース DB と同名のスキーマを既定にし、
**Test against schema** ピッカーで切り替えられます。`relation "…" does not exist`（SQLSTATE **42P01**）は、
そのテーブルがテスト対象スキーマに無いことを意味するだけです — 正しいスキーマを選んで再テストしてください。

> **DSQL プランの読み方:** Aurora DSQL は*分散型*の PostgreSQL 互換エンジンであるため、
> プランの読み方が少し異なります — §9.4 を参照してください。

## 9.3 AI DBA でクエリをチューニングする

**AI 補助が有効になっている**場合（Connect 画面。既定ではオフ）、**Tune with AI DBA**
ボタンが表示されます。ただし、変換された SELECT が **Test on target を通過した後にのみ**
表示されます。AI が推測ではなく根拠に基づいた助言を行うには、このクエリの実際の実行プランが
必要なため、先にテストすることが必須です。テストを **EXPLAIN ANALYZE** をオンにして実行して
**DPU ベースライン**を取得すると、ボタンに現在のコスト（例: *now ≈ 0.03 DPU*）が表示され、
その後 AI が書き換えでどれだけ節約できるかを証明できます。

このボタンをクリックすると、アプリ全体の常設 AI パネルが開き、そのスコープがこのクエリに
設定されます。これは**このクエリの実際の EXPLAIN プランと DPU**、および Aurora DSQL の実行
モデルに根拠を置いています。AI は次を行います。

- 書き換えたクエリをコードブロックで提案し、
- **何を変更し、なぜ DSQL でより安価なのか**（どのスキャンタイプ（scan type）または
  フィルター層（filter layer）が改善され、なぜストレージからコンピュートへ移動するバイト数が
  減るのか）を説明し、
- クエリの**結果を同一に保ちます** — 高速化のためにセマンティクスを変えてはならないと
  指示されています。

DSQL に当てはまらない素の PostgreSQL チューニング助言（`VACUUM`/`REINDEX`、fillfactor、
プランナー GUC、「`cost=` の数値を下げる」といった推論）からは、意図的に*遠ざけられて*います。

### 証明する: 書き換えを再テストする

各書き換え提案の下には **Test rewrite on target** アクションがあります。ツールは応答から
正確な SELECT を抽出し、`EXPLAIN ANALYZE` を使ってターゲット上で読み取り専用で再実行し、
測定した**変更前後の DPU** を同じチャットに戻します。そのため **AI は実際の改善幅を報告**
します（書き換えが効果なしなら正直にそう述べます）。証拠はモデルの説明文ではなく、実測の
DPU です。

> **助言のみ。** 自動適用されるものは何もありません。書き換えを自分でエディターにコピーし直し、
> Convert / Test を再実行します — これが人によるレビュー（human-review）ゲートです。AI 補助は
> オプトインのままで、コントロールプレーン上にあり、データパスには決して触れません。

## 9.4 DSQL のクエリチューニングが PostgreSQL と異なる理由

Aurora DSQL はワイヤプロトコル上は PostgreSQL 互換ですが、*分散型*エンジンとしてクエリを
実行するため、クエリを効率化する方法がいくつか変わります。AI DBA はこれらの事実に根拠を
置いており、自分でプランを読むときにも知っておくと役立ちます。

- **主キーが*すなわち*テーブルです。** すべてのテーブルは主キーで編成された B-tree であり、
  別個の heap は存在しません。述語に使える有効なインデックスのないテーブルは、**Full Scan**
  （「Seq Scan」ではありません）で読み取られます。主キーに対する範囲/等価フィルターは物理的に
  シーケンシャルで本質的に安価なため、**主キーの選択は PostgreSQL よりもはるかに重要です**。
- **コンピュートとストレージは分離されています。** ストレージからコンピュートへ移動するすべての
  行がレイテンシーと **DPU**（Distributed Processing Unit — DSQL のコスト単位。
  `EXPLAIN ANALYZE VERBOSE` に表示され、PostgreSQL の `cost=` の数値は目標ではありません）を
  発生させます。移動するバイト数を減らすように**フィルターを押し下げること**が主要なてこです。
- **3 つのフィルター層（良い順）:** (1) *Index Condition* — インデックスキー列に対する
  等価/範囲述語。(2) *Storage Filter* — 非キー列をインデックスの `INCLUDE` 句に追加し、
  ストレージが転送前にフィルターする。(3) *Query Processor Filter* — トップレベルの
  `Filter:` 行として表示され、フィルターされていないすべてのデータが既にネットワークを
  越えている状態（最悪）。述語を 3 → 2 → 1 の方向へ移動させてください。
- **スキャンタイプ（安い順で最後が最良）:** **Full Scan**（PK またはインデックスを追加）→
  **Index Scan**（`Storage Lookup` ノードはカバリングインデックスが不完全であることを意味します
  — 不足している列を `INCLUDE` に追加）→ **Index Only Scan**（理想的）。

AI DBA が提案する DSQL に適した一般的な書き換え: `SELECT *` の代わりに必要な列だけを射影する。
先頭ワイルドカードの `LIKE '%x%'` を避ける（インデックスを使えません）。オプティマイザーが
結合をまたいで推論できない**冗長な結合述語（redundant join predicate）**を追加する。
`ORDER BY … LIMIT` には **CTE の遅延マテリアライゼーション（late materialization）**を使う。
インデックスをカバリングにするために `INCLUDE` 列を追加する。そして、ホットパーティションを
生み出す単調増加キー（`AUTO_INCREMENT`、タイムスタンプ）よりも、ランダムに分布するキー
（UUID）を優先する。
