## A. はじめに & 一般

**Q1. このツールは何を、どの方向に移行しますか？**

Amazon **RDS / Aurora MySQL または PostgreSQL → Amazon Aurora DSQL**、単方向のみです。サポートするソースは **RDS for MySQL** と **Aurora MySQL**（**5.7 / 8.0 / 8.4**）、および **RDS for PostgreSQL** と **Aurora PostgreSQL**（**PG 13–18**。ツールはハードなバージョン下限/上限を強制しません）です。どちらの経路も — Schema Conversion、Full Load、CDC、cut over — テストでチェックサム付きの **エンドツーエンド検証済み** です。これはバージョンアップグレードではなく **異機種（heterogeneous）** 移行です: MySQL からは **MySQL → PostgreSQL 方言 → DSQL 制約**、PostgreSQL からは **ほぼ同一（near-identity）の PG → DSQL** のパススルーです。

**ソースは読み取り専用** で、例外は CDC のいくつかの付随的な書き込みだけです: PostgreSQL の論理レプリケーションスロットと publication（teardown 時に削除）、再キー化したテーブルへの `REPLICA IDENTITY FULL`、そして `gtid_mode=ON` でないソースでの MySQL の Full load + CDC 実行が行う `FLUSH BINARY LOGS` 1 回（`RELOAD` が必要で、データは書き込みません）です。正確な一覧は [第0章](00-before-you-begin.md) にあります。

**Q2. Aurora DSQL は私のソースエンジン（Aurora MySQL / PostgreSQL）のドロップイン代替になりますか？**

いいえ。DSQL は **PostgreSQL** ワイヤプロトコルを使用し、短命の **IAM トークン**（パスワード不要）で認証し、ロックの代わりに **楽観的並行性制御（OCC）** を使用します。そして水平スケールに適合しない機能を意図的に除外しています — **トリガー/ストアドプロシージャなし、トランザクションあたりの行数制限、値あたり 1 MiB の制限** など（一方、外部キーは **サポートされ、強制されます**）。したがって、スキーマと、箇所によってはアプリケーションを DSQL に合わせて適合させる必要があります。どこを変える必要があるかは、 Evaluation（ステップ1）が正確に教えてくれます。

**Q3. ツールをローカルで実行すべきか、ECS Fargate にデプロイすべきか、単一 EC2 ホストで実行すべきか？**

3 つとも同じ Web UI です。用途に応じて選んでください:

| 選択肢 | 向いているケース | 内容 |
|---|---|---|
| **ローカルで実行** | 手早い評価や小規模な作業 | ノート PC/ワークステーション上で起動する Web UI（デフォルトは `http://127.0.0.1:8080`）。開始が最も速い方法です |
| **AWS（ECS Fargate）にデプロイ** | 実際の本番移行 | Application Load Balancer の背後で動く単一タスク（オプションで Amazon Cognito によるゲート）。チームでアクセスを共有でき、長時間かかる移行も確実に進められます |
| **単一 EC2 ホストで実行**（ソースから） | コンテナ/ECR や AWS Lambda を使えないアカウント | 同じエンジンが VPC 内でソースのまま（`git clone` + `uv` + systemd サービス）動作します。SSM ポートフォワードで接続し、状態は保持型 EBS ボリュームに置き、Fargate の ALB/ECR/Cognito のフロントドアはありません |

いずれの場合もソースは読み取り専用でアクセスされます。ローカル・Fargate の実行方法は [第1章 §1.2–§1.3](01-setup.md)、EC2 ホストの手順は [デプロイガイド](../../../deploy/DEPLOYMENT.ja.md#単一-ec2-ホストで実行-ソースからlambda-free) をご覧ください。

**Q4. ソースとターゲットは同じ AWS リージョンである必要がありますか？**

**はい。** ソースとターゲットは **同じリージョン** でなければならず、オプションの CDC パイプラインも単一のリージョン/VPC で実行されます。**クロスリージョン移行はサポートされていません。**

**Q5. 2つのデータパスとは何であり、どちらが必要ですか？**

| お客様の状況 | 使用するもの |
|---|---|
| 一回限りの移行。短いメンテナンス書き込み凍結が許容できる | **Full Load のみ** — ストリーミングインフラなし、継続コストなし。 |
| 大規模／継続的。**ほぼゼロダウンタイム** のカットオーバーが必要 | **Full Load + CDC** — 隙間のない引き継ぎにより、ソースを稼働させたまま DSQL を収束させる。 |

CDC は実際の可動部（MSK、MSK Connect、シンクコネクタ）を追加し、**デプロイされている間はコストが発生**します。継続的なレプリケーションが本当に必要なときのみ使用してください。そうでなければ Full Load 単独の方がシンプルで安価です。[第10章 §10.1](10-conclusion.md#101-どの経路が必要か) をご覧ください。

**Q6. ツールがアプリケーションのカットオーバーまで行ってくれますか？**

いいえ。本ツールは **評価・変換・ロード・ストリーミング・検証** を行いますが、アプリケーションを *いつ* *どのように* 切り替えるかは、お客様だけが下せる運用上の判断です。ツールは切り替え可否を証拠で裏付け（Validation）、CDC の場合は隙間のないストリームを提供します。カットオーバーは、ツールが画面に表示する手順書（runbook）に従ってお客様ご自身が実施します（[第10章 §10.3](10-conclusion.md#103-カットオーバー-アプリケーションを-dsql-へ切り替える)）。

## B. Full Load（一括コピー）

**Q7. Full Load はどのように動作し、非常に大きなテーブルでも安全ですか？**

Full Load はツール **独自の一括ローダー**（Debezium スナップショットではありません）です。ソース行を **主キーの keyset（キーセット）ページネーション**（`OFFSET` は決して使わない）で **ストリーミング** し、流れてくるそばから書き込みます。そのため **テーブルのサイズに関わらずメモリは1ページ分に制限され**、テーブル全体が RAM に読み込まれることはありません。**TB 規模** のソースと非常に大きなテーブル向けに設計されています。 [第3章 — Full Load](03-full-load.md) をご覧ください。

**Q8. Full Load はべき等ですか？ 中断された場合はどうなりますか？**

はい。行は境界付き並列のべき等な `INSERT … ON CONFLICT` バッチとしてロードされるため、行を再度書き込んでも重複しません。ロードが **中断された** 場合（クラッシュ、停止、タスク置き換え）、完了したテーブルはそのまま保持され、**Retry unfinished tables** が未完了の各テーブルを **最初から** ロードし直し、すでに書き込んだ行はスキップします（**Drop & reload** の場合は、先にテーブルを作り直します）。中断されなかった状態とまったく同じ状態に収束します — **重複なし、損失なし** — ただし、終わり近くで中断された非常に大きなテーブルも最初から読み直されます。テーブルごとの失敗は分離されており、1つの不良テーブルが他のテーブルを中断させることはありません。

**Q8a. ロード中にソースの Aurora クラスタがフェイルオーバーしたら？**

自動的に処理されます。ライター昇格（パッチ適用、インスタンス置換、AZ イベント）は開いているソース接続をすべて閉じるため、数時間かかるロードは必ず遭遇します。該当テーブルは新しい consistent snapshot から **自動的に再読み込み** されます（既定3回、15秒 → 30秒 → 60秒のバックオフで、昇格したライターへ DNS が切り替わる時間を確保）。既に書き込まれた行はスキップされるため、再試行のコストは再読み込み I/O のみで、行が重複することはありません。

Full load + CDC では、実行の開始位置から再生されるストリームが 2 つの読み取りの間に変わったすべての行を正します。Full load only では、ソースに書き込みがあった場合は **Drop & reload** で再実行してください。分割して読む MySQL テーブル（*Reader shards per large table*、[§3.8](03-full-load.md#38-並列ロード)）は読み直しません: そのテーブルは失敗し、**Retry unfinished tables** がもう一度ロードします。

**接続レベル** の失敗のみ再試行し、データ／スキーマエラーは即座に失敗します。再試行を使い切った場合はテーブルのエラーメッセージがそう伝え、再実行は安全です。`DSQL_MIGRATOR_FULL_LOAD_SOURCE_RETRY_ATTEMPTS` で回数を調整できます（1 = 再試行なし）。

**Q9. Full Load はソースでのバイナリログを必要としますか？**

**いいえ。** Full Load 単独では CDC の前提条件は一切不要です（MySQL では binlog もレプリケーションユーザーも不要、PostgreSQL では `wal_level=logical`・レプリケーションスロット・publication も不要）。いずれのエンジンでも通常の読み取り専用接続でソースを読み取ります。それらの前提条件が必要なのは **CDC** だけです（Q12 参照）。

**Q10. Full Load のスループットをチューニングできますか？**

はい。境界付きのデフォルト値があり、大きなハードウェア向けに引き上げたり、負荷の高いソースを保護するために引き下げたりできます。`DSQL_MIGRATOR_FULL_LOAD_TABLE_PARALLELISM`（同時に処理するテーブル数、デフォルト 4）、 `…_BATCH_PARALLELISM`（テーブルあたりの実行中バッチ数、デフォルト 8）、`…_BATCH_ROWS` （書き込みあたりの行数、デフォルト 2000、DSQL の 3000 で厳密に上限あり）。同時に開く DSQL 接続の総数 ≈ テーブル × バッチ並列度 のため、クラスタの接続クォータ内に収まるようにしてください。 [第7章 §7.2](07-performance-and-tuning.md#72-並列度のチューニング) をご覧ください。

**Q11. 並列度を上げても、なぜ速くならないことがあるのですか？**

DSQL はストレージを **主キー単位で** 分散します。そして単調増加する主キー（MySQL の `AUTO_INCREMENT`、または PostgreSQL の `serial` / `IDENTITY` / シーケンス由来のキー）は、すべての挿入を同じ「最も右端の」キー範囲に集中させ — **書き込みホットスポット** を生みます。高並列度ではこれが楽観的並行性の競合率（`SQLSTATE 40001`）を高めるため、スループットの向上が頭打ちになります。これが、Evaluation がソースエンジンに関わらずそうした単調増加の主キーにフラグを立て、Schema Conversion が PK 戦略（キャッシュ付き identity — 生成キーの既定 / 整数のまま維持 / 複合キー）を提供する理由です。 [第7章 §7.1](07-performance-and-tuning.md#プライマリキー戦略--ホットパーティションの回避) をご覧ください。

## C. CDC（ストリーミングレプリケーション）

**Q12. CDC はソースに何を要求しますか？**

ソースエンジンによって異なります。前提条件のチェックは、必須項目が満たされるまで **CDC をブロック** し、それ以外は **警告**（非ブロッキング）にとどめます。

**MySQL ソース**

- **必須:** **フル行イメージを伴う ROW フォーマット** のバイナリログ（`binlog_format=ROW`、`binlog_row_image=FULL`）と、**レプリケーション権限** を持つユーザー。RDS/Aurora では `my.cnf` ではなくパラメータグループと `mysql.rds_set_configuration` で設定します。
- Full Load のウォーターマーク時点のログが CDC 開始まで残るように **binlog の保持期間を延長** してください（Aurora MySQL はデフォルトで binlog を約24時間しか保持しません）。保持期間が短すぎる場合は警告にとどまります。

**PostgreSQL ソース**

- **必須:** `wal_level=logical`（RDS/Aurora: カスタムパラメータグループで `rds.logical_replication=1` を設定し、writer を再起動）、**レプリケーション権限を持つユーザー**、standby/reader ではなくクラスタの **writer**、そしてレプリケートされる各テーブルの使用可能な **`REPLICA IDENTITY`**（`FULL` はどのテーブルでも動作しますが、PostgreSQL 18 で生成列を持つテーブルは例外です。パーティション化されたテーブルではすべてのパーティションに必要）。
- レプリケーションスロット / `max_wal_senders` の余裕は **警告** にとどまります。
- 設定すべき **binlog 保持期間の概念はありません**: ツールが publication と論理スロットを自動作成し、WAL はスロットによってピン留めされるため、`wal_status` を監視してください。非アクティブで未消費のスロットはソースのディスクを埋めうるためです。

[§1.6](01-setup.md#16-cdc-のためのソース準備) と [第6章 §6.2](06-limitations.md#62-移行プロセスの制限) をご覧ください。

**Q13. Full Load → CDC の引き継ぎはどのように「隙間なし」になるのですか？**

Full Load は一貫したスナップショット地点で **ウォーターマーク** を記録します — MySQL ソースでは **binlog/GTID 位置**、PostgreSQL ソースでは事前作成した論理レプリケーションスロットにピン留めされた **WAL LSN** です。CDC は **まさにそのウォーターマークから** ストリーミングを開始し、適用がべき等かつ PK キー付きであるため、スナップショットとストリームの間にいかなる重複があっても **重複を作り出すことはできません**。その結果、隙間もなく、二重適用もありません。[第4章 — CDC](04-cdc-and-dsql-constraints.md) をご覧ください。

**Q14. CDC は何をレプリケートし、何をレプリケートしないのですか？**

CDC は **行データの変更**（INSERT/UPDATE/DELETE）をレプリケートするのであって、SQL ではなく、また **DDL でもありません**。CDC 実行 **中** のソースでのスキーマ変更は DSQL に **伝播されません** — 対応する変更をお客様ご自身で Aurora DSQL に行う必要があります（追加または名前変更された列は **Fix target schema…**、それ以外は `ALTER` または §4.2 の作り直し。CDC のストリーミング中は Schema Conversion の Apply がブロックされます）。ターゲットの形状にもはや一致しない行の多くは **DLQ**（デッドレター）に送られ、そのテーブルが CHECKSUM で一致するまで Cut over を保留します。ただし一部の変更はデッドレターなしに書き込まれるため、ソース DDL の後は CHECKSUM で検証してください。 [第4章 §4.2](04-cdc-and-dsql-constraints.md#42-cdc-は-スキーマ-ではなく-データ-を複製する--重要) をご覧ください。

**Q15. なぜ既製の JDBC シンクではなく、カスタム DSQL シンクコネクタなのですか？**

既製シンクでは処理できない、DSQL 固有の3つの理由があります。(1) 書き込み競合（`40001`）が発生したら、**バッチトランザクション全体**（冪等で PK キー付きの upsert/delete）を **指数バックオフ + フルジッター（full jitter）** とともに再実行しなければなりません。(2) 短命の **IAM トークンを発行・更新** して、数時間に及ぶストリームが認証で停止しないようにしなければなりません。(3) DSQL の 3000行 / 1 MiB の上限を守り、処理不能（poison）な行を DLQ にルーティングしなければなりません。[第4章 §4.1](04-cdc-and-dsql-constraints.md#41-パイプライン) をご覧ください。

**Q16. CDC は一時停止できますか？ また課金されますか？**

ストリーミングパイプライン（MSK Serverless + MSK Connect、加えてツールが作成した場合は NAT ゲートウェイ）は **実行されている限りコストが発生** します — 無料の「一時停止」はありません。カットオーバー後は cdc-stack を撤去してください（**Start over（右上）** → *Delete all CDC infrastructure*。Cut over のランブックがここへ案内します）。 Full Load 単独ではストリーミングインフラを **一切** プロビジョニングしません。 [第6章 §6.2](06-limitations.md#62-移行プロセスの制限) をご覧ください。

**Q17. CDC の各ステップにはどれくらいかかり、なぜそんなに時間がかかるのですか？**

CDC には時間のかかる操作が **3つ** あり、それぞれ別個です。3つすべてを見込んで計画してください（インフラが既に立ち上がっているので *Start CDC* は瞬時に終わる、と考えてしまうのがよくある誤解です）：

| 操作 | 目安 | 時間を支配する要素 |
|---|---|---|
| **Deploy CDC infrastructure** | **~15〜20分** | MSK Serverless クラスタが準備完了になるまでの待機 |
| **Start CDC**（コネクタ作成） | **~20〜30分** | 各 MSK Connect コネクタが `CREATING → RUNNING` になる時間 |
| **Delete CDC infrastructure** | **~15〜25分** | VPC アタッチ Lambda の ENI クリーンアップ（後述） |

瞬時に終わらないのは仕様です。**デプロイ** は MSK Serverless クラスタが準備完了になるまで待ちます（AWS 側の時間なので調整の余地はありません）。**Start CDC** は 2 つの MSK Connect コネクタ（ソース = Debezium、シンク = DSQL）を 1 回のパスで作成し、両方が `RUNNING` になるのを待つため数分かかります。インフラのデプロイとは別に計画してください。MySQL ソースの **撤去** が遅いのは、最後に残る VPC 内のオフセットシーダー Lambda を削除すると、AWS がそれが使用したネットワークインターフェース（ENI）をクリーンアップする必要があり、最大 ~20分かかりうるためです。**PostgreSQL** の撤去にはそうした Lambda がなく、ENI クリーンアップの遅延もありません。

> **ヒント：** 反復や再起動の際には、完全な削除・再作成ではなく既存のインフラを維持したままにすると、~20分の ENI クリーンアップを回避できます。**Stop CDC** は MSK クラスタ・プラグイン・VPC・IAM を保持し、2つのコネクタのみを削除するため、その後の **Start CDC** はインフラの待機をスキップし、中断した箇所から再開します — MySQL ソースはクラスタの `connect-offsets` トピックに残っているオフセットから、PostgreSQL ソースは論理スロットの LSN 位置から。ただし Stop CDC は sink をドレインしないため、その時点で sink が適用していなかった変更は CDC トピックから適用されます: その再開にギャップがないのは、トピックがまだその変更を保持している間 (MSK での保持期間) だけです。PostgreSQL ソースでその期間が過ぎた後の方法は [§4.3](04-cdc-and-dsql-constraints.md) にあります。カットオーバーが完了し CDC が不要になったら、スタックを最終的に撤去してください。

これらの操作はそれぞれ **結果**（成功／失敗と所要時間）をアクティビティログに記録するため、たとえばカットオーバー前に実行した Stop が実際に完了したかを後から確認できます。

## D. スキーマ & 型変換

**Q18. ツールは何が移行可能かをどのように判断しますか？**

Evaluation は **すべてのオブジェクト** を、**AUTO**（自動的に変換）、**MANUAL**（変換されるが判断／アプリケーション側の変更が必要）、**UNSUPPORTED**（自動変換なし — 再設計が必要）のいずれかに分類し、作業量の見積もりと名前衝突の検出を伴います。ロードの **前に** すべての UNSUPPORTED 項目を解決し、各 MANUAL 項目について判断を下してください。[第2章](02-evaluation-and-schema-conversion.md) をご覧ください。

**Q19. ソースのデータ型は DSQL にどのようにマッピングされますか？**

**MySQL ソース** の場合、主なものは次のとおりです。

| MySQL 型 | Aurora DSQL 型 | 備考 |
|---|---|---|
| `TINYINT(1)` | `boolean` | MySQL の boolean 慣例。 |
| `…INT UNSIGNED`（符号なし整数） | `smallint` / `integer` / `bigint` / `numeric(20,0)` | より広い型に **無損失で** 拡張。 |
| `BIT(n)` | サイズ付き整数（`smallint`…`numeric(20,0)`） | DSQL に `BIT` 型はない。 |
| `DECIMAL(p,s)` | `numeric(p,s)` | 精度とスケールを維持（Aurora DSQL は精度 1000 まで許可）。 |
| `DATETIME` | `timestamp` | 壁時計をそのままコピー(タイムゾーンのずれなし)。時計を読むデフォルトはソースのタイムゾーンを明示(`SOURCE_TIME_ZONE`)。 |
| `ENUM` | `text` + `CHECK` | DSQL に `ENUM` はない。 |
| `BLOB` / `BINARY` | `bytea` | 生バイトを保持。 |
| `JSON` | `json` | |

**すべての型についての完全なマッピング**（Aurora DSQL の型と知っておくべきこと）は、 [第 2 章 §2.3](02-evaluation-and-schema-conversion.md#23-型マッピング-リファレンス) にあります。Full Load ローダーと CDC シンクは同一のマッピングに従うため、どちらのパスで移行しても、行は同じように着地します。

**PostgreSQL ソース** の場合、変換とデータパスは **ほぼ同一（near-identity）の PG-16 → DSQL パススルー** です: Aurora DSQL がサポートする型は **そのまま** 引き継がれます。相当のない型は、値を保つ代替型がある場合は警告付きで置き換えられ、**MANUAL** と評価されます（アプリケーションが合わせます）: 配列 → `jsonb` / 子テーブル、`money` → `numeric(23,4)`、`enum`・ネットワーク・幾何（geometric）・`xml`・`bit`・`tsvector`・`range` 型 → `text`。composite 型、domain、pgvector のような拡張型には代替型がなく、再モデリングするまで **UNSUPPORTED** です。`STORED` 生成列は **保持** され、`VIRTUAL` 生成列は通常の列になりアプリケーションでの再計算が必要です。

**Q20. 外部キー、トリガー、ストアドプロシージャはどうなりますか？**

**外部キーはサポートされます** — Aurora DSQL が強制します。ツールは各ソースの FK を **保持** し、ロード後に `ALTER TABLE … ADD CONSTRAINT … FOREIGN KEY … NOT VALID` として再作成します。すぐに追加され、ロード済みの行は Aurora DSQL がバックグラウンドで検証します。Full Load の後は **Apply foreign keys** 操作で適用し、**CDC** マイグレーションでは、シンクが行を順不同でストリームしている間は制約が存在してはならないため、**カットオーバー** まで延期されます。PostgreSQL 18 の 2 種類は作成されません: `NOT ENFORCED` と宣言されたキー（`PG_FK_NOT_ENFORCED`）と、`FOREIGN KEY … PERIOD`（`PG_FK_PERIOD`: アプリケーションで強制してください）です。PostgreSQL のキーは `MATCH FULL` と `DEFERRABLE` / `INITIALLY DEFERRED` を保持します。代わりに FK を **取り除くことを選び**、参照整合性をアプリケーション層で強制することもできます。ランタイムのコストも検討してください: 関連テーブルへの DML は **追加の読み取り** を発生させ、並行する競合は再試行可能な `40001` になり、`CASCADE`/`SET NULL`/`SET DEFAULT` アクションは 3000 行/トランザクションの制限に算入されます。

**トリガー、ストアドプロシージャ/関数、スケジュールされたジョブ** は省略され、UNSUPPORTED としてフラグが立つため、アプリケーションで再実装してください（MySQL の Event Scheduler や PostgreSQL の `pg_cron` のようなスケジュールされたジョブは EventBridge / Lambda に移します）。[第6章 §6.1](06-limitations.md#61-aurora-dsql-の機能制限スキーマがこれらに適合している必要があります) をご覧ください。

**Q21. テーブルに主キーがありません。移行できますか？**

そのままでは移行できません。Aurora DSQL は主キーのないテーブルも作成できますが、このツールは主キーを必要とします — Full Load は主キーの keyset で読み、CDC はキーで変更を適用します (全列が NOT NULL の UNIQUE インデックスがあれば Evaluation が候補として示します)。そのため、主キーのないテーブルは **UNSUPPORTED** としてフラグが立ち、ロードできません。まずソースで（または再設計の中で）主キーを追加してください。

## E. 検証 & 正確性

**Q22. 移行が正しいことをどうやって知るのですか？**

Validation（ステップ4）は **証拠** を提供し、ソースとターゲットを **段階的に厳しくなる3つのパス** で比較します。

| パス | 何を確認するか | 何を捕捉するか |
|---|---|---|
| **行数** | 両側それぞれのテーブルごとの正確な `COUNT(*)` | 行が丸ごと欠落または余分にある |
| **チェックサム**（順序非依存） | すべての行を **両エンジンで同じ方法** でハッシュして比較 | **数は一致するが値が異なる** 行 |
| **完全な主キー突合** | 両側の **すべての PK** をマージし、**ターゲットに欠落している** PK と **ターゲットに余分にある** PK を特定 | **どの行** が欠落／余分かを、行単位で正確に |

- 判定が **MATCH になるのは、すべての差異が説明されたときのみ** です: 移行中もソースが変化し続けたことによる **ドリフト**（Q23）、意図的な **過大値の隔離（quarantine）**（Q24）、あるいは **CDC がまだ追いついている最中** など。説明のつかない欠落／余分な行が1つでもあれば、それは MATCH では *ありません*。
- **行数だけの「一致」は決して信頼されません。** テーブルはチェックサムと PK 突合にも合格しなければなりません。オプションの **Fast sweep**（行数が異なるテーブルのみ深く検査）を有効にした場合、スキップされたテーブルは *行数のみで検証済み* と表示され、レポートからそれらのテーブルだけを深く再検査できます。
- **一部の列型は設計上チェックサムから除外されます。** テキスト形式がエンジン間で安定していないためです: 浮動小数点（MySQL `FLOAT`/`DOUBLE`、PostgreSQL `real`/`double precision`）と `json`。PostgreSQL ソースでは `jsonb` はチェックサムに **含まれます**。行数、PK 突合、その他すべての列は引き続き検証されます。

**不一致を修正したら、そのテーブルだけ再検査できます。** レポートの失敗テーブルごとに **Re-check** アクション（および *Re-check all N*）があり、そのテーブルのみを再比較して結果をレポートにマージするため、1つの修正を確認するために数時間の検証をやり直す必要はなく、全体の go/no-go 判定も自動的に更新されます。

カットオーバー前にこれを実行すれば、希望ではなく **ソースとターゲットが実際に一致するという証明** に基づいて切り替えを決定できます。[第5章 — Validation](05-validation.md) をご覧ください。

**Q23. 移行中もソースが変わり続けます。検証が誤らないのですか？**

いいえ — 正しく帰属されます。Validation はソースの現在位置を Full Load ウォーターマークと照合し、**ドリフト** を報告します（MySQL では **GTID**、GTID を有効化できない場合は binlog の **file:position**、PostgreSQL では現在の **WAL LSN** を Full Load の LSN と照合）。したがって、**新たなソース活動** による件数の差分はバグと区別されます。PostgreSQL ソースでは、ツールは LSN ベースのドリフト値を再計算しません。代わりに CDC の収束を監視してください。クリーンな最終的な go/no-go のためには、ソースへの書き込みを凍結し、先に CDC をドレインさせてください（Q27）。

**Q24. DSQL が格納できない行（例：1 MiB を超える値）はどうなりますか？**

**決して黙って破棄されることはありません。** Full Load では、DSQL の値あたり ~1 MiB の制限を超える値は行単位で **隔離（quarantine）** され（主キーと理由がエラーログに記録される）、テーブルの残りはロードされます。CDC では、そのような行は **DLQ** に送られます。パイプラインを通過することさえできない値（> ~8 MiB）は **キャプチャの時点で除外** します — Data Migration ステップの **Exclude tables & columns** でルールを追加するか、*Oversized-LOB candidates* セクションの **+ add rule** を使います。このセクションは Evaluation が `OVERSIZED_LOB` としてフラグ付けするものと同じ集合を示し、**Check sizes** で実際のサイズを測れます。ツールが書き込む行では、除外した列は NULL になります。CDC 開始前から Aurora DSQL にあった行は値を保持し、Validation がそれらの行を数えます。[第6章 §6.1](06-limitations.md#61-aurora-dsql-の機能制限スキーマがこれらに適合している必要があります) をご覧ください。

**Q25. 「silent より loud」とは、実際にはどういう意味ですか？**

本ツールは、データを静かに破損させることを拒否します。**MySQL ソース** の例：`{0,1}` の範囲外の `TINYINT(1)` 値は、それを `true` に押し込むのではなく **そのテーブルのロードを停止** します。範囲外の `TIME` は、切り詰められるのではなく失敗します。（**PostgreSQL** ソースの Full Load は純粋なパススルー — 両端とも psycopg ネイティブ — なので、こうした値変換はほとんどありません。）いずれの場合も、不完全なロードは **FAILED** として報告され、偽の成功にはなりません。お客様はソースを修正（またはそのカラムを除外）して再実行します。

## F. カットオーバー、ロールバック & 運用

**Q26. カットオーバー時にダウンタイムはありますか？**

**Full Load のみ** の場合、ダウンタイムは最終的な凍結 + ロード + 検証の長さです。 **Full Load + CDC** の場合、それは短い **最終ドレイン + スモークテスト** に縮小されます — CDC がソースを稼働させたまま DSQL を収束させ続けるため、凍結するのは本当に最後だけです。

**Q27. 安全なカットオーバーの手順は？**

（CDC パス）CDC に追いつかせる → **ソースへの書き込みを凍結** → 最終ドレインを待つ（ラグ → 0）→ **Validation を再実行** → クリーンな MATCH のときのみカットオーバー → アプリを切り替えてスモークテスト → **CDC パイプラインを最後に撤去**。詳細と Full Load のみのバリアントは [第10章 §10.3](10-conclusion.md#103-カットオーバー-アプリケーションを-dsql-へ切り替える) にあります。

**Q28. ロールバックできますか？**

計画しておけば可能です。DSQL にサインオフするまで、ソースを **凍結（読み取り専用）したまま、削除しない** ように保ってください。切り替える前であれば、ロールバックは簡単です（ソースは手つかずで正典です）。アプリケーションが DSQL に書き込んだ **後** は、それらの新しい行は DSQL に **のみ** 存在します（本ツールはソース → DSQL をレプリケートするのであって、その逆は **しません**）。そのため、そのときロールバックするということは、それらを自分で突合することを意味します。ロールバックのルールは、カットオーバーの *前に* 決めておいてください。

**Q29. どのような認証情報と権限が必要で、私のデータはどのように保護されますか？**

ソースは **MySQL または PostgreSQL** への通常の **読み取り専用接続**（パスワード、または AWS Secrets Manager のユーザー名/パスワード — **IAM ではありません**。IAM トークン認証はターゲットの DSQL 専用）を使います。CDC ではレプリケーション権限が追加で必要で、MySQL の Full load + CDC 実行ではソースが `gtid_mode=ON` でない限り `RELOAD` も必要です（[§1.6](01-setup.md#16-cdc-のためのソース準備)）。ターゲットは DSQL の **IAM トークン認証**（DB パスワードなし）を使い、すべての接続は **TLS** で暗号化されます。認証情報は **セッションメモリ内のみ** に存在し、ディスク・ログ・レポート・ジョブ状態のいずれにも書き込まれず、ログとレポートには主キーと件数のみが記録され、**実際の行の値は決して記録されません。** オプションの AI アシスト（Amazon Bedrock、デフォルトはオフ）は **助言のみ** で、CDC のデータパスには **一切** 関与しません。

必要な AWS 権限そのものは実行方法（ローカル/Fargate）によらず同じですが、**その権限がどこに付くか** が異なります。**ローカル実行** では標準の認証情報チェーン（`~/.aws`、環境変数、`AWS_PROFILE`、SSO）で **実行するユーザー自身の IAM アイデンティティ** を使うため、そのアイデンティティが権限を直接持つ必要があります（CDC では下の表の最後の行の広範なインフラ作成権限まで）。**Fargate** では CloudFormation が **最小権限の Task Role** を作成し、CDC インフラのデプロイのような特権的な作業は常時稼働のタスクではなく、**専用のデプロイロール（CdcDeployRole）をその操作の間だけ引き受けて（assume）** 実行します。（なお、app-stack を **最初にデプロイする人** には IAM ロールを作成する権限が一度だけ必要です。）

作業ごとの具体的な IAM アクションです（**Fargate では自動作成された Task Role に付くため、自分で書く必要はありません**。**ローカル実行では自分自身のアイデンティティがこれらを直接保持する必要があります**）:

| 対象 | IAM アクション（最小） |
|---|---|
| **ターゲット DSQL（常時）** | `dsql:DbConnect`、`dsql:DbConnectAdmin`（IAM トークン発行）、`dsql:GetCluster` |
| **ソース（常時）** | IAM アクションなし — 読み取り専用の MySQL または PostgreSQL ユーザー/パスワード（または下記の Secrets Manager シークレット）。CDC ではこれにレプリケーション権限が加わり、MySQL の Full load + CDC 実行では、ソースが `gtid_mode=ON` でない限り `RELOAD` も加わる |
| **ソースシークレット（任意）** | `secretsmanager:GetSecretValue` — ソース認証情報が Secrets Manager シークレットにある場合のみ |
| **AI アシスト（任意）** | `bedrock:InvokeModel`、`bedrock:InvokeModelWithResponseStream` — Fargate スタックでは `BedrockModelArns` で絞らない限りすべての Anthropic モデル(EC2 スタックは選択したモデルにスコープ)。AI を有効にした場合のみ |
| **CDC — パイプラインのデプロイ/削除** | cdc-stack が必要とする広範なインフラ作成権限: `cloudformation:CreateStack`/`UpdateStack`/`DeleteStack`/`Describe*`/`GetTemplate`、広範な `ec2:*`（VPC サブネット・NAT・EIP・ルートテーブル・セキュリティグループ・VPC エンドポイント・ネットワークインターフェイス）、`iam:CreateRole`/`AttachRolePolicy`/`PassRole`/…（コネクタロール）、`kafka:*` / `kafkaconnect:*`（MSK Serverless + MSK Connect）、`logs:*`、プラグインバケットへの `s3:*`。Full Load のみの移行では **一切不要**。 |

> **Full Load のみ** なら上表の最初の 3 行だけで十分です。**CDC** は最後の行（広範なインフラ作成権限）を追加します。Fargate ではこの権限は分離された `CdcDeployRole`（デプロイ/削除中のみ引き受け）にあり、常時稼働のタスクは保持しません。しかし **ローカル実行では自分の ID が CDC 行全体を保持する必要がある** ため、CDC には Fargate を推奨します。

**Q30. 複数の移行を実行したり、ツールを水平スケールしたりできますか？**

AWS ホスト形態は **単一の ECS Fargate タスク** であり、複数のタスクを実行しないでください。そのジョブ／セッションの状態はすでにツールが管理する S3 バケットに保持されているため、タスクの置き換え後もワークベンチの状態と Full Load の記録は残ります（その時点で実行中のジョブは中断され、Retry unfinished tables が完了していない各テーブルを最初からロードし直します）。タスクを 1 つに限る理由は **単一ライターのオーケストレーション** です: CDC デプロイの調整と各セッションのライブ状態が、その 1 つのタスクの中にあります。[第6章 §6.3](06-limitations.md#63-デプロイの制限aws-ホスト形態) をご覧ください。

**Q31. すべての AWS インフラを削除して、完全にゼロからやり直すには？**

まず違いを明確にしてください。UI の **Start over** ボタンは、ツールの *セッション*（接続、プラン、進捗）をリセットするだけです — 意図的に、いかなる AWS リソースも **削除しません** ので、コストのかかるものが誤って撤去されることはありません。実際にインフラを削除してすべてのコストを止めるには、次の順序でスタックを撤去します（正確なコマンドを含む完全な手順は [デプロイ §9 — Teardown](../../../deploy/DEPLOYMENT.ja.md#teardown) にあります）：

1. **最初に CDC インフラ**（CDC をデプロイしたことがある場合のみ — これはコストのかかる MSK / MSK Connect / NAT の部分です）。**アプリがまだ実行されている間** に、UI から行います：**Start over（右上）→ 「Delete all CDC infrastructure」**（アプリが `cdc-stack` の削除を駆動、~15〜25分、そしてそれが作成したマネージドのソース認証情報シークレットも削除します。ただし PostgreSQL でレプリケーションスロットを削除できなかった場合は、スロットの削除に必要な認証情報であるため、そのシークレットを残します）。アプリがすでに消えている場合は、スタックを手動で削除します： `aws cloudformation delete-stack --stack-name dsql-cdc-stack`（実際の cdc-stack 名を使用してください — デフォルトは `dsql-cdc-stack` で、レガシーのスタックは `mysql-dsql-cdc-stack` の場合があります）。
2. **app-stack** — `deploy/teardown.sh <stack-name>` を実行（ECS/ALB/IAM スタックを削除。`DELETE_ECR=true` を渡すとコンテナイメージリポジトリも削除します）。
3. **build-stack** — オプションの CodeBuild ビルドパスを使用した場合のみ。
4. **スタックが所有しない残留物を確認：** ツールはアカウント／リージョンごとの **プラグインバケット** `mysql-dsql-migrator-plugins-<account>-<region>` を自動作成しますが、これはどのスタックにも属さないため、 `delete-stack` では削除されません — 本当にクリーンな状態にしたい場合は手動で削除してください（`aws s3 rb` に `--force`。元に戻せず、そのアカウントとリージョンにあるツールのすべてのデプロイがこのバケットを共有するため、どのデプロイももう使用していないときだけ）。このバケットは、デプロイがアップロードした CDC プラグインファイルのすべてのバージョンを 1 つずつ保持し（`cdc-plugins/<hash>/<file>`、それぞれ最大約 31 MiB）、それらを整理するものはありません。ECS Fargate では、保存されたセッションとジョブの状態もこのバケットにあります。また、手作業で追加した **Route 53** レコードも削除してください。その後、`mysql-dsql-*` または `dsql-cdc-*` の CloudFormation スタックが残っていないことを確認してください。

撤去後は、初回インストールとまったく同じようにゼロから再デプロイできます（デプロイガイド）。*移行そのものだけを再開したい* 場合 — 同じインフラで、新しいワークフロー — は、代わりに **Start over** を使用してください。即座で、無料です。残しておく CDC スタックで CDC がストリーミングしたことがある場合、そのスタックで新しく Full load + CDC を実行するには、先に **Delete CDC infrastructure** して再デプロイする必要があります: それまでは Full Load ステップが新しい開始位置を拒否します ([第 3 章 §3.5](03-full-load.md#35-ウォーターマーク--cdc-への橋渡し))。ターゲットのテーブルに以前の実行の行がまだ残っている場合は、新しい実行の Start Full Load のダイアログで **Drop & reload** を選んでください: 既定の *Append* はそれらの行をそのまま残します。
