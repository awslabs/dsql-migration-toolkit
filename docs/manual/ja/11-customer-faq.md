# 11. お客様向け FAQ

_言語: [English](../en/11-customer-faq.md) | [한국어](../ko/11-customer-faq.md) | **日本語**_

> **前へ:** [10. まとめ](10-conclusion.md)

異機種データベース移行には多くの疑問が伴います。本章では、**Full Load**、**CDC**、
**制限事項**、**計画すべき事項** について、お客様から最もよく寄せられる質問にお答えします。
すべての回答は本ツールが実際に行う動作を反映しており、各項目は詳細を記した章へリンクしています。
最初にひとつだけ読むのであれば、[第0章 — はじめる前に](00-before-you-begin.md) をお読みください。

## A. はじめに & 一般

**Q1. このツールは何を、どの方向に移行しますか？**

Amazon **RDS / Aurora MySQL → Amazon Aurora DSQL**、単方向のみです。これはバージョンアップグレードではなく、
**異機種（heterogeneous）** 移行（MySQL → PostgreSQL 方言 → DSQL 制約）です。DSQL は
PostgreSQL ワイヤ互換で、分散型、サーバーレス、IAM 認証方式です。**ソースは全工程を通じて読み取り専用**であり、
本ツールがお客様の MySQL に書き込むことは一切ありません。


**Q2. Aurora DSQL は Aurora MySQL のドロップイン代替になりますか？**

いいえ。DSQL は **PostgreSQL** ワイヤプロトコルを使用し、短命の **IAM トークン**（パスワード不要）で認証し、
ロックの代わりに **楽観的並行性制御（OCC）** を使用します。そして水平スケールに適合しない機能を意図的に
除外しています — **外部キーなし、トリガー/ストアドプロシージャなし、トランザクションあたりの行数制限、
値あたり 1 MiB の制限** など。したがって、スキーマと、箇所によってはアプリケーションを DSQL に合わせて
適合させる必要があります。どこを変える必要があるかは、Evaluation（ステップ2）が正確に教えてくれます。


**Q3. ツールをローカルで実行すべきか、AWS（ECS Fargate）にデプロイすべきか？**

どちらも同じ Web UI であり、ユースケースに応じて選んでください。

- **ローカルで実行** — ノートPC/ワークステーション上で起動します（デフォルトは
  `http://127.0.0.1:8080`）。**開始が最も速く**、互換性評価や比較的小規模な移行に適しています。
- **AWS（ECS Fargate）にデプロイ** — 実際の移行で多くのチームが利用する形態です。
  Application Load Balancer の背後に単一タスクとして実行され（オプションで Amazon Cognito によるゲート）、
  チームでアクセスを共有し、長時間かかる移行を確実に進めることができます。

要するに、**手早く評価したい場合や小規模なジョブならローカル、実際の本番移行なら Fargate** です。
いずれの場合もソースは読み取り専用でアクセスされます。それぞれの実行方法は
[第1章 §1.2–§1.3](01-setup.md) をご覧ください。


**Q4. ソースとターゲットは同じ AWS リージョンである必要がありますか？**

**はい。** ソースとターゲットは **同じリージョン** でなければならず、オプションの CDC パイプラインも
単一のリージョン/VPC で実行されます。**クロスリージョン移行はサポートされていません。**


**Q5. 2つのデータパスとは何であり、どちらが必要ですか？**

| お客様の状況 | 使用するもの |
|---|---|
| 一回限りの移行。短いメンテナンス書き込み凍結が許容できる | **Full Load のみ** — ストリーミングインフラなし、継続コストなし。 |
| 大規模／継続的。**ほぼゼロダウンタイム** のカットオーバーが必要 | **Full Load + CDC** — 隙間のない引き継ぎにより、MySQL を稼働させたまま DSQL を収束させる。 |

CDC は実際の可動部（MSK、MSK Connect、シンクコネクタ）を追加し、**デプロイされている間はコストが発生**します。
継続的なレプリケーションが本当に必要なときのみ使用してください。そうでなければ Full Load 単独の方が
シンプルで安価です。[第10章 §10.1](10-conclusion.md#101-どの経路が必要か) をご覧ください。


**Q6. ツールがアプリケーションのカットオーバーまで行ってくれますか？**

いいえ。本ツールは **評価・変換・ロード・ストリーミング・検証** を行いますが、アプリケーションを
*いつ* *どのように* 切り替えるかは、お客様だけが下せる運用上の判断です。ツールは切り替え可否を
証拠で裏付け（Validation）、CDC の場合は隙間のないストリームを提供します。カットオーバーは、
ツールが画面に表示する手順書（runbook）に従ってお客様ご自身が実施します
（[第10章 §10.3](10-conclusion.md#103-カットオーバー-アプリケーションを-dsql-へ切り替える)）。

## B. Full Load（一括コピー）

**Q7. Full Load はどのように動作し、非常に大きなテーブルでも安全ですか？**

Full Load はツール **独自の一括ローダー**（Debezium スナップショットではありません）です。ソース行を
**主キーの keyset（キーセット）ページネーション**（`WHERE pk > :last ORDER BY pk LIMIT n`、`OFFSET` は
決して使わない）でサーバーサイドカーソル越しに **ストリーミング** し、流れてくるそばから書き込みます。
そのため **テーブルのサイズに関わらずメモリは1ページ分に制限され**、テーブル全体が RAM に読み込まれることは
ありません。**TB 規模** のソースと非常に大きなテーブル向けに設計されています。
[第3章 — Full Load](03-full-load.md) をご覧ください。


**Q8. Full Load はべき等ですか？ 中断された場合はどうなりますか？**

はい。行は境界付き並列のべき等な `INSERT … ON CONFLICT` バッチとしてロードされ、各バッチは安定した
PK 範囲にマッピングされます。ロードが **中断された** 場合（クラッシュ、停止、タスク置き換え）、
再実行すると **未完了の PK 範囲のみを再実行** し、中断されなかった状態とまったく同じ状態に収束します —
**重複なし、損失なし**。テーブルごとの失敗は分離されており、1つの不良テーブルが他のテーブルを中断させることは
ありません。


**Q9. Full Load はソースでのバイナリログを必要としますか？**

**いいえ。** Full Load 単独では CDC の前提条件（binlog もレプリケーションユーザーも）は一切不要です。
通常の読み取り専用接続でソースを読み取ります。バイナリログが必要なのは **CDC** だけです（Q12 参照）。


**Q10. Full Load のスループットをチューニングできますか？**

はい。境界付きのデフォルト値があり、大きなハードウェア向けに引き上げたり、負荷の高いソースを保護するために
引き下げたりできます。`DSQL_MIGRATOR_FULL_LOAD_TABLE_PARALLELISM`（同時に処理するテーブル数、デフォルト 4）、
`…_BATCH_PARALLELISM`（テーブルあたりの実行中バッチ数、デフォルト 8）、`…_BATCH_ROWS`
（書き込みあたりの行数、デフォルト 2000、DSQL の 3000 で厳密に上限あり）。同時に開く DSQL 接続の総数 ≈
テーブル × バッチ並列度 のため、クラスタの接続クォータ内に収まるようにしてください。
[第7章 §7.2](07-performance-and-tuning.md#72-並列度のチューニング) をご覧ください。


**Q11. 並列度を上げても、なぜ速くならないことがあるのですか？**

DSQL はストレージを **主キー単位で** 分散します。そして単調増加する `AUTO_INCREMENT` PK は、
すべての挿入を同じ「最も右端の」キー範囲に集中させ — **書き込みホットスポット** を生みます。
高並列度ではこれが楽観的並行性の競合率（`SQLSTATE 40001`）を高めるため、スループットの向上が
頭打ちになります。これが、Evaluation が `AUTO_INCREMENT` にフラグを立て、Schema Conversion が
PK 戦略（整数のまま維持 / UUID に変換 / キャッシュ付き identity）を提供する理由です。
[第7章 §7.1](07-performance-and-tuning.md#71-この設計の理由-技術的な根拠) をご覧ください。

## C. CDC（ストリーミングレプリケーション）

**Q12. CDC はソースに何を要求しますか？**

CDC は、**フル行イメージを伴う ROW フォーマット** のバイナリログ（`binlog_format=ROW`、
`binlog_row_image=FULL`）と、**レプリケーション権限** を持つユーザーを必要とします。また、
Full Load のウォーターマーク（watermark）時点のログが CDC 開始まで残るように **binlog の保持期間を
延長** する必要があります（Aurora MySQL はデフォルトで binlog を約24時間しか保持しません）。RDS/Aurora では、
これらは `my.cnf` ではなく **パラメータグループ** と `mysql.rds_set_configuration` で設定します。
前提条件のゲートは、これらが満たされるまで **CDC をブロック** します。[§1.1](01-setup.md#11-前提条件) と
[第6章 §6.2](06-limitations.md#62-移行プロセスの制限) をご覧ください。


**Q13. Full Load → CDC の引き継ぎはどのように「隙間なし」になるのですか？**

Full Load は一貫したスナップショット地点で **binlog/GTID ウォーターマーク** を記録します。
CDC は **まさにそのウォーターマークから** ストリーミングを開始し、適用がべき等かつ PK キー付きであるため、
スナップショットとストリームの間にいかなる重複があっても **重複を作り出すことはできません**。その結果、
隙間もなく、二重適用もありません。[第4章 — CDC](04-cdc-and-dsql-constraints.md) をご覧ください。


**Q14. CDC は何をレプリケートし、何をレプリケートしないのですか？**

CDC は **行データの変更**（INSERT/UPDATE/DELETE）をレプリケートするのであって、SQL ではなく、
また **DDL でもありません**。CDC 実行 **中** のソースでのスキーマ変更は DSQL に **伝播されません** —
同等の DDL をお客様ご自身で DSQL に適用する必要があります。ターゲットの形状にもはや一致しない行は、
失われるのではなく **DLQ**（デッドレター）に送られます。
[第4章 §4.2](04-cdc-and-dsql-constraints.md#42-cdc-は-スキーマ-ではなく-データ-を複製する--重要) をご覧ください。


**Q15. なぜ既製の JDBC シンクではなく、カスタム DSQL シンクコネクタなのですか？**

既製シンクでは処理できない、DSQL 固有の3つの理由があります。(1) 書き込み競合を、バッチ全体を
再送信するのではなく **ステートメントレベル**（競合した行だけを再実行）で再試行するため、
ホットキーでのライブロックを回避します。(2) 短命の **IAM トークンを発行・更新** するため、
数時間に及ぶストリームが認証で停止することがありません。(3) DSQL の 3000行 / 1 MiB のエンベロープを
強制し、処理不能（poison）な行を DLQ にルーティングします。
[第4章 §4.1](04-cdc-and-dsql-constraints.md#41-パイプライン) をご覧ください。


**Q16. CDC は一時停止できますか？ また課金されますか？**

ストリーミングパイプライン（MSK Serverless + MSK Connect、加えてツールが作成した場合は NAT ゲートウェイ）は
**実行されている限りコストが発生** します — 無料の「一時停止」はありません。カットオーバー後は
cdc-stack を撤去してください（**Cut over** ステップの *Delete all CDC infrastructure* がこれを行います）。
Full Load 単独ではストリーミングインフラを **一切** プロビジョニングしません。
[第6章 §6.2](06-limitations.md#62-移行プロセスの制限) をご覧ください。


**Q17. CDC インフラのデプロイ／撤去にはどれくらいかかり、なぜそんなに時間がかかるのですか？**

デプロイも撤去も、いずれもおよそ **15〜25分** かかります。これは仕様上、瞬時には終わりません —
その理由を説明します。

**起動（デプロイ）に時間がかかる理由** — cdc-stack はいくつかの AWS リソースを順番に作成します。

1. **MSK Serverless クラスタのプロビジョニング** — マネージド Kafka クラスタが準備完了になるのを待ちます
   （最大の単一の塊）。
2. **2つの MSK Connect コネクタの作成** — まずソース（Debezium）コネクタ（そのトピックが存在するように）、
   次にシンク（DSQL）コネクタ。それぞれが `CREATING → RUNNING` になるのに数分かかり、順番に実行されるため、
   時間が積み重なります。
3. その間、VPC 内の **オフセットシーダー Lambda** が、隙間のない引き継ぎのためのオフセットをシードします。

**撤去に時間がかかる理由** — MSK 自体の削除は比較的速いのですが、最後まで残るリソース —
VPC 内の **オフセットシーダー Lambda** — がボトルネックです。VPC にアタッチされた Lambda を削除すると、
AWS はそれが使用した **ネットワークインターフェース（ENI）** をクリーンアップする必要があり、そのクリーンアップは
**最大 ~20分** かかりうる、文書化された AWS の動作です（私たち自身のテストでも、削除時間の大部分を占めていました）。
この Lambda はプライベートな MSK bootstrap に到達するために **VPC 内に存在しなければならない** ため、
この遅延は撤去時に回避するのが困難です。

> **ヒント：** 反復や再起動の際には、可能な限り完全な削除・再作成ではなく **その場で再起動する
> （既存のインフラを維持する）** ようにしてください — これにより、この ~20分の ENI クリーンアップを回避できます。
> カットオーバーが完了し CDC が不要になったら、スタックを最終的に撤去してください。

## D. スキーマ & 型変換

**Q18. ツールは何が移行可能かをどのように判断しますか？**

Evaluation は **すべてのオブジェクト** を、**AUTO**（自動的に変換）、**MANUAL**（変換されるが判断／
アプリケーション側の変更が必要）、**UNSUPPORTED**（自動変換なし — 再設計が必要）のいずれかに分類し、
作業量の見積もりと名前衝突の検出を伴います。ロードの **前に** すべての UNSUPPORTED 項目を解決し、
各 MANUAL 項目について判断を下してください。[第2章](02-evaluation-and-schema-conversion.md) をご覧ください。


**Q19. MySQL のデータ型は DSQL にどのようにマッピングされますか？**

主なものは次のとおりです。

| MySQL 型 | Aurora DSQL 型 | 備考 |
|---|---|---|
| `TINYINT(1)` | `boolean` | MySQL の boolean 慣例。 |
| `…INT UNSIGNED`（符号なし整数） | `smallint` / `integer` / `bigint` / `numeric(20,0)` | より広い型に **無損失で** 拡張。 |
| `BIT(n)` | サイズ付き整数（`smallint`…`numeric(20,0)`） | DSQL に `BIT` 型はない。 |
| `DECIMAL(p,s)` | `numeric(p,s)` | 精度 > 38 は非対応。 |
| `DATETIME` | `timestamp`（UTC） | UTC に正規化。 |
| `ENUM` | `text` + `CHECK` | DSQL に `ENUM` はない。 |
| `BLOB` / `BINARY` | `bytea` | 生バイトを保持。 |
| `JSON` | `json` | |

**すべての型についての完全なマッピング**（ターゲット DSQL 型 + 格納される値の形式）は、
[第4章 §4.6](04-cdc-and-dsql-constraints.md#46-mysql--dsql-の型と制約の処理-リファレンス) にあります。
**Full Load ローダーと CDC シンクは同一のマッピングに従う**（共有の write-contract テストがそれを強制）ため、
どちらのパスで移行しても、行は同じように着地します。


**Q20. 外部キー、トリガー、ストアドプロシージャはどうなりますか？**

DSQL にはこれらがありません。**外部キー** は DDL からは削除されますが **レポートには保持** されます
（参照整合性はアプリケーションで強制してください） — MANUAL としてフラグが立ちます。**トリガー、
ストアドプロシージャ/関数、スケジュールされたイベント** は UNSUPPORTED としてフラグが立ちます —
アプリケーションで再実装してください（スケジュールされたイベント → EventBridge / Lambda）。
[第6章 §6.1](06-limitations.md#61-aurora-dsql-の機能制限スキーマがこれらに適合している必要があります) をご覧ください。


**Q21. テーブルに主キーがありません。移行できますか？**

そのままでは移行できません。DSQL は **主キーを必須とし**、ツールの keyset エクスポートも主キーを必要とするため、
主キーのないテーブルは **UNSUPPORTED** としてフラグが立ち、ロードできません。まずソースで（または再設計の中で）
主キーを追加してください。

## E. 検証 & 正確性

**Q22. 移行が正しいことをどうやって知るのですか？**

Validation（ステップ5）は **証拠** を提供し、ソースとターゲットを **段階的に厳しくなる3つのパス** で比較します —
それぞれが前より精密（かつ高コスト）です。

| パス | 何を確認するか | 何を捕捉するか |
|---|---|---|
| **行数** | 両側それぞれのテーブルごとの正確な `COUNT(*)` | 行が丸ごと欠落または余分にある |
| **チェックサム**（順序非依存） | すべての行を **両エンジンで同じ方法** でハッシュして比較 | **数は一致するが値が異なる** 行 |
| **完全な主キー突合** | 両側の **すべての PK** をマージし、**ターゲットに欠落している** PK と **ターゲットに余分にある** PK を特定 | **どの行** が欠落／余分かを、行単位で正確に |

- 判定が **MATCH になるのは、すべての差異が説明されたときのみ** です — 例えば、移行中もソースが変化し続けたことによる
  **ドリフト**（Q23）、意図的な **過大値の隔離（quarantine）**（Q24）、あるいは **CDC がまだ追いついている最中** など。
  説明のつかない欠落／余分な行が1つでもあれば、それは MATCH では *ありません*。
- **行数だけの「一致」は決して信頼されません。** 数が等しくても値が異なることを隠している可能性があるため、
  真の一致とみなすには、テーブルはチェックサムと PK 突合にも合格しなければなりません。

したがって、カットオーバー前にこれを実行することは、希望ではなく **ソースとターゲットが実際に一致するという証明** に
基づいて切り替えを決定することを意味します。[第5章 — Validation](05-validation.md) をご覧ください。


**Q23. 移行中もソースが変わり続けます。検証が誤らないのですか？**

いいえ — 正しく帰属されます。Validation はソースの GTID を Full Load ウォーターマークと照合して読み取り、
**ドリフト** を報告します。したがって、**新たなソース活動** による件数の差分はバグと区別されます。
クリーンな最終的な go/no-go のためには、ソースへの書き込みを凍結し、先に CDC をドレインさせてください（Q27）。


**Q24. DSQL が格納できない行（例：1 MiB を超える値）はどうなりますか？**

**決して黙って破棄されることはありません。** Full Load では、DSQL の値あたり ~1 MiB の制限を超える値は
行単位で **隔離（quarantine）** され（その主キー + 理由がエラーログに記録される）、テーブルの残りはロードされます。
CDC では、そのような行は **DLQ** に送られます。パイプラインを通過することさえできない値（> ~8 MiB）は、
Evaluation からの `OVERSIZED_LOB` フラグに従って **キャプチャの時点で除外** されます。何が取り分けられたかを
正確に確認できます。
[第6章 §6.1](06-limitations.md#61-aurora-dsql-の機能制限スキーマがこれらに適合している必要があります) をご覧ください。


**Q25. 「silent より loud」とは、実際にはどういう意味ですか？**

本ツールは、データを静かに破損させることを拒否します。例：`{0,1}` の範囲外の `TINYINT(1)` 値は、
それを `true` に押し込むのではなく **そのテーブルのロードを停止** します。範囲外の `TIME` は、
切り詰められるのではなく失敗します。不完全なロードは **FAILED** として報告され、偽の成功にはなりません。
お客様はソースを修正（またはそのカラムを除外）して再実行します。

## F. カットオーバー、ロールバック & 運用

**Q26. カットオーバー時にダウンタイムはありますか？**

**Full Load のみ** の場合、ダウンタイムは最終的な凍結 + ロード + 検証の長さです。
**Full Load + CDC** の場合、それは短い **最終ドレイン + スモークテスト** に縮小されます —
CDC が MySQL を稼働させたまま DSQL を収束させ続けるため、凍結するのは本当に最後だけです。


**Q27. 安全なカットオーバーの手順は？**

（CDC パス）CDC に追いつかせる → **ソースへの書き込みを凍結** → 最終ドレインを待つ（ラグ → 0）→
**Validation を再実行** → クリーンな MATCH のときのみカットオーバー → アプリを切り替えてスモークテスト →
**CDC パイプラインを最後に撤去**。詳細と Full Load のみのバリアントは
[第10章 §10.3](10-conclusion.md#103-カットオーバー-アプリケーションを-dsql-へ切り替える) にあります。


**Q28. ロールバックできますか？**

計画しておけば可能です。DSQL にサインオフするまで、MySQL ソースを **凍結（読み取り専用）したまま、削除しない** ように
保ってください。切り替える前であれば、ロールバックは簡単です（ソースは手つかずで正典です）。アプリケーションが
DSQL に書き込んだ **後** は、それらの新しい行は DSQL に **のみ** 存在します（本ツールは MySQL → DSQL を
レプリケートするのであって、その逆は **しません**）。そのため、そのときロールバックするということは、
それらを自分で突合することを意味します。ロールバックのルールは、カットオーバーの *前に* 決めておいてください。


**Q29. どのような認証情報と権限が必要で、私のデータはどのように保護されますか？**

ソースは通常の読み取り専用 MySQL 接続を使用します。ターゲットは DSQL の **IAM トークン認証（DB パスワードなし）**
を使用します。すべての接続は **TLS** を使用します。認証情報は **セッションごとのメモリ内にのみ** 存在し —
ディスク、ログ、レポート、ジョブの状態に書き込まれることは決してありません。ログとレポートは主キーと件数を
記録し、**行の値は決して記録しません**。オプションの AI アシスト（Amazon Bedrock、デフォルトではオフ）は
**助言のみ** であり、CDC のデータパスには **決して** 入りません。

ツールが必要とする AWS 権限は、ローカルで実行しても Fargate で実行しても同じです。異なるのは
**それらの権限がどこにアタッチされるか** です：

- **必須（両モード）：** DSQL IAM トークンを発行するための `dsql:DbConnect` / `dsql:DbConnectAdmin`
  （お客様のクラスタにスコープされる）、加えてソース MySQL への読み取り専用アクセス。オプションで
  `secretsmanager:GetSecretValue`（ソース認証情報のシークレットを再利用するため）と `bedrock:InvokeModel`
  （AI アシストを有効にした場合のみ）。
- **ローカルで実行** — ツールは標準の認証情報チェーン（`~/.aws`、環境変数、`AWS_PROFILE`、SSO）を介して
  **お客様自身の IAM アイデンティティ** を使用するため、*お客様の* アイデンティティがこれらの権限を直接
  保持している必要があります。特に、CDC を使用するには、cdc-stack が CloudFormation を介して MSK、
  MSK Connect、IAM ロールをプロビジョニングするため、お客様のアイデンティティには、より広い
  **インフラ作成権限** が必要です。
- **AWS（ECS Fargate）にデプロイ** — 認証情報をアプリに渡すことはありません。CloudFormation が
  **最小権限のタスクロール** を作成し、それらの権限をそれにアタッチします。CDC インフラのデプロイのような
  特権的な作業は、長時間実行されるタスクロールには付与されません。代わりに、タスクは **その操作の期間中のみ、
  専用のデプロイロール（CdcDeployRole）を引き受け** るため、権限昇格は分離されます。（app-stack を
  *最初にデプロイする* 人は、IAM ロールを作成する権限が一度だけ必要です。）このモードが最小権限に最も適合します。

作業別の具体的な IAM アクションです（**Fargate では自動生成されるタスクロールにアタッチされ、自分で
記述する必要はありません**。**ローカル実行時は自分の ID がこれらを保持している必要があります**）:

| 対象 | IAM アクション（最小） |
|---|---|
| **ターゲット DSQL（常時）** | `dsql:DbConnect`、`dsql:DbConnectAdmin`（IAM トークン発行）、`dsql:GetCluster` |
| **ソース MySQL（常時）** | IAM アクションなし — 読み取り専用の MySQL ユーザー/パスワード（または下記のシークレット） |
| **ソースシークレット（任意）** | `secretsmanager:GetSecretValue` — ソース認証情報が Secrets Manager シークレットにある場合のみ |
| **AI アシスト（任意）** | `bedrock:InvokeModel`、`bedrock:InvokeModelWithResponseStream` — 選択したモデルにスコープ。AI を有効にした場合のみ |
| **CDC — パイプラインのデプロイ/削除** | cdc-stack が必要とする広範なインフラ作成権限: `cloudformation:CreateStack`/`UpdateStack`/`DeleteStack`/`Describe*`/`GetTemplate`、広範な `ec2:*`（VPC サブネット・NAT・EIP・ルートテーブル・セキュリティグループ・VPC エンドポイント・ネットワークインターフェイス）、`iam:CreateRole`/`AttachRolePolicy`/`PassRole`/…（コネクタロール）、`kafka:*` / `kafkaconnect:*`（MSK Serverless + MSK Connect）、`logs:*`、プラグインバケットへの `s3:*`。Full Load のみの移行では **一切不要**。 |

> **Full Load のみ** なら上表の最初の 3 行だけで十分です。**CDC** は最後の行（広範なインフラ作成権限）を
> 追加します。Fargate ではこの権限は分離された `CdcDeployRole`（デプロイ/削除中のみ引き受け）にあり、
> 常時稼働のタスクは保持しません。しかし **ローカル実行では自分の ID が CDC 行全体を保持する必要がある**
> ため、CDC には Fargate を推奨します。


**Q30. 複数の移行を実行したり、ツールを水平スケールしたりできますか？**

AWS ホスト形態は **単一の ECS Fargate タスク** であり、そのジョブ／セッションの状態はエフェメラルストレージ上の
ローカル SQLite です — タスクの置き換えは実行中のジョブ状態を失います（再接続して読み取り専用のステップを
再実行します）。その状態を共有ストア（例：ゼロロスの再開のための EFS マウント）に移さない限り、複数のタスクを
実行しないでください。[第6章 §6.3](06-limitations.md#63-デプロイの制限aws-ホスト形態) をご覧ください。


**Q31. すべての AWS インフラを削除して、完全にゼロからやり直すには？**

まず違いを明確にしてください。UI の **Start over** ボタンは、ツールの *セッション*（接続、プラン、進捗）を
リセットするだけです — 意図的に、いかなる AWS リソースも **削除しません** ので、コストのかかるものが誤って
撤去されることはありません。実際にインフラを削除してすべてのコストを止めるには、次の順序でスタックを撤去します
（正確なコマンドを含む完全な手順は [デプロイ §9 — Teardown](../../../deploy/DEPLOYMENT.ja.md#teardown) にあります）：

1. **最初に CDC インフラ**（CDC をデプロイしたことがある場合のみ — これはコストのかかる MSK / MSK Connect /
   NAT の部分です）。**アプリがまだ実行されている間** に、UI から行います：**Start over（右上）→
   「Delete all CDC infrastructure」**（アプリが `cdc-stack` の削除を駆動、~15〜25分、そしてそれが作成した
   マネージドのソース認証情報シークレットも削除します）。アプリがすでに消えている場合は、スタックを手動で削除します：
   `aws cloudformation delete-stack --stack-name mysql-dsql-cdc-stack`。
2. **app-stack** — `deploy/teardown.sh <stack-name>` を実行（ECS/ALB/IAM スタックを削除。`DELETE_ECR=true`
   を渡すとコンテナイメージリポジトリも削除します）。
3. **build-stack** — オプションの CodeBuild ビルドパスを使用した場合のみ。
4. **スタックが所有しない残留物を確認：** ツールはアカウント／リージョンごとの **プラグインバケット**
   `mysql-dsql-migrator-plugins-<account>-<region>` を自動作成しますが、これはどのスタックにも属さないため、
   `delete-stack` では削除されません — 本当にクリーンな状態にしたい場合は手動で削除してください。また、手作業で
   追加した **Route 53** レコードも削除してください。その後、`mysql-dsql-*` の CloudFormation スタックが
   残っていないことを確認してください。

撤去後は、初回インストールとまったく同じようにゼロから再デプロイできます（デプロイガイド）。*移行そのものだけを
再開したい* 場合 — 同じインフラで、新しいワークフロー — は、代わりに **Start over** を使用してください。
即座で、無料です。
